# 🔄 First Render Cycle: Step by Step

---

## 🧠 What We're Tracing

```
root.render(<App />)
              │
              └──→ ??? → ??? → ??? → pixels on screen
```

Every React developer writes `root.render(<App />)`.  
Almost none know what happens after that semicolon.

By the end of this phase, you'll trace every step — from that one function call to the browser painting the first frame.

---

## 🗺️ The Complete First Render Map

```
┌─────────────────────────────────────────────────────────────────┐
│                    root.render(<App />)                         │
└───────────────────────────┬─────────────────────────────────────┘
                            │
            ┌───────────────▼───────────────┐
            │        STEP 1: TRIGGER        │
            │   Schedule work on FiberRoot  │
            └───────────────┬───────────────┘
                            │
            ┌───────────────▼────────────────┐
            │       STEP 2: RENDER PHASE     │  ← interruptible
            │                                │
            │  2a. beginWork (top → down)    │
            │      Call component functions  │
            │      Build fiber tree          │
            │                                │
            │  2b. completeWork (bottom → up)│
            │      Build effect list         │
            │      Compute DOM props         │
            └───────────────┬────────────────┘
                            │
            ┌───────────────▼────────────────┐
            │      STEP 3: COMMIT PHASE      │  ← synchronous, uninterruptible
            │                                │
            │  3a. BeforeMutation            │
            │  3b. Mutation  ← DOM written   │
            │  3c. Layout    ← refs + layout │
            │       effects                  │
            └───────────────┬────────────────┘
                            │
            ┌───────────────▼────────────────┐
            │      STEP 4: BROWSER PAINT     │
            │   Browser renders pixels       │
            └───────────────┬────────────────┘
                            │
            ┌───────────────▼────────────────┐
            │   STEP 5: PASSIVE EFFECTS      │
            │   useEffect fires              │
            └────────────────────────────────┘
```

## 📍 Step 1 — Trigger

```jsx
const root = createRoot(document.getElementById('root'));
root.render(<App />);
```

### What `root.render(<App />)` actually calls:

```
root.render(<App />)
       │
       ↓
ReactDOMRoot.prototype.render()
       │
       ↓
updateContainer(children, root._internalRoot, null, null)
       │
       ↓
  1. Get current time:
     const lane = requestUpdateLane(current);
     // First render → SyncLane (highest priority)
     // or DefaultLane depending on context
       │
       ↓
  2. Create update object:
     const update = createUpdate(eventTime, lane);
     update.payload = { element: <App /> }
     // This update goes into the HostRootFiber's update queue
       │
       ↓
  3. Enqueue the update:
     enqueueUpdate(current, update, lane)
       │
       ↓
  4. Schedule work:
     scheduleUpdateOnFiber(root, current, lane, eventTime)
       │
       ↓
  5. Ensure root is scheduled:
     ensureRootIsScheduled(root, eventTime)
       │
       ↓
  6. Hand off to Scheduler:
     Scheduler.scheduleCallback(
       priority,
       performConcurrentWorkOnRoot.bind(null, root)
     )
```

### The Fiber Tree at This Point

```
BEFORE root.render():

FiberRoot
    │
    └── HostRootFiber (tag: HostRoot)
          stateNode: FiberRoot
          child: null          ← nothing rendered yet
          memoizedState: null
          updateQueue: null


AFTER root.render() — update enqueued:

FiberRoot
    │
    └── HostRootFiber
          updateQueue: {
            pending: Update {
              payload: { element: <App /> },
              lane: SyncLane
            }
          }
```

Nothing rendered yet. Just work scheduled.

## 🔧 Step 2a — Render Phase: `beginWork` (Top → Down)

React processes fibers one at a time, **top-down**, using DFS.  
For each fiber, `beginWork` is called.

```
beginWork(current, workInProgress, renderLanes)
  │
  ↓
Checks fiber.tag to decide what to do:
  HostRoot       → process root update, get <App /> element
  FunctionComponent → call the function: App(props)
  HostComponent  → process native element ('div', 'button', etc.)
  HostText       → process text node
```

### Tracing Through a Real Component Tree

```jsx
// Our app:
function App() {
  return (
    <div className="app">
      <Header title="My App" />
      <main>
        <p>Hello World</p>
      </main>
    </div>
  );
}

function Header({ title }) {
  return <h1>{title}</h1>;
}
```

#### beginWork — Node by Node

```
STEP 2a — beginWork traversal:

1. beginWork(HostRootFiber)
   │  Process pending update
   │  Payload = { element: <App /> }
   │  Creates WIP fiber for App
   └─→ child: AppFiber (WIP)

2. beginWork(AppFiber)
   │  tag: FunctionComponent
   │  Calls: App({})
   │  App() returns JSX:
   │    <div className="app">
   │      <Header title="My App" />
   │      <main><p>Hello World</p></main>
   │    </div>
   │  Creates WIP fibers for children
   └─→ child: divFiber

3. beginWork(divFiber)
   │  tag: HostComponent ('div')
   │  props: { className: 'app' }
   │  Creates children fibers
   └─→ child: HeaderFiber

4. beginWork(HeaderFiber)
   │  tag: FunctionComponent
   │  Calls: Header({ title: 'My App' })
   │  Header() returns: <h1>My App</h1>
   └─→ child: h1Fiber

5. beginWork(h1Fiber)
   │  tag: HostComponent ('h1')
   │  Creates text child fiber
   └─→ child: textFiber("My App")

6. beginWork(textFiber "My App")
   │  tag: HostText
   │  No children
   └─→ child: null  ← leaf node, beginWork done here
                       completeWork starts
```

### What happens inside `beginWork` for a FunctionComponent:

```
beginWork(HeaderFiber)
       │
       ↓
renderWithHooks(current, workInProgress, Header, props)
       │
       ├── Sets ReactCurrentDispatcher.current = HooksDispatcherOnMount
       │   (first render → mount dispatcher, not update dispatcher)
       │
       ├── Calls Header(props):
       │   Header({ title: 'My App' })
       │   → returns React Element: { type: 'h1', props: { children: 'My App' } }
       │
       └── reconcileChildren(current, workInProgress, nextChildren, lanes)
           │
           └── Creates fiber for <h1> as child of HeaderFiber
```

### First Render vs Update — Mount Dispatcher

```
FIRST RENDER (mount):
  ReactCurrentDispatcher = HooksDispatcherOnMount
  useState  → mountState  → initializes hook storage
  useEffect → mountEffect → registers effect

SUBSEQUENT RENDERS (update):
  ReactCurrentDispatcher = HooksDispatcherOnUpdate
  useState  → updateState → reads from existing hook storage
  useEffect → updateEffect → compares deps, schedules if changed

This is HOW React enforces hooks rules:
  Hook called in wrong order → reads wrong slot in linked list
  Immediate wrong behavior → caught in development
```

## 🔧 Step 2b — Render Phase: `completeWork` (Bottom → Up)

After `beginWork` reaches a leaf node (no children), `completeWork` fires.  
It travels **bottom-up** — completing children before parents.

```
completeWork(fiber)
  │
  For HostComponent ('div', 'h1', etc.):
  │  ├── Creates real DOM node:
  │  │     instance = createInstance('div', props)
  │  │     = document.createElement('div')
  │  │
  │  ├── Appends child DOM nodes to this DOM node:
  │  │     appendAllChildren(instance, workInProgress)
  │  │
  │  ├── Sets props on DOM node:
  │  │     finalizeInitialChildren(instance, type, props)
  │  │     = sets className, style, event listeners, etc.
  │  │
  │  └── Attaches DOM node to fiber:
  │        workInProgress.stateNode = instance
  │
  For FunctionComponent:
  │  └── Bubble up effect flags from children
  │
  Then: move to sibling or return to parent
```

### completeWork Traversal Order

```
COMPLETE WORK — bottom-up:

             HostRoot
                │
              App
                │
              div.app
             /       \
          Header      main
            │           │
           h1           p
            │           │
        "My App"    "Hello World"


completeWork fires in this order:
  1. textFiber "My App"      → no DOM node (text in h1)
  2. h1Fiber                 → createElement('h1')
                               appendChild(textNode "My App")
  3. HeaderFiber             → no DOM node (function component)
  4. textFiber "Hello World" → no DOM node (text in p)
  5. pFiber                  → createElement('p')
                               appendChild(textNode "Hello World")
  6. mainFiber               → createElement('main')
                               appendChild(pFiber.stateNode)
  7. divFiber                → createElement('div')
                               appendChild(h1Fiber.stateNode)
                               appendChild(mainFiber.stateNode)
  8. AppFiber                → no DOM node (function component)
  9. HostRootFiber           → container already exists
```

### The DOM Tree Built in Memory (Not Yet Inserted)

```
After completeWork, in JS memory:

div.app (not in real DOM yet)
  ├── h1
  │    └── "My App" (text node)
  └── main
       └── p
            └── "Hello World" (text node)

This entire tree exists as real DOM nodes
but is NOT attached to document.getElementById('root') yet
```

### Effect List — What completeWork Produces

```
Each fiber gets effectTag flags during render phase:

Placement    (0b000000000010) → needs to be inserted into DOM
Update       (0b000000000100) → props changed, needs DOM update
Deletion     (0b000000001000) → needs to be removed from DOM
LayoutEffect (0b000001000000) → has useLayoutEffect to run
PassiveEffect(0b100000000000) → has useEffect to run

First render: every new fiber gets Placement flag

Effect list = linked list of fibers that have work to do
React builds this during completeWork (bottom-up)
Used in commit phase to avoid walking entire tree again
```

```
HostRootFiber (WIP)

  │
  └── AppFiber (WIP)

              │           stateNode: <h1> (real DOM node, not inserted)

              └── mainFiber (WIP)
                    effectTag: Placement
                    stateNode: <main> (real DOM node, not inserted)
```

## ⚡ Step 3 — Commit Phase (Synchronous, Uninterruptible)

Commit phase has **three sub-phases.**  
Each sub-phase walks the effect list once.

```
commitRoot(root)
    │
    ├── SUB-PHASE 1: BeforeMutation
    │     commitBeforeMutationEffects()
    │
    ├── SUB-PHASE 2: Mutation  ← DOM CHANGES HAPPEN HERE
    │     commitMutationEffects()
    │
    └── SUB-PHASE 3: Layout    ← AFTER DOM, BEFORE PAINT
          commitLayoutEffects()
```

---

### Commit Sub-Phase 1: BeforeMutation

```
commitBeforeMutationEffects()
  │
  Walks effect list
  │
  For each fiber with BeforeMutation flag:
  │
  ├── Class components:
  │     getSnapshotBeforeUpdate()
  │     snapshot stored for componentDidUpdate
  │
  ├── Function components:
  │     NO action on first render
  │     On updates: schedules useEffect CLEANUP functions
  │
  └── Schedules flushPassiveEffects (useEffect) asynchronously
        scheduleCallback(NormalPriority, flushPassiveEffects)
        ← useEffect is SCHEDULED here, not run yet
```

---

### Commit Sub-Phase 2: Mutation

**This is where the DOM is actually changed.**

```
commitMutationEffects()
  │
  Walks effect list
  │
  For Placement (new nodes):
  │     commitPlacement(fiber)
  │       │
  │       ├── Find parent DOM node (walk up fiber tree)
  │       ├── Find before sibling if inserting before
  │       └── parentNode.appendChild(fiber.stateNode)
  │           OR
  │           parentNode.insertBefore(fiber.stateNode, before)
  │
  For Update (prop changes):
  │     commitWork(fiber)
  │       └── updateDOMProperties(domNode, updatePayload)
  │           sets className, style, event listeners, etc.
  │
  For Deletion:
  │     commitDeletion(fiber)
  │       ├── Removes DOM node
  │       ├── Runs useLayoutEffect cleanups
  │       └── Runs useEffect cleanups
  │
  After ALL mutations:
      root.current = finishedWork  ← POINTER FLIP
      (WIP tree becomes current tree)
      (old current becomes next WIP)
```

### The Pointer Flip — Critical Timing

```
BEFORE mutation:                AFTER mutation + pointer flip:

FiberRoot                       FiberRoot
  current → OLD tree              current → NEW tree (just committed)
  WIP     → NEW tree (built)      WIP     → OLD tree (recycled next render)

The flip happens BETWEEN mutation and layout sub-phases.

WHY this timing matters:
  useLayoutEffect fires AFTER the flip
  → when useLayoutEffect runs, root.current IS the new tree
  → reading state in useLayoutEffect sees committed state

  useEffect fires AFTER paint
  → also sees committed state
  → but browser has already painted by then
```

---

### Commit Sub-Phase 3: Layout

```
commitLayoutEffects()
  │
  Walks effect list
  │
  For FunctionComponent with LayoutEffect flag:
  │     commitHookEffectListMount(HookLayout, fiber)
  │       └── Runs useLayoutEffect callbacks
  │             const cleanup = useLayoutEffect(() => {
  │               // DOM is updated, browser hasn't painted yet
  │               // You CAN read layout: offsetHeight, getBoundingClientRect
  │               // Runs synchronously — blocks paint
  │             });
  │
  For FunctionComponent — ref assignment:
  │     ref.current = fiber.stateNode
  │       └── After layout effects
  │
  For HostComponent — ref assignment:
  │     ref.current = domInstance
  │
  For Class components:
        componentDidMount()  OR  componentDidUpdate()
```

### What You Can and Can't Do in Each Effect

```
┌─────────────────────────────────────────────────────────────┐
│                    EFFECT TIMING                             │
│                                                             │
│  useLayoutEffect(() => {                                    │
│    // ✅ DOM is updated                                     │
│    // ✅ Refs are assigned                                  │
│    // ✅ Can read layout: offsetHeight, scrollTop           │
│    // ✅ Can setState → triggers sync re-render before paint│
│    // ❌ Browser has NOT painted yet                        │
│    // ❌ User cannot see changes yet                        │
│    // ⚠️  Runs synchronously — blocks browser paint         │
│  });                                                        │
│                                                             │
│  useEffect(() => {                                          │
│    // ✅ DOM is updated                                     │
│    // ✅ Refs are assigned                                  │
│    // ✅ Browser HAS painted                                │
│    // ✅ User CAN see the current render                    │
│    // ✅ Async — does not block paint                       │
│    // ❌ setState here → second render (after first paint)  │
│  });                                                        │
└─────────────────────────────────────────────────────────────┘
```

## 🎨 Step 4 — Browser Paint

```
COMMIT PHASE DONE
  │
  ↓
React releases the main thread
  │
  ↓
Browser's rendering pipeline runs:
  1. Style recalculation
     (which CSS rules apply to which elements)
  2. Layout / Reflow
     (compute position + size of every element)
  3. Paint
     (fill pixels: colors, text, borders, shadows)
  4. Composite
     (combine layers, GPU upload)
  │
  ↓
User sees content on screen  ← FIRST CONTENTFUL PAINT
```

```
┌────────────────────────────────────────────────────────────┐
│              BROWSER RENDERING PIPELINE                     │
│                                                            │
│   JS (React commit)                                        │
│   ──────────────────────────────────────────────────────  │
│                                                            │
│                     │ release main thread                  │
│                     ↓                                      │
│   Style Calculation → Layout → Paint → Composite           │
│   ─────────────────────────────────────────────────────── │
│                                                            │
│                     │ first frame                          │
│                     ↓                                      │
│   User sees content on screen                              │
│                                                            │
│                     │ after paint                          │
│                     ↓                                      │
│   useEffect fires                                          │
└────────────────────────────────────────────────────────────┘
```

## 🔁 Step 5 — Passive Effects (useEffect)

After the browser paints, React's scheduler fires `flushPassiveEffects`:

```
flushPassiveEffects()
  │
  ├── CLEANUP phase first:
  │     Run cleanup functions from PREVIOUS render's useEffects
  │     (On first render: nothing to clean up)
  │
  └── MOUNT phase:
        For each fiber with useEffect:
          commitHookEffectListMount(HookPassive, fiber)
            │
            └── Runs each useEffect callback:
                  const cleanup = useEffect(() => {
                    // Everything is painted
                    // DOM available, refs available
                    // Safe to start subscriptions, timers, fetch
                    
                    return () => {
                      // cleanup function stored
                      // runs before next effect or unmount
                    };
                  }, []);
```

## 🔬 Zoom In: What Happens When App() Is Called

```jsx
function App() {
  const [count, setCount] = useState(0);  // hook call 1
  const [name, setName] = useState('');   // hook call 2

  useEffect(() => {                        // hook call 3
    document.title = `Count: ${count}`;
  }, [count]);

  return <div>{count}</div>;
}
```

When React calls `App()` during render phase:

```
renderWithHooks(null, AppFiber, App, {})
  │
  ├── Set dispatcher to HooksDispatcherOnMount
  │
  ├── Execute App():
  │
  │   useState(0):
  │     mountState(0)
  │       │
  │       ├── Create hook object:
  │       │   { memoizedState: 0, queue: {...}, next: null }
  │       │
  │       ├── Attach to fiber's hook linked list:
  │       │   AppFiber.memoizedState → hook1 → null
  │       │
  │       └── Return [0, dispatchSetState.bind(AppFiber, queue)]
  │
  │   useState(''):
  │     mountState('')
  │       │
  │       ├── Create hook object:
  │       │   { memoizedState: '', queue: {...}, next: null }
  │       │
  │       ├── Attach to list:
  │       │   AppFiber.memoizedState → hook1 → hook2 → null
  │       │
  │       └── Return ['', dispatchSetState.bind(AppFiber, queue)]
  │
  │   useEffect(() => {...}, [count]):
  │     mountEffect(create, [count])
  │       │
  │       ├── Create hook object:
  │       │   { memoizedState: { create, deps: [0], tag: Passive },
  │       │     next: null }
  │       │
  │       ├── Attach to list:
  │       │   AppFiber.memoizedState → hook1 → hook2 → hook3 → null
  │       │
  │       └── Mark fiber with PassiveEffect flag
  │
  └── App() returns JSX → React Element
```

### The Hook Linked List

```
AppFiber.memoizedState:

hook1                   hook2                   hook3
┌─────────────────┐    ┌─────────────────┐    ┌─────────────────┐
│ memoizedState:0 │───→│ memoizedState:''│───→│ memoizedState:  │
│ baseState: 0    │    │ baseState: ''   │    │  { create, deps }│
│ queue: {...}    │    │ queue: {...}    │    │ queue: null     │
│ next: →         │    │ next: →         │    │ next: null      │
└─────────────────┘    └─────────────────┘    └─────────────────┘
  useState(0)            useState('')           useEffect(...)

This is WHY hooks must always be called in the same order.
React reads hooks by position in this linked list.
Call hooks conditionally → wrong hook reads wrong slot.
```

## 🔍 The DOM Before vs After Commit

```
BEFORE COMMIT MUTATION:

Real DOM (document):
  <html>
    <body>
      <div id="root">   ← empty
      </div>
    </body>
  </html>

JS Memory (not in DOM):
  <div class="app">
    <h1>My App</h1>
    <main>
      <p>Hello World</p>
    </main>
  </div>


AFTER COMMIT MUTATION (appendChild called):

Real DOM (document):
  <html>
    <body>
      <div id="root">
        <div class="app">        ← inserted
          <h1>My App</h1>        ← inserted
          <main>                 ← inserted
            <p>Hello World</p>   ← inserted
          </main>
        </div>
      </div>
    </body>
  </html>
```

**On first render: one `appendChild` call.**  
React inserts the top-level DOM node. All children were already assembled in memory during `completeWork`. This is why first render is efficient — one DOM insertion, not N.

## ⏱️ Strict Mode — Double Invocation

React 18 StrictMode in development changes the first render:

```
WITHOUT StrictMode:           WITH StrictMode (development only):

App() called once             App() called TWICE
                                1st call: result thrown away
                                2nd call: result used

useLayoutEffect               useLayoutEffect
  mount                         mount
                                cleanup
                                mount (again)

useEffect                     useEffect
  mount                         mount
                                cleanup
                                mount (again)
```

```
WHY StrictMode double-invokes:

React's concurrent mode CAN restart renders
(interrupted render → restart from beginning)

StrictMode simulates this in development:
  "If your component has side effects in the render function,
   they'll appear doubled → you'll notice and fix them"

WHAT THIS CATCHES:
  - API calls in component body (not useEffect)
  - Mutating external variables during render
  - Non-idempotent render functions
  - Effects that don't clean up properly

PRODUCTION: No double invocation, no impact
```

## 🔗 DSA / Internals Connection

```
┌──────────────────────────────────────────────────────────────┐
│  FIRST RENDER STEP          CS / DSA CONCEPT                 │
├──────────────────────────────────────────────────────────────┤
│  Fiber tree traversal       DFS on N-ary tree                │
├──────────────────────────────────────────────────────────────┤
│  beginWork (top-down)       Pre-order DFS traversal          │
├──────────────────────────────────────────────────────────────┤
│  completeWork (bottom-up)   Post-order DFS traversal         │
├──────────────────────────────────────────────────────────────┤
│  Hook storage               Singly linked list               │
│                             (memoizedState chain)            │
├──────────────────────────────────────────────────────────────┤
│  Effect list                Linked list of work units        │
├──────────────────────────────────────────────────────────────┤
│  Commit pointer flip        Double buffering                 │
├──────────────────────────────────────────────────────────────┤
│  Single appendChild         Tree assembled in memory first   │
│  on first render            (O(1) DOM insertion not O(n))    │
├──────────────────────────────────────────────────────────────┤
│  Scheduler task queue       Priority queue (min-heap)        │
├──────────────────────────────────────────────────────────────┤
│  Lane model                 Bitmask operations               │
│  (SyncLane, DefaultLane)    32-bit integer flags             │
└──────────────────────────────────────────────────────────────┘
```

### Why Post-Order for completeWork

```
Pre-order (top-down):
  Visit parent → then children
  Used for beginWork because:
    parent decides what children to create

Post-order (bottom-up):
  Visit children → then parent
  Used for completeWork because:
    parent needs children's DOM nodes to appendChildren
    parent needs children's effect flags bubbled up
    "build from leaves, assemble upward"
```

## 🏭 Production Relevance — MUST KNOW

### Long First Render — What Breaks

```
Large app, slow device:
  Render phase: 200ms of JS execution
  
Legacy mode (ReactDOM.render):
  Main thread blocked for 200ms
  Browser cannot respond to input
  Scroll, clicks, animations: frozen
  User sees blank/frozen page

Concurrent mode (createRoot):
  Render phase: chunked into 5ms slices
  Browser handles input between slices
  Page may show partial content (with Suspense)
  User sees loading states, not freezes
```

### Code Splitting — Why It Helps First Render

```jsx
// Without code splitting:
// ALL component code downloaded + parsed before first render
import HeavyDashboard from './HeavyDashboard'; // 200kb
import LightLanding from './LightLanding';     // 5kb

// With code splitting:
// Only LightLanding runs in first render cycle
// HeavyDashboard downloaded lazily
const HeavyDashboard = lazy(() => import('./HeavyDashboard'));

function App() {
  return (
    <Suspense fallback={<Spinner />}>
      <HeavyDashboard />  {/* doesn't block first render */}
    </Suspense>
  );
}
```

### StrictMode in Production Codebase

```jsx
// Standard production setup:
createRoot(document.getElementById('root')).render(
  <React.StrictMode>
    <App />
  </React.StrictMode>
);

// StrictMode is development-only overhead
// In production builds: StrictMode is a passthrough
// No double invocation, no performance cost
// Always use it in development
```

## ⚠️ Silent Bugs & Failure Cases

### Bug 1: Side Effect in Render Body

```jsx
// ❌ Side effect during render — breaks in concurrent mode
let renderCount = 0;

function ProductList() {
  renderCount++; // mutation during render
  // Concurrent mode may call this function multiple times
  // renderCount becomes wrong
  // StrictMode doubles it → you notice in dev

  return <div>{/* products */}</div>;
}

// ✅ Count renders for debugging:
const renderCount = useRef(0);
useEffect(() => {
  renderCount.current++;
}); // runs after render, not during
```

### Bug 2: Assuming useEffect Runs Before Next Interaction

```jsx
// ❌ Wrong assumption about timing
function SearchBox() {
  const [query, setQuery] = useState('');
  const inputRef = useRef(null);

  // ❌ useEffect fires AFTER paint
  // If user types very fast, they might interact
  // before this focus runs
  useEffect(() => {
    inputRef.current.focus();
  }, []);

  // ✅ If focus must happen before paint use useLayoutEffect
  useLayoutEffect(() => {
    inputRef.current.focus();
    // Fires synchronously after DOM commit, before paint
    // Focus visible on very first frame
  }, []);
}
```

### Bug 3: Reading Layout During useEffect

```jsx
// ❌ Reading layout in useEffect causes double paint
function Tooltip({ targetRef, children }) {
  const [position, setPosition] = useState({ top: 0, left: 0 });

  useEffect(() => {
    // useEffect fires AFTER paint
    // Reading layout here → setState → triggers second render
    // User sees: wrong position flash → correct position
    // This is the "layout flash" / "flicker" problem
    const rect = targetRef.current.getBoundingClientRect();
    setPosition({ top: rect.bottom, left: rect.left });
  }, []);

  // ✅ Use useLayoutEffect for layout reads that affect render
  useLayoutEffect(() => {
    const rect = targetRef.current.getBoundingClientRect();
    setPosition({ top: rect.bottom, left: rect.left });
    // Fires before paint → setState → sync re-render → no flicker
  }, []);
}
```

### Bug 4: Forgetting Cleanup Causes Memory Leak

```jsx
// ❌ No cleanup — leak on unmount
function LiveFeed({ channelId }) {
  const [messages, setMessages] = useState([]);

  useEffect(() => {
    const socket = new WebSocket(`wss://api.example.com/${channelId}`);
    socket.onmessage = (e) => setMessages(m => [...m, e.data]);
    // Component unmounts → socket stays open → setMessages
    // called on unmounted component → memory leak
    // React 18: warning suppressed but memory still leaks
  }, [channelId]);
}

// ✅ Always return cleanup
useEffect(() => {
  const socket = new WebSocket(`wss://api.example.com/${channelId}`);
  socket.onmessage = (e) => setMessages(m => [...m, e.data]);

  return () => {
    socket.close(); // cleanup on unmount or channelId change
  };
}, [channelId]);
```

## 🎤 Interview Section

### Common Questions

**Q: What are the phases of a React render cycle?**
> *"Three phases: Render, Commit, and then passive effects. The render phase calls component functions and builds the work-in-progress fiber tree — it's pure computation, no DOM changes, and is interruptible in concurrent mode. The commit phase has three sub-phases: BeforeMutation (snapshots, schedules effects), Mutation (actual DOM changes), and Layout (refs + useLayoutEffect). After commit the browser paints. Then useEffect fires asynchronously as passive effects."*

---

**Q: What's the difference between `useEffect` and `useLayoutEffect`?**
> *"`useLayoutEffect` fires synchronously after DOM mutation but before browser paint — it blocks paint. Use it when you need to read DOM layout or make DOM changes that must be visible on the first frame (tooltips, scroll positions, measurements). `useEffect` fires asynchronously after paint — the browser has already shown the user the current render. Use it for everything else: subscriptions, timers, data fetching. `useLayoutEffect` in wrong context is a performance hazard."*

---

**Q: Why should component functions be pure?**
> *"Because React's concurrent mode can call a component function multiple times before committing the result — interrupted renders restart from the beginning. If the render function has side effects (API calls, mutations), those run multiple times. Side effects belong in `useEffect` which only runs once after commit, never during the interruptible render phase."*

---

### Senior-Level Questions

**Q: Why does React build the entire DOM tree in memory before inserting it?**
> *"During `completeWork`, React assembles child DOM nodes into parent nodes — building the full tree in JS memory. Then during commit, a single `appendChild` inserts the root of this assembled tree into the real document. This is O(1) DOM insertion instead of O(n) individual insertions. Inserting DOM nodes triggers browser layout/reflow — batching them as one insertion minimizes reflow cost compared to inserting nodes one-by-one and triggering reflow each time."*

---

**Q: What is the timing of `root.current` pointer flip during commit and why does it matter?**
> *"The pointer flip happens between the Mutation and Layout sub-phases of commit. After DOM mutations are applied but before `useLayoutEffect` runs. This means when `useLayoutEffect` reads `React.__SECRET_INTERNALS` or state, `root.current` already points to the newly committed tree. This guarantees `useLayoutEffect` always sees consistent committed state. If the flip happened after Layout, there'd be a window where DOM is updated but React's tree pointer is stale."*

---

**Q: Why does StrictMode double-invoke component functions and effects?**
> *"To simulate concurrent mode's behavior of restarting interrupted renders. In concurrent mode, a component function may run multiple times before React commits the result. StrictMode surfaces this by intentionally calling functions twice in development. If your render function is pure (no side effects), double invocation produces the same result and you notice nothing. If it's impure, you see doubled side effects — a signal to fix them before concurrent mode exposes them in production."*

---

### ⚠️ Interview Traps

**Trap 1:** *"Does React insert DOM nodes one by one during the first render?"*

Wrong: *"Yes, it appends each element as it creates it."*  
Correct:
> *"No. React assembles the entire DOM tree in JavaScript memory during `completeWork` — each parent appends its children. The resulting tree is not attached to the document yet. Then in the commit Mutation phase, React inserts the top-level node with a single `appendChild`. This minimizes browser reflow — one DOM insertion instead of N insertions each triggering layout recalculation."*

---

**Trap 2:** *"Can you read DOM measurements in `useEffect`?"*

Wrong: *"Yes, the DOM is available in useEffect."*  
Correct:
> *"Technically yes, but you shouldn't for layout-dependent state. `useEffect` fires after paint — if you read a measurement and set state, it triggers a second render and a second paint. The user sees a flicker: wrong layout → correct layout. `useLayoutEffect` fires before paint — the same read + setState triggers a synchronous re-render before the browser paints, so the user only sees the final correct layout. Use `useLayoutEffect` for measurement-driven renders."*

---

**Trap 3:** *"What happens to `useEffect` if a component unmounts immediately after mounting?"*

> *"On first render, React schedules `useEffect` asynchronously after paint. If the component unmounts before that scheduled callback fires, React still runs the effect's mount phase and then immediately runs its cleanup. This is why cleanup is critical — if you start a WebSocket in `useEffect` and the component unmounts before the callback fires, the cleanup must close the socket. React guarantees mount effect always pairs with cleanup on unmount, even for rapid mount/unmount."*
