# 🎭 Polymorphism in Java — Complete Guide

> **Polymorphism** means **one name, many forms** — same method behaves differently based on context.

---

## 📌 Core Idea

```
Poly  = Many
Morph = Forms

Example 1: We' can use same abs() method for int type, long type, float type etc.
1. abs(int)
2. abs(long)
3. abs(float)

Example 2: 
We can use the parent reference to hold any child objects. We can use the same List reference to hold ArrayList object, LinkedList object, Vector object, or Stack object.
Example: 
1. List l=new ArrayList();
2. List l=new LinkedList();
3. List l=new Vector();
4. List l=new Stack();

Same method name → different behavior
depending on WHO calls it or WHAT arguments passed

Real World:
Person acts differently in different roles:
Same "Rahul" → Son at home
              → Employee at office
              → Friend with friends
Same entity, different behavior = Polymorphism!
```

## 🗂️ Types of Polymorphism

```
Polymorphism in Java
│
├── Compile-Time Polymorphism (Static)
│   └── Method Overloading
│       ├── Same class, same name, different params
│       └── Resolved at compile time
│   └── Method Hiding
│       ├── Subclass defines static method with same signature
│       └── Resolved at compile time
│
├── Runtime Polymorphism (Dynamic)
│   └── Method Overriding
│       ├── Subclass redefines parent method
│       └── Resolved at runtime via vtable
│
├── Other Forms
│   ├── Interface polymorphism
│   ├── Coercion (type casting)
│   └── Parametric (Generics)
│
└── Key Mechanisms
    ├── Dynamic dispatch (invokevirtual)
    ├── Reference type vs object type
    └── Virtual method table (vtable)
```

## 1️⃣ Compile-Time Polymorphism — Method Overloading

> **Same method name, different parameters** — compiler decides which to call.

```java
class Calculator {
    // Same name — different parameter types/count
    int add(int a, int b) {
        return a + b;
    }
    double add(double a, double b) {
        return a + b;
    }
    int add(int a, int b, int c) {
        return a + b + c;
    }
    String add(String a, String b) {
        return a + b;
    }
}

Calculator c = new Calculator();
c.add(1, 2);          // int version    ← compiler picks at compile time
c.add(1.5, 2.5);      // double version
c.add(1, 2, 3);       // 3-arg version
c.add("Hi", " Java"); // String version
```

```
Overloading is resolved at COMPILE TIME
based on:
├── Number of parameters
├── Type of parameters
└── Order of parameters

NOT based on:
├── Return type alone ❌
└── Access modifier   ❌
```

```
When multiple overloads match:
  1. Exact match                    (no conversion)
  2. Widening primitive conversion  (int → long → float → double)
  3. Autoboxing                     (int → Integer)
  4. Child Class to Parent Class    (upcasting)
  5. Varargs                        (lowest priority)
```

### Overloading — What Counts & What Doesn't

```java
// ✅ Valid overloads
// Same name — different parameter types
// Different parameter ORDER counts
void show(int a) { }
void show(double a) { }       // different type
void show(int a, int b) { }   // different count
void show(String a, int b) { }
void show(int a, String b) { } // different order

// ❌ NOT valid overloads — compile error!
int  show(int a) { return 1; }
void show(int a) { }           // return type alone ❌ COMPILE ERROR!
```

### ⚠️ Overloading with Type Promotion
```java
class Demo {
    void show(int a)    { System.out.println("int");    }
    void show(long a)   { System.out.println("long");   }
    void show(double a) { System.out.println("double"); }
}

Demo d = new Demo();
d.show(10);    // int    ← exact match first!
d.show(10L);   // long
d.show(10.0);  // double
d.show('A');   // int    ← char promoted to int! (65)

// What if only long exists?
class Demo2 {
    void show(long a) { System.out.println("long"); }
}
new Demo2().show(10); // long ← int promoted to long ✅
```

```
Auto-promotion order (widening):
byte → short → int → long → float → double
char → int → long → float → double

If exact match not found → widens automatically!
```

## 2️⃣ Runtime Polymorphism — Method Overriding

> **Same method, different implementation** — JVM decides which to call at runtime.

```java
class Animal {
    void sound() {
        System.out.println("Some sound");
    }
}

class Dog extends Animal {
    @Override
    void sound() { System.out.println("Woof!"); }
}

class Cat extends Animal {
    @Override
    void sound() { System.out.println("Meow!"); }
}

class Duck extends Animal {
    @Override
    void sound() { System.out.println("Quack!"); }
}

// 🔥 Runtime Polymorphism in action!
Animal[] animals = {new Dog(), new Cat(), new Duck()};

for (Animal a : animals) {
    a.sound(); // SAME call — DIFFERENT result each time!
}
// Woof!
// Meow!
// Quack!
// JVM decides at runtime based on actual object type ✅
```

```
Key rule:
  Reference type → determines what methods are ACCESSIBLE (compile time)
  Object type    → determines which method RUNS (runtime)

Shape s = new Circle(5);
s.area();   // Shape says area() exists → compile ✅
            // Circle.area() runs       → runtime dispatch
```

```
1. In overriding method names and arguments must be same. That is method signature must be same.
2. Until 1.4 version the return types must be same but from 1.5 version onwards covariant return types are allowed.

class Parent {
    public Object methodOne() {
        return null;
    }
}
class Child extends Parent {
    public String methodOne() {
        return null;
    }
}
C:> javac -source 1.4 Parent.java //error
It is valid in "1.5" but invalid in "1.4". 

Parent
  methodOne() : Object      String      double      Number

Child
  methodOne() : String      Object      int         Integer
                // ✅       // ❌      // ❌       // ✅
```

## 🔬 In-Depth — How Runtime Polymorphism Works

```java
Animal a = new Dog();
a.sound(); // How does JVM know to call Dog's sound()?
```

```
Step 1: Object created on Heap
┌─────────────────────────────────────┐
│           Dog Object                │
│  vtable pointer ────────────────────┼──▶ Dog's vtable
│  [Animal part]                      │    ┌──────────────────────┐
│  [Dog part]                         │    │ sound() → Dog.sound  │
└─────────────────────────────────────┘    │ eat()   → Animal.eat │
                                           └──────────────────────┘

Step 2: a.sound() called
├── JVM looks at ACTUAL object (Dog) not reference type (Animal)
├── Finds Dog's vtable
├── Looks up sound() → Dog.sound()
└── Executes Dog.sound() → "Woof!" ✅

This lookup happens at RUNTIME → Runtime Polymorphism!
```

```
Compile time thinks:  Animal reference → calls Animal.sound()
Runtime actually:     Dog object      → calls Dog.sound()
JVM always goes by ACTUAL object, not reference type!
```

## 🔄 Dynamic Dispatch — The Engine of Runtime Polymorphism

```java
class Shape {
    double area() { return 0; }
}

class Circle extends Shape {
    double radius;
    Circle(double r) { this.radius = r; }

    @Override
    double area() { return Math.PI * radius * radius; }
}

class Rectangle extends Shape {
    double w, h;
    Rectangle(double w, double h) { this.w = w; this.h = h; }

    @Override
    double area() { return w * h; }
}

class Triangle extends Shape {
    double base, height;
    Triangle(double b, double h) { this.base = b; this.height = h; }

    @Override
    double area() { return 0.5 * base * height; }
}

// Dynamic Dispatch — same reference, different dispatch!
Shape s;

s = new Circle(5);
System.out.println(s.area()); // 78.53 ← Circle's area()

s = new Rectangle(4, 6);
System.out.println(s.area()); // 24.0 ← Rectangle's area()

s = new Triangle(3, 8);
System.out.println(s.area()); // 12.0 ← Triangle's area()

// s.area() is the SAME call every time
// but dispatched to DIFFERENT methods at runtime!
```

## ⚠️ What CANNOT Be Overridden

```java
class Parent {
    // 1. final method
    final void show() { }           // ❌ cannot override

    // 2. static method — HIDDEN not overridden
    static void display() { }       // ❌ hiding, not overriding

    // 3. private method — not visible
    private void secret() { }       // ❌ cannot override

    // 4. constructor — not inherited

1. Based on own requirement we can declare the same Parent class private/final/static method in child class also. It is valid but not overriding
2. Parent class non final methods we can override as final in child class. We can override native methods in the child classes.
3. We should override Parent class abstract methods in Child classes to provide implementation.
abstract
    |
    |   <---overriding is possible
    |
non-abstract

4. We can override a non-abstract method as abstract this approach is helpful to stop availability of Parent method implementation to the next level child classes.

class Parent {
    public void methodOne() { }
}
abstract class Child extends Parent {
    public abstract void methodOne();
}

5. We can override :-
final  ───────────────► non-final               // ❌ cannot override final method
non-final ────────────► final                   // ✅ can override non-final as final

native ───────────────► non-native              // ✅ can override native method as non-native
non-native ───────────► native                  // ✅ can override non-native as native

abstract ─────────────► non-abstract            // ✅ can override abstract as non-abstract (provide implementation)
non-abstract ─────────► abstract                // ✅ can override non-abstract as abstract (force subclasses to implement)

synchronized ─────────► non-synchronized        // ✅ can override synchronized as non-synchronized
non-synchronized ─────► synchronized            // ✅ can override non-synchronized as synchronized

strictfp ─────────────► non-strictfp              // ✅ can override strictfp as non-strictfp
non-strictfp ─────────► strictfp                  // ✅ can override non-strictfp as strictfp
}

6. While overriding we can't reduce the scope of access modifier
private < default < protected < public

Example:
class A {
    public void m1() {}
}
class B extends A {}
A a = new B();
a.m1(); // Parent method will execute

Example:
class A {
    public void m1() {}
}
class B extends A {
    @Override
    public void m1() {}
}
A a = new B();
a.m1(); // Child method will execute

Example:
class A {
    public void m1() {}
}
class B extends A {
    @Override
    void m1() {} // CE — cannot reduce access from public to default
}
A a = new B();
a.m1();


6. Rule: While overriding if the child class method throws any checked exception compulsory the parent class method should throw the same checked exception or its parent otherwise we will get compile time error. But there are no restrictions for un-checked exceptions.

Example:
class Parent {
    public void methodOne() {}
}
class Child extends Parent{
    public void methodOne()throws Exception {}
} 

Output:
Compile time error : methodOne() in Child cannot override methodOne() in Parent; overridden method does not throw java.lang.Exception

Rules of Exceptions in Method Overriding
│
├── Child class can throw:
│      ✅ same exception
│      ✅ subclass exception (narrower)
│      ✅ no exception
│      ✅ any unchecked exception
│
├── Child class cannot throw:
│      ❌ broader checked exception
│      ❌ new checked exception
│
└── Rule applies only to:
       Checked Exceptions

1)
Parent : methodOne() throws Exception
Child  : methodOne()
✅ VALID

Reason:
Child removed exception.


--------------------------------------------------

2)
Parent : methodOne()
Child  : methodOne() throws Exception
❌ INVALID

Reason:
Child added new checked exception.


--------------------------------------------------

3)
Parent : methodOne() throws Exception
Child  : methodOne() throws Exception
✅ VALID

Reason:
Same checked exception.


--------------------------------------------------

4)
Parent : methodOne() throws IOException
Child  : methodOne() throws Exception
❌ INVALID

Reason:
Exception is broader than IOException.


--------------------------------------------------

5)
Parent : methodOne() throws IOException
Child  : methodOne() throws EOFException,
                               FileNotFoundException
✅ VALID

Reason:
Both are subclasses of IOException.


--------------------------------------------------

6)
Parent : methodOne() throws IOException
Child  : methodOne() throws EOFException,
                               InterruptedException
❌ INVALID

Reason:
InterruptedException is unrelated to IOException.


--------------------------------------------------

7)
Parent : methodOne() throws IOException
Child  : methodOne() throws EOFException,
                               ArithmeticException
✅ VALID

Reason:
ArithmeticException is unchecked.


--------------------------------------------------

8)
Parent : methodOne()
Child  : methodOne() throws ArithmeticException,
                               NullPointerException,
                               ClassCastException,
                               RuntimeException
✅ VALID

Reason:
Unchecked exceptions are always allowed.

```

## 🔄 Object Type vs Reference Type

```java
// Reference type = Animal (left side)
// Object type    = Dog    (right side)
Animal a = new Dog();

// Compile-time: compiler only sees Animal reference
// Runtime:      JVM sees actual Dog object

a.sound();      // ✅ sound() in Animal → overridden → Dog.sound()!
a.bark();       // ❌ COMPILE ERROR! bark() not in Animal reference
                // compiler only checks Animal — doesn't see Dog methods!

// To access Dog methods — cast!
Dog d = (Dog) a;
d.bark();       // ✅ now can call bark()

// ⚠️ Wrong cast → ClassCastException at runtime!
Animal a2 = new Cat();
Dog d2 = (Dog) a2; // compiles ✅ but 💥 ClassCastException at runtime!

// Safe cast — always check first!
if (a instanceof Dog dog) {
    dog.bark(); // ✅ safe (Java 16+ pattern matching)
}
```

## 🔄 Polymorphism with Constructors ⚠️

```java
class Parent {
    Parent() {
        show();         // ⚠️ calling overridable method in constructor!
    }
    void show() {
        System.out.println("Parent show");
    }
}

class Child extends Parent {
    int x = 10;

    @Override
    void show() {
        System.out.println("Child show: " + x);
    }
}

new Child();
// Output: "Child show: 0" 😱

// Why 0? Not 10?
// 1. Child() called
// 2. super() runs first → Parent constructor
// 3. show() called → polymorphism → Child.show()!
// 4. BUT x not yet initialized! (Child fields init AFTER super())
// 5. x = 0 (default) ← dangerous!
// Rule: NEVER call overridable methods in constructors! ⚠️
```

## 🔬 Interface Polymorphism

```java
// One interface — many implementations
public interface Sorter {
    void sort(int[] arr);
    default String name() { return getClass().getSimpleName(); }
}

public class QuickSorter implements Sorter {
    @Override
    public void sort(int[] arr) { quickSort(arr, 0, arr.length - 1); }
}

public class MergeSorter implements Sorter {
    @Override
    public void sort(int[] arr) { mergeSort(arr, 0, arr.length - 1); }
}

public class TimSorter implements Sorter {
    @Override
    public void sort(int[] arr) { Arrays.sort(arr); }  // JDK TimSort
}

// Polymorphic — caller uses Sorter, not concrete class
public class SortBenchmark {

    public void benchmark(Sorter sorter, int[] data) {
        long start = System.nanoTime();
        sorter.sort(data);                          // which sort runs? runtime decides
        long elapsed = System.nanoTime() - start;
        System.out.printf("%s: %dms%n", sorter.name(), elapsed / 1_000_000);
    }

    public static void main(String[] args) {
        SortBenchmark bench = new SortBenchmark();
        int[] data = generateData(100_000);

        bench.benchmark(new QuickSorter(), data.clone());
        bench.benchmark(new MergeSorter(), data.clone());
        bench.benchmark(new TimSorter(),   data.clone());
        // Swap implementations — SortBenchmark unchanged
    }
}
```

## 🔬 Polymorphism with Generics (Parametric)

```java
// Generic class — works with any type
public class Repository<T> {

    private final List<T> store = new ArrayList<>();

    public void save(T entity) {
        store.add(entity);
    }

    public Optional<T> findFirst(Predicate<T> filter) {
        return store.stream().filter(filter).findFirst();
    }

    public List<T> findAll(Predicate<T> filter) {
        return store.stream().filter(filter).collect(Collectors.toList());
    }
}

// Same class — different type behavior
Repository<User>    users    = new Repository<>();
Repository<Order>   orders   = new Repository<>();
Repository<Product> products = new Repository<>();

users.save(new User("Alice"));
orders.save(new Order("O-001"));

// Type-safe — compiler enforces
users.save(new Order("O-001"));     // ❌ COMPILE ERROR — wrong type
```

## 🔬 Polymorphism Anti-Patterns

### Using instanceof chains — defeats polymorphism

```java
// ❌ instanceof chain — not polymorphic
double computeArea(Shape shape) {
    if (shape instanceof Circle c) {
        return Math.PI * c.getRadius() * c.getRadius();
    } else if (shape instanceof Rectangle r) {
        return r.getWidth() * r.getHeight();
    } else if (shape instanceof Triangle t) {
        return 0.5 * t.getBase() * t.getHeight();
    }
    throw new IllegalArgumentException("Unknown shape");
}
// Adding new Shape → must modify this method → Open/Closed violated

// ✅ Polymorphic — each shape knows its area
double computeArea(Shape shape) {
    return shape.area();    // polymorphic dispatch handles all cases
}
// Adding Triangle → implement area() in Triangle → no other change
```

### Type-switching in multiple places

```java
// ❌ Same instanceof logic duplicated across codebase
// Processing:
if (notification instanceof EmailNotification e) sendEmail(e);
else if (notification instanceof SmsNotification s) sendSms(s);

// Logging:
if (notification instanceof EmailNotification e) logEmail(e);
else if (notification instanceof SmsNotification s) logSms(s);

// ✅ Polymorphism — behavior in the type
interface Notification {
    void send();
    void log();
}
class EmailNotification implements Notification {
    public void send() { sendEmail(); }
    public void log()  { logEmail(); }
}
```

## Method Hiding

All rules of method hiding are exactly same as overriding except the following
differences.

```
+----------------------+---------------------------------------------+--------------------------------------------------+
| Feature              | Method Overriding                           | Method Hiding                                   |
+----------------------+---------------------------------------------+--------------------------------------------------+
| Method Type          | Both methods should be non-static           | Both methods should be static                    |
+----------------------+---------------------------------------------+--------------------------------------------------+
| Resolution Done By   | JVM                                         | Compiler                                         |
+----------------------+---------------------------------------------+--------------------------------------------------+
| Based On             | Runtime object                              | Reference type                                   |
+----------------------+---------------------------------------------+--------------------------------------------------+
| Polymorphism Type    | Runtime polymorphism                        | Compile-time polymorphism                        |
|                      | Dynamic polymorphism                        | Static polymorphism                              |
|                      | Late binding                                | Early binding                                    |
+----------------------+---------------------------------------------+--------------------------------------------------+
| Method Call          | Object decides method                       | Reference decides method                         |
+----------------------+---------------------------------------------+--------------------------------------------------+
| Keyword Context      | Inheritance with instance methods           | Inheritance with static methods                  |
+----------------------+---------------------------------------------+--------------------------------------------------+
| Example              | Parent p = new Child();                     | Parent p = new Child();                          |
|                      | p.show(); → Child version                   | p.show(); → Parent version                       |
+----------------------+---------------------------------------------+--------------------------------------------------+
```

## 🎯 Interview Cheat Sheet

```
Q: What is Polymorphism?
A: One name, many forms. Same method behaves
   differently based on object type or parameters.

Q: How many types of polymorphism in Java?
A: Two:
   1. Compile-time (Static)  → Method Overloading
   2. Runtime (Dynamic)      → Method Overriding

Q: Can we overload main() method?
A: YES ✅ — but JVM calls only String[] args version.
   public static void main(int[] args) {} ← valid but JVM ignores

Q: Can we override main() method?
A: NO ❌ — main() is static → can be hidden, not overridden.

Q: What is the role of @Override annotation?
A: Optional but HIGHLY recommended.
   Tells compiler "this is an override."
   If method signature wrong → compile error catches it!
   Without @Override → silent bug (new method, not override).

Q: Can we overload by changing return type only?
A: NO ❌ — compile error. Parameters must differ.

Q: Difference between method hiding and overriding?
A: Overriding → instance methods, runtime decision
   Hiding     → static methods, compile-time decision

Q: Can constructors be overloaded?
A: YES ✅ — very common! Constructor overloading.
   Same class name, different parameters.

Q: Can constructors be overridden?
A: NO ❌ — constructors NOT inherited → cannot override.

Q: Automatic type promotion in overloading?
A: YES — if exact match not found, Java promotes:
   byte→short→int→long→float→double
   char→int

Q: Which polymorphism gives better performance?
A: Compile-time → slightly faster (resolved at compile time).
   Runtime → slight overhead (vtable lookup at runtime).
   In practice — difference negligible.

Q: Can private methods be overloaded?
A: YES ✅ — overloading within same class.
   But private methods CANNOT be overridden.
```
**🪤 Trap 1 — Overloading resolved at compile time — reference type decides**

```java
class Printer {
    void print(Object o)  { System.out.println("Object"); }
    void print(String s)  { System.out.println("String"); }
}

Printer p = new Printer();
Object obj = "hello";           // reference type = Object, object type = String

p.print(obj);                   // "Object" — NOT "String"
// Overloading uses REFERENCE TYPE (compile-time)
// obj declared as Object → print(Object) selected at compile time
// String-specific overload NOT considered

p.print("hello");               // "String" — reference type = String
p.print((String) obj);          // "String" — explicit cast changes reference type
```

> 🔑 Overloading is **always** resolved at compile time using the **reference type** — not the actual object type. This is the exact opposite of overriding.

## 🧩 DSA Angle

```java
// 1. Polymorphism in Graph algorithms
abstract class GraphAlgorithm {
    abstract void execute(int[][] graph, int start);

    // Template — same structure, different execution
    void run(int[][] graph, int start) {
        System.out.println("Starting from: " + start);
        execute(graph, start);  // polymorphic call!
        System.out.println("Done!");
    }
}

class BFS extends GraphAlgorithm {
    @Override
    void execute(int[][] graph, int start) {
        Queue<Integer> queue = new LinkedList<>();
        boolean[] visited = new boolean[graph.length];
        queue.add(start);
        visited[start] = true;
        while (!queue.isEmpty()) {
            int node = queue.poll();
            System.out.print(node + " ");
            for (int i = 0; i < graph[node].length; i++)
                if (graph[node][i] == 1 && !visited[i]) {
                    visited[i] = true;
                    queue.add(i);
                }
        }
    }
}

class DFS extends GraphAlgorithm {
    @Override
    void execute(int[][] graph, int start) {
        boolean[] visited = new boolean[graph.length];
        dfs(graph, start, visited);
    }
    private void dfs(int[][] graph, int node, boolean[] visited) {
        visited[node] = true;
        System.out.print(node + " ");
        for (int i = 0; i < graph[node].length; i++)
            if (graph[node][i] == 1 && !visited[i])
                dfs(graph, i, visited);
    }
}

// Swap algorithm without changing client code!
GraphAlgorithm algo = new BFS();
algo.run(graph, 0); // BFS

algo = new DFS();
algo.run(graph, 0); // DFS — same call! ✅

// 2. Comparator overloading — sort by different criteria
Comparator<int[]> byStart  = (a, b) -> a[0] - b[0];
Comparator<int[]> byEnd    = (a, b) -> a[1] - b[1];
Comparator<int[]> byLength = (a, b) -> (a[1]-a[0]) - (b[1]-b[0]);

Arrays.sort(intervals, byStart);  // sort by start
Arrays.sort(intervals, byEnd);    // sort by end
Arrays.sort(intervals, byLength); // sort by length
// Same sort() call — different behavior via polymorphism! ✅

// 3. Method overloading — clean DSA utility
class ArrayUtils {
    static int sum(int[] arr) {
        int s = 0; for (int x : arr) s += x; return s;
    }
    static long sum(long[] arr) {
        long s = 0; for (long x : arr) s += x; return s;
    }
    static double sum(double[] arr) {
        double s = 0; for (double x : arr) s += x; return s;
    }
}
// Same name — different type handled! ✅
```

**Underlying primitive: vtable + invokevirtual bytecode**

```
Runtime polymorphism — JVM vtable:

class Animal:
  vtable slot 0: Animal.eat()
  vtable slot 1: Animal.sleep()
  vtable slot 2: Animal.toString()

class Dog extends Animal:
  vtable slot 0: Dog.eat()       ← overridden — Dog's version
  vtable slot 1: Animal.sleep()  ← inherited — Animal's version
  vtable slot 2: Dog.toString()  ← overridden — Dog's version
  vtable slot 3: Dog.bark()      ← new — Dog only

invokevirtual animal.eat():
  1. Get object from stack
  2. Read klass pointer from object header
  3. Look up slot 0 in klass vtable
  4. Call method at that slot
  Cost: 1 pointer dereference + 1 indexed lookup = O(1)

JIT optimization:
  Monomorphic: one type always at call site
    → direct call (devirtualize) — no vtable lookup
  Bimorphic: two types
    → inline cache check + direct call
  Megamorphic: many types
    → vtable dispatch (generic slow path)

Compile-time overloading:
  Resolved entirely by javac
  Different method descriptors in bytecode:
    add(II)I      → add(int, int):int
    add(DD)D      → add(double, double):double
    add(Ljava/lang/String;Ljava/lang/String;)Ljava/lang/String;
  No runtime cost — direct invocation
```

```java
// Polymorphic payment processing
public interface PaymentStrategy {
    PaymentResult pay(BigDecimal amount, PaymentContext context)
        throws PaymentException;
    boolean supports(PaymentMethod method);
    String  strategyName();
}

public class CardPaymentStrategy implements PaymentStrategy {

    private final StripeClient stripe;

    public CardPaymentStrategy(StripeClient stripe) {
        this.stripe = stripe;
    }

    @Override
    public PaymentResult pay(BigDecimal amount, PaymentContext ctx)
            throws PaymentException {
        try {
            String chargeId = stripe.charge(
                ctx.getCardToken(), amount, ctx.getCurrency()
            );
            return PaymentResult.success(chargeId, PaymentMethod.CARD);
        } catch (StripeException e) {
            throw new PaymentException("Card payment failed", e);
        }
    }

    @Override
    public boolean supports(PaymentMethod method) {
        return method == PaymentMethod.CARD
            || method == PaymentMethod.DEBIT;
    }

    @Override
    public String strategyName() { return "card-via-stripe"; }
}

public class WalletPaymentStrategy implements PaymentStrategy {

    private final WalletService wallet;

    public WalletPaymentStrategy(WalletService wallet) {
        this.wallet = wallet;
    }

    @Override
    public PaymentResult pay(BigDecimal amount, PaymentContext ctx)
            throws PaymentException {
        if (wallet.getBalance(ctx.getUserId()).compareTo(amount) < 0)
            throw new PaymentException("Insufficient wallet balance");
        wallet.deduct(ctx.getUserId(), amount);
        return PaymentResult.success(
            UUID.randomUUID().toString(), PaymentMethod.WALLET
        );
    }

    @Override
    public boolean supports(PaymentMethod method) {
        return method == PaymentMethod.WALLET;
    }

    @Override
    public String strategyName() { return "wallet"; }
}

// Router — pure polymorphism — never mentions concrete strategy
public class PaymentRouter {

    private final List<PaymentStrategy> strategies;

    public PaymentRouter(List<PaymentStrategy> strategies) {
        this.strategies = strategies;
    }

    public PaymentResult route(BigDecimal amount,
                               PaymentMethod method,
                               PaymentContext context) throws PaymentException {

        PaymentStrategy strategy = strategies.stream()
            .filter(s -> s.supports(method))
            .findFirst()
            .orElseThrow(() -> new PaymentException(
                "No strategy for payment method: " + method
            ));

        log.info("Routing {} {} via {}",
            amount, method, strategy.strategyName());

        return strategy.pay(amount, context);   // polymorphic dispatch
    }
}

// Wiring — only place that knows concrete implementations
PaymentRouter router = new PaymentRouter(List.of(
    new CardPaymentStrategy(stripeClient),
    new WalletPaymentStrategy(walletService),
    new CryptoPaymentStrategy(cryptoClient)   // new strategy — router unchanged
));
```

🔴 **What breaks if done wrong:** `PaymentRouter` uses `if (method == CARD) { stripe.charge() }` → adding crypto payment = modify router → every new payment method = modify router → Open/Closed violated → regression risk in prod on every payment method addition.
