## 🧬 Inheritance in Java — Complete Guide

> **Inheritance** is the OOP mechanism where a **subclass (child)** acquires the properties (fields) and behaviors (methods) of a **superclass (parent)**. It enables code reuse and establishes an **IS-A relationship**.


```
Java Inheritance
│
├── Types
│   ├── Single          → class extends one class
│   ├── Multilevel      → A extends B extends C
│   ├── Hierarchical    → multiple classes extend one class
│   └── Multiple        → ❌ not via classes (via interfaces only)
│
├── Keywords
│   ├── extends         → class inherits class
│   └── implements      → class inherits interface
│
├── What Is Inherited
│   ├── public fields + methods
│   ├── protected fields + methods
│   ├── default (package-private) — same package only
│   └── NOT: private, constructors, static members (hidden not inherited)
│
├── Key Mechanisms
│   ├── Method Overriding
│   ├── super keyword
│   ├── Constructor chaining
│   └── instanceof check
│
└── Special Rules
    ├── Every class extends Object implicitly
    ├── final class cannot be extended
    ├── abstract class forces subclassing
    └── Constructor NOT inherited — but super() called
```

```java
Without Inheritance
class Loan {
//common methods which are required for any type of loan.
// 300 methods
class HousingLoan {
//Housing loan specific methods.
// 500 methods
}
class EducationLoan {
//Education Loan specific methods.
// 400 methods
}
// Development Time: +90Hr

With Inheritance
class Loan {
//common methods which are required for any type of loan.
// 300 methods

//Housing loan specific methods.
// +200 methods
}
class EducationLoan extends Loan {
//Education Loan specific methods.
// +100 methods
}
// Development Time: +20Hr

The common methods which are required for housing loan, vehicle loan, personal loan
and education loan we can define into a separate class in parent class loan. So that
automatically these methods are available to every child loan class.

1. For all java classes the most commonly required functionality is define inside
object class hence object class acts as a root for all java classes.
2. For all java exceptions and errors the most common required functionality
defines inside Throwable class hence Throwable class acts as a root for exception
hierarchy.

Java’s class hierarchy is massive. At the top, we have the `Object` class — the root of all classes.
                           Object
                         /    |    \
                        /     |     \
                       /      |      \
                  String    Number   Throwable
                              |          /   \
                              |         /     \
                              |    Exception   Error
                              |
         -------------------------------------------------
         |        |         |        |        |         |
       Byte     Short    Integer    Long    Float    Double
```

```java
// Parent (superclass / base class)
public class Animal {
    protected String name;
    protected int    age;

    public Animal(String name, int age) {
        this.name = name;
        this.age  = age;
    }

    public void eat()    { System.out.println(name + " is eating"); }
    public void sleep()  { System.out.println(name + " is sleeping"); }
    public String toString() { return "Animal[" + name + ", " + age + "]"; }
}

// Child (subclass / derived class)
public class Dog extends Animal {

    private String breed;

    public Dog(String name, int age, String breed) {
        super(name, age);           // must call parent constructor first
        this.breed = breed;
    }

    // Additional method — only in Dog
    public void bark() { System.out.println(name + " says: Woof!"); }

    @Override
    public String toString() {
        return "Dog[" + name + ", " + age + ", " + breed + "]";
    }
}

// Usage
Dog dog = new Dog("Rex", 3, "Labrador");
dog.eat();          // ✅ inherited from Animal
dog.sleep();        // ✅ inherited from Animal
dog.bark();         // ✅ Dog-specific
dog.toString();     // ✅ overridden in Dog

class Parent {
    public void methodOne() {
        System.out.println("Parent - methodOne");
    }
}

class Child extends Parent {
    public void methodOne() {
        System.out.println("Child - methodOne");
    }

    public void methodTwo() {
        System.out.println("Child - methodTwo");
    }
}

class Test {
    public static void main(String[] args) {
        // Parent object
        Parent p = new Parent();
        p.methodOne();
        // p.methodTwo(); // ❌ Compile-time error

        // Child object
        Child c = new Child();
        c.methodOne();
        c.methodTwo();

        // Parent reference → Child object
        Parent p1 = new Child();
        p1.methodOne();
        // p1.methodTwo(); // ❌ Compile-time error

        // ❌ Compile-time error
        // incompatible types found : Parent required: Child
        // Child c1 = new Parent();
    }
}

Conclusion :
1. Whatever the parent has by default available to the child but whatever the child has by default not available to the parent. Hence on the child reference we can call both parent and child class methods. But on the parent reference we can call only methods available in the parent class and we can't call child specific methods.
2. Parent class reference can be used to hold child class object but by using that reference we can call only methods available in parent class and child specific methods we can't call.
3. Child class reference cannot be used to hold parent class object.
```

<Aside type="tip">
**Key Insight**: Inheritance is not just about code reuse — it's about **modeling real-world relationships** and enabling **polymorphism**.  
By establishing IS-A relationships, you:
- ✅ Reduce duplication — common logic lives in parent
- ✅ Enable polymorphism — treat subclasses uniformly via parent type
- ✅ Support extensibility — add new subclasses without modifying existing code
- ✅ Clarify domain model — IS-A relationships reflect real-world hierarchies
</Aside>

## 🗂️ The extends Keyword — Single Inheritance

> Java supports **single inheritance for classes** — a class can extend **only one** direct superclass.

### 🔑 Basic Syntax & Rules

<Code lang="java" title="Single inheritance — one parent only" code={`
// ✅ Valid: One parent class
class Dog extends Animal { }

// ❌ Invalid: Multiple parent classes (not allowed in Java)
// class Dog extends Animal, Mammal { }  // ❌ C.E: '{' expected

// ✅ Valid: Multiple interfaces (different from class inheritance)
class Dog extends Animal implements Pet, Trainable { }`} />

### 🧭 Inheritance Hierarchy Visualization

```java
public class Parent {
    public    int publicField    = 1;   // ✅ inherited
    protected int protectedField = 2;   // ✅ inherited
              int defaultField   = 3;   // ✅ inherited (same package)
    private   int privateField   = 4;   // ❌ NOT inherited — not visible

    public    void publicMethod()    { }  // ✅ inherited
    protected void protectedMethod() { }  // ✅ inherited
              void defaultMethod()   { }  // ✅ inherited (same package)
    private   void privateMethod()   { }  // ❌ NOT inherited

    static    void staticMethod()    { }  // ❌ NOT inherited — hidden
    static    int  staticField  = 5;      // ❌ NOT inherited — hidden

    Parent() { }                          // ❌ NOT inherited
    Parent(int x) { }                     // ❌ NOT inherited
}

class Child extends Parent {
    void test() {
        System.out.println(publicField);    // ✅
        System.out.println(protectedField); // ✅
        System.out.println(defaultField);   // ✅ if same package
        System.out.println(privateField);   // ❌ COMPILE ERROR

        publicMethod();                     // ✅
        protectedMethod();                  // ✅
        defaultMethod();                    // ✅ if same package
        privateMethod();                    // ❌ COMPILE ERROR

        Parent.staticMethod();              // ✅ accessed via class name
        staticMethod();                     // ✅ compiles — but it's Parent's
    }
}
```
```
Single Inheritance:
  Animal ← Dog

Multilevel Inheritance:
  Animal ← Dog ← GoldenRetriever

Hierarchical Inheritance:
  Animal ← Dog
  Animal ← Cat
  Animal ← Bird

Multiple Inheritance (via interfaces only):
  interface Flyable { }
  interface Swimmable { }
  class Duck implements Flyable, Swimmable { }

❌ Multiple class inheritance — NOT allowed:
  class A { }
  class B { }
  class C extends A, B { }   // COMPILE ERROR
```

```java
// Multilevel
class Animal   { void breathe() { } }
class Mammal   extends Animal  { void nurse() { } }
class Dog      extends Mammal  { void bark()  { } }

Dog d = new Dog();
d.breathe();    // ✅ from Animal (2 levels up)
d.nurse();      // ✅ from Mammal (1 level up)
d.bark();       // ✅ own method

// instanceof checks entire chain
System.out.println(d instanceof Dog);    // true
System.out.println(d instanceof Mammal); // true
System.out.println(d instanceof Animal); // true
System.out.println(d instanceof Object); // true — always
```


<Code lang="java" title="Multi-level inheritance — chain of IS-A relationships" code={`
// Root of all classes (implicit)
class Object { /* ... */ }

// Level 1: Direct subclass of Object
class Animal {
    String name;
    void breathe() { System.out.println("Breathing..."); }
}

// Level 2: Subclass of Animal
class Mammal extends Animal {
    boolean hasFur;
    void nurseYoung() { System.out.println("Nursing young..."); }
}
// Level 3: Subclass of Mammal
class Dog extends Mammal {
    void bark() { System.out.println("Woof!"); }
}

// Usage — Dog inherits from entire chain
Dog dog = new Dog();
dog.name = "Buddy";        // ✅ From Animal
dog.breathe();             // ✅ From Animal
dog.hasFur = true;         // ✅ From Mammal
dog.nurseYoung();          // ✅ From Mammal
dog.bark();                // ✅ From Dog
dog.toString();            // ✅ From Object (root of hierarchy)
`} />

<Aside type="note">
**Every class in Java implicitly extends `Object`** if no explicit `extends` is declared.  
This means **all classes** inherit methods like `toString()`, `equals()`, `hashCode()`, `getClass()`.
</Aside>

## 🔗 Constructor Chaining with super()

> When a subclass object is created, **constructors execute from top to bottom** — parent first, then child.

### 🔑 Constructor Execution Order

<Code lang="java" title="Constructor chaining — parent initializes first" code={`
class Animal {
    String name;
    
    Animal(String name) {
        this.name = name;
        System.out.println("Animal constructor: " + name);
    }
}

class Dog extends Animal {
    String breed;
    
    Dog(String name, String breed) {
        super(name);  // ✅ Must call parent constructor FIRST (explicit or implicit)
        this.breed = breed;
        System.out.println("Dog constructor: " + breed);
    }
}

// Object creation sequence:
Dog dog = new Dog("Buddy", "Golden Retriever");
/* Output:
Animal constructor: Buddy   ← Parent constructor runs first
Dog constructor: Golden Retriever  ← Child constructor runs after
*/`} />

```java
class A {
    A() {
        System.out.println("A constructor");
    }
}

class B extends A {
    B() {
        super();    // implicit if not written — calls A()
        System.out.println("B constructor");
    }
}

class C extends B {
    C() {
        super();    // calls B() → B calls A()
        System.out.println("C constructor");
    }
}

new C();
// Output:
// A constructor    ← top of hierarchy first
// B constructor
// C constructor    ← bottom last
```

```
Constructor chain order:
  new C() → C() → super() → B() → super() → A() → super() → Object()
  Execution order: Object → A → B → C (top-down)

  Object's no-arg constructor always called at the top
  Every constructor in chain completes before child continues
```

### ⚠️ super() Rules & Common Pitfalls

```
super keyword uses:
  ├── super()           → call parent constructor (must be line 1)
  ├── super.method()    → call parent version of overridden method
  └── super.field       → access parent field (shadowed by child field)

this() and super() cannot BOTH appear in same constructor.
```

<CardGrid>
  <Card title="Rule: super() Must Be First Statement in Constructor" icon="approve-check">
```java
    class Dog extends Animal {
        Dog(String name) {
            // ❌ Invalid: super() not first
            // System.out.println("Before super");
            // super(name);  // ❌ C.E: call to super must be first statement
            
            // ✅ Correct: super() first
            super(name); // ① super() — call parent constructor
            System.out.println("After super");
        }
    }
```
  </Card>
  
  <Card title="Rule: Implicit super() if No Explicit Call" icon="information">
```java
    class Animal {
        Animal() { System.out.println("Animal()"); }  // No-arg constructor
    }
    
    class Dog extends Animal {
        Dog() {
            // Implicit super() inserted by compiler:
            // super();  // ← Compiler adds this automatically
            System.out.println("Dog()");
        }
    }
    
    // Output: Animal() → Dog()
    
    // ❌ But if parent has ONLY parameterized constructor:
    class Animal {
        Animal(String name) { }  // No no-arg constructor
    }
    class Dog extends Animal {
        Dog() {
            // Implicit super() → super() → ❌ C.E: no matching constructor
            // Fix: Call explicit super with args:
            Dog(String name) { super(name); }        }
    }
```
  </Card>

  <Card title="Pitfall: Forgetting super() When Parent Has No No-Arg Constructor" icon="error">
```java
    class Parent {
        Parent(int x) { }  // Only parameterized constructor
    }
    
    class Child extends Parent {
        // ❌ Compile Error: Parent() is not defined
        // Child() { }  // Implicit super() → super() → no matching constructor
        
        // ✅ Fix: Explicit super() with matching args
        Child(int x) { super(x); }
    }
```
  </Card>
</CardGrid>

### 💻 Constructor Chaining Patterns

<Code lang="java" title="this() and super() — constructor delegation" code={`class Person {
    String name;
    int age;
    
    // Primary constructor
    Person(String name, int age) {
        this.name = name;
        this.age = age;
    }
    
    // Delegating constructor — uses this()
    Person(String name) {
        this(name, 0);  // Delegate to primary constructor
    }
}

class Employee extends Person {
    String employeeId;
    
    // Delegating constructor — uses super()
    Employee(String name, String employeeId) {
        super(name);  // Call parent constructor
        this.employeeId = employeeId;
    }
    
    // Another delegating constructor — uses this()    Employee(String employeeId) {
        this("Unknown", employeeId);  // Delegate to other constructor
    }
}

// Key rules:
// • this() → calls another constructor in SAME class
// • super() → calls constructor in PARENT class
// • Both must be FIRST statement in constructor
// • Cannot use both this() and super() in same constructor
`} />

<Aside type="tip">
**Best Practice**: Use **constructor chaining** to avoid code duplication:
- One "primary" constructor does all initialization
- Other constructors delegate to it via `this()` or `super()`
- Centralizes validation and setup logic
</Aside>

## 🔄 Method Overriding — Polymorphism in Action

> **Overriding** allows a subclass to provide a **specific implementation** of a method already defined in its superclass.

### 🔑 Overriding Rules & Syntax

<Code lang="java" title="Method overriding — same signature, different implementation" code={`
class Animal {
    // Method to be overridden
    public void makeSound() {
        System.out.println("Some generic animal sound");
    }
    
    // Final method — cannot be overridden
    public final void breathe() {
        System.out.println("Breathing...");
    }

    public String describe() { return "I am a Animal"; }
}

class Dog extends Animal {
    // ✅ Valid override — same signature, compatible return type
    @Override  // ✅ Recommended: compile-time check
    public void makeSound() {
        System.out.println("Woof! Woof!");
    }
    
    // ❌ Invalid: Cannot override final method
    // @Override
    // public void breathe() { }  // ❌ C.E: cannot override final method

    // ❌ Invalid: Cannot reduce visibility
    // @Override
    // void makeSound() { }  // ❌ C.E: attempting to assign weaker access privileges

    // Override — can call super version
    @Override
    public String describe() {
        return super.describe() + " — specifically a Dog";  // ✅ Can call parent method with super
    }
}

// Polymorphism in action:
Animal myPet = new Dog();  // Parent reference, child object
myPet.makeSound();  // "Woof! Woof!" ← Dynamic method dispatch ✅
myPet.breathe();    // "Breathing..." ← Final method, not overridden
myPet.describe();  // "I am a Animal — specifically a Dog" ← Overridden method with super call
`} />

### ⚠️ Overriding Rules Checklist

```
✅ MUST match:
  ├── Method name — exactly
  ├── Parameter list — exactly (same types, same order)
  └── Return type — same OR covariant (subtype)

✅ CAN change:
  ├── Access modifier — only WIDEN (protected → public)
  ├── Return type — to subtype (covariant return)
  ├── throws clause — only NARROW (fewer/subtype checked exceptions)
  └── Method body — completely

❌ CANNOT change:
  ├── Narrow access (public → protected → private)
  ├── Broaden throws (add new checked exceptions)
  └── Change static to instance or vice versa
```

  <Card title="Rule 1: Same Method Signature" icon="approve-check">
```java
    class Parent {
        void display(int x) { }
    }
    class Child extends Parent {
        // ✅ Valid override — same name, same parameter types
        @Override
        void display(int x) { }
        
        // ❌ Not override — different parameter type (overloading)
        void display(String s) { }  // Overload, not override
    }
```
  </Card>
  
  <Card title="Rule 2: Return Type Must Be Same or Covariant" icon="approve-check">
```java

    class AnimalFactory {
        Animal create() { return new Animal(); }
    }
    
    class DogFactory extends AnimalFactory {
        // ✅ Covariant return type — Dog IS-A Animal
        @Override
        Dog create() { return new Dog(); }  // More specific return type ✅
    }
    
    // ❌ Invalid: Cannot return unrelated type
    // class Cat { }
    // @Override
    // Cat create() { return new Cat(); }  // ❌ C.E: return type incompatible
```  </Card>

```java

        protected void show() { }

        @Override
        public void show() { }  // protected → public ✅

    }

  </Card>

```

class Parent {
    protected Number compute() throws IOException { return 0; }
}

class Child extends Parent {
    // ✅ Covariant return — Integer IS-A Number
    // ✅ Widened access — public > protected
    // ✅ Narrowed throws — FileNotFoundException ⊂ IOException
    @Override
    public Integer compute() throws FileNotFoundException { return 42; }
}
```

### 🎯 @Override Annotation — Why It Matters

<Code lang="java" title="@Override — compile-time safety check" code={`
class Animal {
    public void makeSound() { }
}

class Dog extends Animal {
    // ✅ With @Override — compiler checks signature matches
    @Override
    public void makeSound() { }  // ✅ Valid override
    
    // ❌ Typo in method name — @Override catches error at compile time
    @Override    public void makeSounds() { }  // ❌ C.E: method does not override or implement a supertype method
    
    // Without @Override — typo becomes silent bug (new method, not override)
    public void makeSounds() { }  // ❌ Compiles, but creates NEW method — not override!
}

// Best Practice: ALWAYS use @Override for overridden methods
// ✅ Catches typos, signature mismatches, and accidental overloads at compile time
`} />

<Aside type="tip">
**@Override Benefits**:
1. ✅ **Compile-time safety** — catches signature mismatches early
2. ✅ **Self-documenting** — clearly signals intent to override
3. ✅ **Refactoring aid** — IDEs use it to find/replace overridden methods
4. ✅ **Prevents silent bugs** — typos become compile errors, not runtime surprises
</Aside>

## 🔍 instanceof and Type Casting — Working with Inheritance

> **instanceof** checks an object's runtime type; **casting** converts reference types safely.

### 🔑 instanceof — Runtime Type Check

<Code lang="java" title="instanceof — safe type checking before casting" code={`class Animal { }
class Dog extends Animal { }
class Cat extends Animal { }

Animal pet = new Dog();  // Parent reference, child object

// ✅ Safe type check before casting
if (pet instanceof Dog) {
    Dog dog = (Dog) pet;  // ✅ Safe cast — guaranteed to succeed
    // Use dog-specific methods...
}

// ❌ Unsafe cast without check — may throw ClassCastException
// Cat cat = (Cat) pet;  // 💥 Runtime: ClassCastException (Dog cannot be cast to Cat)

// ✅ Modern Java 16+: Pattern matching for instanceof
if (pet instanceof Dog dog) {  // ✅ Declare and cast in one step
    // dog is automatically cast to Dog type in this block
    System.out.println("It's a dog!");
}

// instanceof with null — always returns false (never throws NPE)
Animal nullPet = null;
System.out.println(nullPet instanceof Dog);  // false ✅`} />

### 🔗 Type Casting — Upcasting vs Downcasting

<Code lang="java" title="Upcasting (implicit) vs Downcasting (explicit)" code={`class Animal {
    void eat() { System.out.println("Eating..."); }
}
class Dog extends Animal {
    void bark() { System.out.println("Woof!"); }
}

// ✅ Upcasting — implicit, always safe
Animal animal = new Dog();  // Dog IS-A Animal → implicit upcast
animal.eat();  // ✅ Works — method from Animal
// animal.bark();  // ❌ C.E: bark() not defined in Animal reference

// ✅ Downcasting — explicit, requires instanceof check
if (animal instanceof Dog) {
    Dog dog = (Dog) animal;  // ✅ Safe downcast
    dog.bark();  // ✅ Now can call Dog-specific methods
}

// ❌ Unsafe downcast — may throw ClassCastException at runtime
Cat cat = (Cat) animal;  // 💥 Runtime: ClassCastException (Dog cannot be cast to Cat)

// ✅ Modern pattern matching (Java 16+) — safer and cleaner
if (animal instanceof Dog dog) {
    dog.bark();  // dog is already cast — no manual (Dog) needed
}
`} />

### ⚠️ Casting Pitfalls & Best Practices

<CardGrid>
  <Card title="Pitfall: Casting Without instanceof Check" icon="error">
```java
    Animal animal = getAnimal();  // Could be Dog, Cat, or other subclass
    
    // ❌ Dangerous: No type check before cast
    Dog dog = (Dog) animal;  // 💥 ClassCastException if animal is not Dog
    
    // ✅ Safe: Check type first
    if (animal instanceof Dog) {
        Dog dog = (Dog) animal;  // ✅ Guaranteed safe
        dog.bark();
    }
    
    // ✅ Modern: Pattern matching (Java 16+)
    if (animal instanceof Dog dog) {
        dog.bark();  // ✅ Safe and concise    }
```
  </Card>
  
  <Card title="Pitfall: Unnecessary Casting" icon="caution">
```java
    Animal animal = new Dog();
    
    // ❌ Unnecessary: animal already IS-A Animal
    Animal a = (Animal) animal;  // Redundant cast — compiler warns
    
    // ✅ Clean: No cast needed
    Animal a = animal;
    
    // ❌ Unnecessary: Upcasting is implicit
    Animal b = (Dog) new Dog();  // Redundant — Dog automatically upcasts to Animal
```
  </Card>

  <Card title="Best Practice: Program to the Interface/Abstract Type" icon="rocket">
```java
    // ❌ Tightly coupled — depends on concrete class
    List<String> names = new ArrayList<>();  // Hard to change implementation later
    
    // ✅ Loosely coupled — depends on abstraction
    List<String> names = new ArrayList<>();  // Can swap to LinkedList, etc. without changing client code
    
    // Same principle with inheritance:
    // ❌ Depends on concrete subclass
    Dog dog = new Dog();
    dog.bark();  // Only works for Dog
    
    // ✅ Depends on abstract supertype
    Animal pet = new Dog();  // Can be Dog, Cat, or any Animal subclass
    pet.eat();  // Works for all Animal types — polymorphism ✅
```
  </Card>
</CardGrid>

## 🚫 Inheritance Restrictions & final Keyword

### 🔒 final Classes — Prevent Inheritance

<Code lang="java" title="final class — cannot be extended" code={`// ✅ final class — inheritance prohibited
public final class String {  // Real Java example
    // ... implementation
}
// ❌ Compile Error: cannot inherit from final String
// class MyString extends String { }  // ❌ C.E: cannot inherit from final String

// Why use final classes?
// • Security: Prevent malicious subclasses from overriding behavior
// • Immutability: Guarantee state cannot be changed via subclass
// • Performance: JVM can optimize final classes more aggressively
// • Design: Signal "this class is complete — not meant for extension"
`} />

### 🔒 final Methods — Prevent Overriding

<Code lang="java" title="final method — cannot be overridden" code={`class Animal {
    // ✅ final method — implementation locked
    public final void breathe() {
        System.out.println("Breathing...");
    }
    
    // ✅ Non-final method — can be overridden
    public void makeSound() {
        System.out.println("Generic sound");

## 🌐 Multiple Inheritance Through Interfaces

> Java doesn't support multiple class inheritance, but **interfaces enable multiple inheritance of type**.

### 🔑 Interface Implementation — Multiple Capabilities

<Code lang="java" title="One class, multiple interfaces — multiple inheritance of type" code={`
// Capabilities as interfaces
interface Flyable {
    void fly();
}
interface Swimmable {
    void swim();
}
interface Runnable {
    void run();
}

// One class implementing multiple interfaces
class Duck implements Flyable, Swimmable, Runnable {
    @Override
    public void fly() { System.out.println("Flying..."); }
    
    @Override
    public void swim() { System.out.println("Swimming..."); }
    
    @Override
    public void run() { System.out.println("Running..."); }
}

// Usage — polymorphism via multiple interface types
Flyable f = new Duck();
f.fly();  // ✅

Swimmable s = new Duck();
s.swim();  // ✅

// Duck has ALL capabilities
Duck duck = new Duck();
duck.fly();   // ✅
duck.swim();  // ✅
duck.run();   // ✅
`} />

### ⚠️ Default Method Conflict Resolution

<Code lang="java" title="Resolving default method conflicts from multiple interfaces" code={`
interface A {
    default void show() { System.out.println("A"); }
}
interface B {
    default void show() { System.out.println("B"); }
}

// ❌ Compile Error: class inherits unrelated defaults for show() from A and B
class C implements A, B {
    // MUST resolve conflict explicitly:
    @Override
    public void show() {
        // Option 1: Choose one interface's default
        A.super.show();  // "A"
        // OR B.super.show();  // "B"
        
        // Option 2: Provide custom implementation
        // System.out.println("C");
        
        // Option 3: Combine both
        // A.super.show();
        // B.super.show();
    }
}

// Usage:
C c = new C();
c.show();  // Depends on implementation choice above
`} />

Example:

- `class Dog implements Flyable, Trainable` (CAN-DO capabilities)  
✅ This combines single class inheritance with multiple interface inheritance.

## 🔬  Field Hiding vs Method Overriding

```java
class Parent {
    String name = "Parent";             // field
    static String type = "ParentType";  // static field

    void show() { System.out.println("Parent.show"); }
}

class Child extends Parent {
    String name = "Child";              // HIDES parent field — not override
    static String type = "ChildType";  // HIDES parent static field

    @Override
    void show() { System.out.println("Child.show"); }  // OVERRIDES
}

Parent p = new Child();

// Field access — reference type decides (compile-time)
System.out.println(p.name);     // "Parent" — field hiding, not override
System.out.println(p.type);     // "ParentType" — static field hiding

// Method call — runtime type decides
p.show();                       // "Child.show" — overriding, runtime dispatch

Child c = (Child) p;
System.out.println(c.name);     // "Child" — Child reference sees Child field
```

> 🔑 Fields are **hidden**, not overridden. The reference type determines which field is accessed. Method overriding uses runtime type. This asymmetry is a deep source of confusion and bugs.

## 💻 Real-World Code — Payment Processing Hierarchy

```java
// Base — common behavior all processors share
public abstract class PaymentProcessor {

    protected final String merchantId;
    protected final Logger log = LoggerFactory.getLogger(getClass());

    private static final int DEFAULT_TIMEOUT_MS = 5000;

    protected PaymentProcessor(String merchantId) {
        this.merchantId = Objects.requireNonNull(merchantId);
    }

    // Template method — final — algorithm fixed
    public final PaymentResult process(PaymentRequest request) {
        validate(request);                          // ① validate (abstract)
        log.info("Processing {} via {}",
            request.getId(), getClass().getSimpleName());
        PaymentResult result = doProcess(request);  // ② process (abstract)
        audit(request, result);                     // ③ audit (concrete)
        return result;
    }

    // Abstract — each processor validates differently
    protected abstract void validate(PaymentRequest request);

    // Abstract — each processor calls different API
    protected abstract PaymentResult doProcess(PaymentRequest request);

    // Concrete — shared audit logic
    private void audit(PaymentRequest req, PaymentResult result) {
        log.info("Processed {} → {} txn={}",
            req.getId(), result.getStatus(), result.getTransactionId());
    }

    // Overridable — subclass may customize timeout
    protected int timeoutMs() { return DEFAULT_TIMEOUT_MS; }
}

// Mid-level — card processing specifics
public abstract class CardProcessor extends PaymentProcessor {

    protected CardProcessor(String merchantId) {
        super(merchantId);
    }

    // Shared card validation for all card processors
    @Override
    protected void validate(PaymentRequest request) {
        Objects.requireNonNull(request, "request required");
        Objects.requireNonNull(request.getCard(), "card required");
        if (request.getCard().isExpired())
            throw new PaymentException("Card expired");
        if (request.getAmount().compareTo(BigDecimal.ZERO) <= 0)
            throw new PaymentException("Amount must be positive");
    }
}

// Leaf — Stripe card processing
public final class StripeCardProcessor extends CardProcessor {

    private final StripeClient stripeClient;

    public StripeCardProcessor(String merchantId, StripeClient stripeClient) {
        super(merchantId);
        this.stripeClient = stripeClient;
    }

    @Override
    protected PaymentResult doProcess(PaymentRequest request) {
        try {
            StripeCharge charge = stripeClient.charge(
                request.getCard().getToken(),
                request.getAmount(),
                merchantId
            );
            return PaymentResult.success(charge.getId());
        } catch (StripeException e) {
            throw new PaymentException("Stripe charge failed", e);
        }
    }

    @Override
    protected int timeoutMs() { return 8000; }  // Stripe needs more time
}

// Leaf — Braintree card processing
public final class BraintreeCardProcessor extends CardProcessor {

    private final BraintreeGateway braintreeGateway;

    public BraintreeCardProcessor(String merchantId,
                                   BraintreeGateway gateway) {
        super(merchantId);
        this.braintreeGateway = gateway;
    }

    @Override
    protected PaymentResult doProcess(PaymentRequest request) {
        TransactionRequest txnReq = new TransactionRequest()
            .amount(request.getAmount())
            .paymentMethodToken(request.getCard().getToken());
        Result<Transaction> result = braintreeGateway.transaction().sale(txnReq);
        if (result.isSuccess())
            return PaymentResult.success(result.getTarget().getId());
        throw new PaymentException("Braintree declined: " + result.getMessage());
    }
}
```

🔴 **What breaks if done wrong:** `process()` not `final` → subclass overrides → skips audit logging → compliance violation → financial transactions have no audit trail → regulatory breach.

**Underlying primitive: vtable (virtual dispatch table) + class metadata chain**

```
Inheritance in JVM:

class hierarchy:
  Object ← Animal ← Dog

Each class has a vtable:
  Object vtable: [toString, equals, hashCode, ...]
  Animal vtable: [toString, equals, hashCode, eat, sleep]
                                                ↑     ↑
                              inherited slots   |     |
  Dog vtable:    [toString, equals, hashCode, eat, sleep, bark]
                  ↑ overridden if Dog overrides toString

Method dispatch:
  dog.eat()
  → JVM: get klass pointer from dog's object header
  → klass = Dog metadata
  → Dog.vtable[eat_slot] → Animal.eat (if Dog didn't override)
  → execute Animal.eat

Inheritance chain in bytecode (.class file):
  Dog.class attribute: super_class = Animal
  Animal.class attribute: super_class = Object
  Object.class attribute: super_class = none

instanceof bytecode:
  instanceof instruction
  → walks klass chain: Dog → Animal → Object
  → checks each against target type
  → O(depth of hierarchy)

Class loading order:
  Dog requires Animal requires Object
  Loaded: Object → Animal → Dog
  Static init: Object → Animal → Dog (top to bottom)
```

## 🎯 Interview Cheat Sheet

<CardGrid>
  <Card title="Q: What is the difference between method overloading and overriding?" icon="information">
    **Overloading**: Same method name, **different parameters** — resolved at **compile time** (static binding).  
    **Overriding**: Same method name **and parameters** in subclass — resolved at **runtime** (dynamic binding).  
    ✅ Overloading = compile-time polymorphism; Overriding = runtime polymorphism.
  </Card>
  
  <Card title="Q: Can we override static methods?" icon="error">
    **NO ❌** — static methods are **hidden**, not overridden.  
    Method call depends on **reference type**, not object type.  
    Example: `Parent p = new Child(); p.staticMethod()` calls `Parent.staticMethod()`, not `Child`'s version.
  </Card>

  <Card title="Q: What is covariant return type?" icon="approve-check">
    **Covariant return type**: Overriding method can return a **more specific subtype** of the parent's return type.  
    ```java
    class Animal { Animal copy() { return new Animal(); } }
    class Dog extends Animal { @Override Dog copy() { return new Dog(); } }  // ✅ Dog IS-A Animal
    ```
    ✅ Enables more type-safe APIs while maintaining polymorphism.
  </Card>

  <Card title="Q: Why does Java not support multiple class inheritance?" icon="information">
    **To avoid ambiguity and complexity**:  
    - Diamond problem: Which parent's method/field to inherit if both define same name?  
    - Increased complexity in method resolution, constructor chaining, memory layout  
    ✅ Java uses **interfaces** for multiple inheritance of type — avoids diamond problem while enabling capabilities.
  </Card>

  <Card title="Q: What is the IS-A relationship?" icon="approve-check">
    **IS-A** means a subclass **is a type of** its superclass.  
    - `Dog IS-A Animal` → `Dog` can be used anywhere `Animal` is expected  
    - Enables polymorphism: `Animal pet = new Dog()`  
    ✅ Verified at compile time via inheritance hierarchy.
  </Card>

  <Card title="Q: Can a constructor be overridden?" icon="error">
    **NO ❌** — constructors are **not inherited** and cannot be overridden.  
    Each class defines its own constructors; child constructors must explicitly call parent constructors via `super()`.
  </Card>

  <Card title="Q: What happens if a subclass constructor doesn't call super()?" icon="caution">
    **Compiler inserts implicit `super()`** (no-arg) as first statement.  
    ❌ Compile Error if parent has **no no-arg constructor** — must explicitly call matching parent constructor.
  </Card>

  <Card title="Q: How does instanceof work with inheritance?" icon="approve-check">
    `instanceof` checks **runtime type** against a type in the inheritance hierarchy.  
    ```java
    Dog dog = new Dog();
    System.out.println(dog instanceof Dog);    // true
    System.out.println(dog instanceof Animal); // true (Dog IS-A Animal)
    System.out.println(dog instanceof Object); // true (all classes extend Object)
    ```
    ✅ Returns `false` for unrelated types; `null instanceof X` always returns `false` (no NPE).
  </Card>
</CardGrid>

**🪤 Trap 1 — Constructor not inherited — super() implicit only if no-arg exists**

```java
class Parent {
    Parent(int x) {
        System.out.println("Parent: " + x);
    }
    // No no-arg constructor
}

class Child extends Parent {
    Child() {
        // implicit super() tries to call Parent() — DOESN'T EXIST
        // COMPILE ERROR: no suitable constructor found
    }

    Child(int x) {
        super(x);   // ✅ explicit — required
    }
}
```

Adding a parameterized constructor to a parent class removes its implicit no-arg. Every subclass that relied on implicit `super()` now fails to compile. Silent breaking change in team codebases.

**🪤 Trap 2 — Field hiding vs method overriding asymmetry**

```java
class Base {
    int value = 10;
    int getValue() { return value; }
}

class Derived extends Base {
    int value = 20;                 // hides Base.value
    @Override
    int getValue() { return value; } // returns Derived.value = 20
}

Base b = new Derived();
System.out.println(b.value);        // 10 — field: reference type decides
System.out.println(b.getValue());   // 20 — method: runtime type decides
```

Same object, same field name, different values depending on how accessed. This is one of the deepest and most dangerous Java gotchas.

**🪤 Trap 4 — `instanceof` returns true for entire hierarchy**

} else if (obj instanceof B b) {

}

## 🔑 Quick Reference Summary

### Inheritance Rules Checklist

| Rule | Description | Example |
|------|-------------|---------|
| **Single Inheritance** | Class can extend only one direct superclass | `class Dog extends Animal` ✅ |
| **Constructor Chaining** | Parent constructor runs before child | `super()` must be first in child constructor |
| **Method Overriding** | Same signature, compatible return type, same/wider access | `@Override public void makeSound()` |
| **final Classes** | Cannot be extended | `public final class String` |
| **final Methods** | Cannot be overridden | `public final void breathe()` |
| **private Members** | Not accessible in subclass | `private String secret` not visible in child |
| **static Methods** | Hidden, not overridden — resolved by reference type | `Parent p = new Child(); p.staticMethod()` → Parent's version |

### instanceof & Casting Quick Guide

| Operation | Syntax | When to Use |
|-----------|--------|-------------|
| **Type Check** | `obj instanceof Type` | Before casting to ensure safety |
| **Upcasting** | `Parent p = new Child()` | Implicit — always safe |
| **Downcasting** | `Child c = (Child) parentRef` | Explicit — requires `instanceof` check first |
| **Pattern Matching** | `if (obj instanceof Child c)` | Java 16+ — safe cast + declaration in one step |

### Common Pitfalls & Fixes

| Pitfall | Risk | Fix |
|---------|------|-----|
| Forgetting `super()` when parent has no no-arg constructor | Compile error | Explicitly call matching parent constructor |
| Overriding with more restrictive access | Compile error | Match or widen access modifier |
| Casting without `instanceof` check | `ClassCastException` at runtime | Always check type first or use pattern matching |
| Confusing overloading with overriding | Silent bugs, unexpected behavior | Use `@Override` annotation for compile-time checks |
| Deep inheritance hierarchies | Fragile code, hard to maintain | Favor composition; keep hierarchies shallow |

<Aside type="caution">
**Final Checklist for Inheritance Design**:
1. ✅ Use inheritance for **IS-A relationships** — not just code reuse
2. ✅ Favor **composition over inheritance** when behavior varies independently
3. ✅ Use `@Override` always — catches signature mismatches at compile time
4. ✅ Document abstract methods clearly — JavaDoc for expected behavior
5. ✅ Keep hierarchies **shallow and focused** — avoid deep, complex trees
6. ✅ Test polymorphic behavior — ensure subclasses fulfill parent contract
7. ✅ Use `final` judiciously — prevent unintended extension/overriding when appropriate
8. ✅ Prefer interfaces for **capabilities**, abstract classes for **shared implementation**
</Aside>

## 🧩 Composition & Aggregation in Java

---

## 🗺️ The Full Map

```
Object Relationships
│
├── Inheritance      → IS-A relationship
│   └── Dog IS-A Animal
│
├── Composition      → HAS-A (strong) — owns it
│   └── Car HAS-A Engine — Engine dies with Car
│
├── Aggregation      → HAS-A (weak) — uses it
│   └── Team HAS-A Player — Player exists without Team
│
└── Association      → USES-A — loose reference
    └── Order USES-A Customer — temporary relationship
```

---

## 🔬 Step 1 — What Each Means

```
Composition (strong HAS-A):
  ├── Owner creates the owned object
  ├── Owned object CANNOT exist without owner
  ├── Owner is responsible for lifecycle
  ├── Owner destroyed → owned destroyed
  └── Example: House HAS-A Room — Room meaningless without House

Aggregation (weak HAS-A):
  ├── Owner references an externally created object
  ├── Owned object CAN exist without owner
  ├── Lifecycle is independent
  ├── Owner destroyed → owned still alive
  └── Example: University HAS-A Professor — Professor exists after University closes

Association (USES-A):
  ├── Loosest relationship — just a reference
  ├── No ownership at all
  ├── May be temporary (method parameter)
  └── Example: Driver USES-A Car — doesn't own it
```

## 🔬 Step 2 — Composition in Code

```java
// Engine cannot exist meaningfully without a Car
// Car creates and owns Engine

public final class Engine {

    private final int    horsepower;
    private final String type;
    private       boolean running;

    // Package-private — only Car creates Engine
    Engine(int horsepower, String type) {
        if (horsepower <= 0)
            throw new IllegalArgumentException("horsepower must be positive");
        this.horsepower = horsepower;
        this.type       = type;
        this.running    = false;
    }

    void start()  { this.running = true; }
    void stop()   { this.running = false; }
    boolean isRunning() { return running; }
    int getHorsepower() { return horsepower; }
}

public final class Car {

    private final String  model;
    private final Engine  engine;       // ← COMPOSITION
    private final Chassis chassis;      // ← COMPOSITION
    private final Gearbox gearbox;      // ← COMPOSITION

    public Car(String model, int horsepower) {
        this.model   = model;
        this.engine  = new Engine(horsepower, "V8");    // Car creates Engine
        this.chassis = new Chassis();
        this.gearbox = new Gearbox();
    }

    public void start() {
        engine.start();
        gearbox.engage();
        System.out.println(model + " started");
    }

    public void stop() {
        gearbox.disengage();
        engine.stop();
    }

    // No getter for engine — encapsulated completely
    public int getHorsepower() { return engine.getHorsepower(); }
}

// Engine never exposed — Car controls entire lifecycle
Car car = new Car("BMW M3", 503);
car.start();
// car goes out of scope → Car GC'd → Engine GC'd (no other references)
```

```
Composition indicators in code:
  ├── Object created with new INSIDE the owner's constructor
  ├── No public getter exposing the component
  ├── Component class has package-private or private constructor
  └── Component has no meaning/value standalone
```

## 🔬 Step 5 — Composition over Inheritance

```
"Favor composition over inheritance" — Effective Java

Inheritance problems:
  ├── Tight coupling to parent implementation
  ├── Fragile base class — parent change breaks subclass
  ├── Forced IS-A relationship — may not be semantically correct
  └── Cannot change relationship at runtime

Composition advantages:
  ├── Loose coupling — depend on interface, not class
  ├── Change behavior at runtime by swapping component
  ├── Easier to test — mock components
  └── More flexible — combine behaviors freely
```

```java
// ❌ Inheritance — LoggingList tightly coupled to ArrayList internals
public class LoggingList<E> extends ArrayList<E> {

    private int addCount = 0;

    @Override
    public boolean add(E element) {
        addCount++;
        return super.add(element);      // calls ArrayList.add()
    }

    @Override
    public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return super.addAll(c);         // calls ArrayList.addAll()
        // PROBLEM: ArrayList.addAll() calls this.add() internally
        // → our add() increments addCount again → double counting
    }
}

// ✅ Composition — wraps List, doesn't extend it
public class LoggingList<E> implements List<E> {

    private final List<E> delegate;     // ← COMPOSITION — any List impl
    private       int     addCount = 0;

    public LoggingList(List<E> delegate) {
        this.delegate = Objects.requireNonNull(delegate);
    }

    @Override
    public boolean add(E element) {
        addCount++;
        return delegate.add(element);   // delegates — no surprise internals
    }

    @Override
    public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return delegate.addAll(c);      // delegates — addAll doesn't call our add()
    }

    public int getAddCount() { return addCount; }

    // All other List methods delegate
    @Override public int size()             { return delegate.size(); }
    @Override public boolean isEmpty()      { return delegate.isEmpty(); }
    @Override public E get(int index)       { return delegate.get(index); }
    // ... rest of List interface
}

// Now works with ANY List — can swap ArrayList for LinkedList
LoggingList<String> list = new LoggingList<>(new ArrayList<>());
list.add("a");
list.add("b");
list.addAll(List.of("c", "d"));
System.out.println(list.getAddCount());  // 4 — correct
```

## 💻 Real-World Code — Order Processing System

```java
// Strongly composed — Order owns its line items
public final class Order {

    private final UUID             id;
    private final String           customerId;
    private final List<LineItem>   items;       // ← COMPOSITION — Order creates/owns
    private final Money            total;
    private       OrderStatus      status;
    private final Instant          createdAt;

    public Order(String customerId) {
        this.id         = UUID.randomUUID();
        this.customerId = Objects.requireNonNull(customerId);
        this.items      = new ArrayList<>();
        this.status     = OrderStatus.PENDING;
        this.createdAt  = Instant.now();
        this.total      = Money.ZERO;
    }

    public void addItem(String productId, int quantity, Money unitPrice) {
        if (status != OrderStatus.PENDING)
            throw new IllegalStateException("Cannot add items to " + status + " order");
        // LineItem created BY Order — composition
        items.add(new LineItem(productId, quantity, unitPrice));
    }

    public Money calculateTotal() {
        return items.stream()
            .map(LineItem::subtotal)
            .reduce(Money.ZERO, Money::add);
    }

    // LineItem is an inner implementation detail
    // Caller never creates LineItem directly
    private static final class LineItem {
        private final String productId;
        private final int    quantity;
        private final Money  unitPrice;

        private LineItem(String productId, int quantity, Money unitPrice) {
            this.productId = productId;
            this.quantity  = quantity;
            this.unitPrice = unitPrice;
        }

        Money subtotal() {
            return unitPrice.multiply(BigDecimal.valueOf(quantity));
        }
    }
}

// OrderService — aggregates repositories (injected, not created)
public class OrderService {

    // AGGREGATION — all injected, exist independently
    private final OrderRepository    orderRepository;
    private final InventoryService   inventoryService;
    private final PaymentGateway     paymentGateway;
    private final NotificationService notificationService;

    // Injected — not created here
    public OrderService(OrderRepository    orderRepository,
                        InventoryService   inventoryService,
                        PaymentGateway     paymentGateway,
                        NotificationService notificationService) {
        this.orderRepository    = Objects.requireNonNull(orderRepository);
        this.inventoryService   = Objects.requireNonNull(inventoryService);
        this.paymentGateway     = Objects.requireNonNull(paymentGateway);
        this.notificationService = Objects.requireNonNull(notificationService);
    }

    public OrderConfirmation placeOrder(PlaceOrderRequest request) {

        // Order created — owns its line items (composition inside Order)
        Order order = new Order(request.getCustomerId());
        request.getItems().forEach(item ->
            order.addItem(item.getProductId(), item.getQuantity(), item.getPrice())
        );

        // Check inventory — uses InventoryService (aggregation)
        inventoryService.reserve(order);

        // Charge payment — uses PaymentGateway (aggregation)
        PaymentResult payment = paymentGateway.charge(
            request.getPaymentToken(),
            order.calculateTotal()
        );

        // Save — uses OrderRepository (aggregation)
        orderRepository.save(order);

        // Notify — uses NotificationService (aggregation)
        notificationService.sendOrderConfirmation(order);

        return OrderConfirmation.of(order, payment);
    }
}
```

🔴 **What breaks if done wrong:** `OrderService extends OrderRepository` — inheritance instead of composition → `OrderService` is a repository → cannot swap repository implementation → cannot mock in tests → tightly coupled to database → integration tests required for every unit test.

## 🔩 DSA / Internals Connection

**Underlying primitive: Object graph + reference counting/tracing GC**

```
Object relationships in heap:

Composition (Car owns Engine):
  Stack:         Heap:
  car → 0x100 →  Car object
                   engine field → 0x200  ← direct reference
                              Engine object
                               (no other refs to Engine)

  car = null → Car eligible for GC
  → Engine has no other references → also GC eligible
  → Both collected in same GC cycle

Aggregation (Department contains Professors):
  Stack:               Heap:
  dept → 0x100  →      Department object
                         professors[0] → 0x300 ─────────┐
  prof1 → 0x300 ──────────────────────────────────── Professor object
                                                         (2 references: dept + prof1)

  dept = null → Department eligible for GC
  → professors list GC'd
  → Professor at 0x300 still has prof1 reference → NOT GC'd
  → Aggregation: component survives owner

GC tracing algorithm:
  Starts from GC roots (stack frames, static fields)
  Traces all reachable objects
  Unreachable = collectable
  Composition: reachable only via owner → collected together
  Aggregation: reachable via multiple paths → survives owner
```
