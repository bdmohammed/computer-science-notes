## 🏗️ Instance Control Flow in Java

> **Every time `new` is called, the JVM executes instance members in a strict, defined order. This is Instance Control Flow — the sequence governing instance variable defaults, instance initializer blocks, and constructor execution.**

<Aside type="tip">
**🧠 Mental Model**: Think of object creation as a **three-phase assembly line**.  
1. **Identification**: Memory allocated, fields zeroed (`0`, `null`, `false`).  
2. **Execution**: Run assignments and instance blocks top-to-bottom.  
3. **Constructor**: Run the constructor body last.  
⚠️ Parent completes all 3 phases before Child begins Phase 1.
</Aside>

---

## 🔬 The Three Phases (Per Object Creation)

```
new MyClass() called
        │
        ▼
┌─────────────────────────────────────────────┐
│  PHASE 1 — IDENTIFICATION                   │
│  JVM scans top-to-bottom                    │
│  All instance variables → DEFAULT values    │
│  (0, null, false)                           │
│  No assignments. No blocks. No constructor. │
└─────────────────────────────────────────────┘
        │
        ▼
┌─────────────────────────────────────────────┐
│  PHASE 2 — EXECUTION (top → bottom)         │
│  Instance variable assignments  ──┐         │
│  Instance initializer blocks    ──┤ in order│
│  (interleaved by position)      ──┘         │
└─────────────────────────────────────────────┘
        │
        ▼
┌─────────────────────────────────────────────┐
│  PHASE 3 — CONSTRUCTOR BODY executes        │
│  (after Phase 2 completes fully)            │
└─────────────────────────────────────────────┘
```

### The Execution Order 📜
```
Interview Critical: Memorize this sequence for every object creation.
Instance Variables (Default values → Explicit values)
Instance Initializer Blocks (IIB) (Top to bottom)
Constructor

🏛️ Flow Diagram:

+---------------------+
|   new Child()       |
+---------------------+
         |
         v
+---------------------+
| 1. Parent Static    | (If not loaded yet)
+---------------------+
         |
         v
+---------------------+
| 2. Child Static     | (If not loaded yet)
+---------------------+
         |
         v
+---------------------+
| 3. Parent Instance  | (Vars -> IIB -> Constructor)
+---------------------+
         |
         v
+---------------------+
| 4. Child Instance   | (Vars -> IIB -> Constructor)
+---------------------+
```


## 📋 Execution Order Rules

| Rule | Behavior |
|------|----------|
| **Instance Variables** | Get **default** value in Phase 1 (`0`, `null`, `false`). |
| **Assignments + Blocks** | Execute **top-to-bottom** in Phase 2. |
| **Constructor** | Always runs **after** Phase 2 completes. |
| **Multiple Instance Blocks** | All run, in declaration order, before constructor. |
| **`this()` Constructor Call** | Must be **first statement**; redirects to another constructor. |
| **`super()` Call** | Implicit or explicit; always **first thing** in constructor. |

## 💻 Real-World Code — Connection Object Pattern

<Code lang="java" title="DBConnection — Watch the order!" code={`
public class DBConnection {

    // Phase 1: retries = 0, host = null, timeout = 0 (defaults)

    int retries = 3;                          // Phase 2, Step 1

    {                                         // Phase 2, Step 2
        System.out.println("Block 1 — retries: " + retries);   // 3
        System.out.println("Block 1 — timeout: " + timeout);   // 0 ← default!
    }

    int timeout = 5000;                       // Phase 2, Step 3

    {                                         // Phase 2, Step 4
        System.out.println("Block 2 — timeout: " + timeout);   // 5000
    }

    DBConnection() {
        System.out.println("Constructor — timeout: " + timeout); // 5000
    }
}`} />

**Output when `new DBConnection()` is called:**
```text
Block 1 — retries: 3
Block 1 — timeout: 0      ← ⚠️ TRAP: read timeout before its assignment
Block 2 — timeout: 5000
Constructor — timeout: 5000
```

<Aside type="danger">
**🚨 Production Bug**: Validation logic inside an early instance block reads a field that appears initialized in source but is still `0`/`null`. Silent misconfiguration — no exception thrown. Always be aware of the **top-to-bottom execution order**.
</Aside>

## 🔁 Inheritance — Full Flow

> **Rule**: Parent instance initialization completes **fully** (all 3 phases) before Child instance initialization begins.

```
new Child() triggered
        │
        ▼
  Static Control Flow (if class not yet loaded)
  Parent static → Child static
        │
        ▼
  ┌─────────────────────────────────────┐
  │  Parent — Phase 1 (identify)        │
  │  Parent — Phase 2 (assignments +    │
  │           instance blocks)          │
  │  Parent — Phase 3 (constructor)     │
  └─────────────────────────────────────┘
        │
        ▼
  ┌─────────────────────────────────────┐
  │  Child — Phase 1 (identify)         │
  │  Child — Phase 2 (assignments +     │
  │          instance blocks)           │
  │  Child — Phase 3 (constructor)      │
  └─────────────────────────────────────┘
        │
        ▼
  Object reference returned to caller
```

<Code lang="java" title="Parent/Child Instance Initialization Order" code={`class Parent {
    int x = 10;
    {
        System.out.println("Parent block — x: " + x); // 10
    }
    Parent() {
        System.out.println("Parent constructor");
        show(); // ← ⚠️ DANGER: polymorphic call before Child init
    }
    void show() {
        System.out.println("Parent.show()");
    }
}

class Child extends Parent {
    int y = 20;
    {
        System.out.println("Child block — y: " + y);  // 20
    }
    Child() {
        // implicit super() fires first
        System.out.println("Child constructor");
    }
    @Override
    void show() {
        // Called from Parent() — before Child Phase 2 runs!
        System.out.println("Child.show() — y: " + y); // y = 0 ← TRAP
    }
}

// new Child() output:
// Parent block — x: 10
// Parent constructor
// Child.show() — y: 0   ← NOT 20! Child Phase 2 hasn't run yet.
// Child block — y: 20
// Child constructor`} />

<Aside type="caution">
**Key Insight**: When `Child` is instantiated:  
1. `Parent` initializes completely (`x=10`, block runs, constructor runs).  
2. `Parent` constructor calls `show()` → polymorphic dispatch → `Child.show()`.  
3. At this point, `Child` Phase 2 hasn't run yet → `y` is still `0` (default)!  
4. Only after `Parent` constructor returns does `Child` Phase 2 begin.
</Aside>

## ⚠️ Forward Reference Rule (Instance)

Same rules as static context. Java prevents you from using an instance variable **directly** before it is declared.

<CardGrid>
  <Card title="❌ Direct Read (Compile Error)" icon="error">
    ```java
    class Service {
        {
            int z = limit; // ❌ C.E: illegal forward reference
        }
        int limit = 50;
    }
    ```
  </Card>
  
  <Card title="✅ Indirect Read (Allowed)" icon="approve-check">
    ```java
    class Service {
        {
            method(); // ✅ Allowed: Method call bypasses check
        }
        void method() {
            System.out.println(limit); // Prints 0 (default value)
        }
        int limit = 50;
    }
    ```
  </Card>

  <Card title="✅ Write Before Declaration" icon="information">
    ```java
    class Service {
        {
            limit = 100; // ✅ Allowed: Writing is safe
        }
        int limit = 50; // Overwrites 100 with 50 later
    }
    // Final value of limit is 50.
    ```
  </Card>
</CardGrid>

<Aside type="note">
Polymorphism in IIB
```java
class Parent {
    { method(); }
    void method() { System.out.println("Parent"); }
}
class Child extends Parent {
    void method() { System.out.println("Child"); }
}
// new Child() prints "Child" inside Parent's IIB!
```
Why? Instance methods are virtual. Even inside Parent's IIB, the object is of type Child, so Child's overridden method is called.
⚠️ Danger: Accessing child fields in Parent's IIB/Constructor can cause NullPointerException because Child fields aren't initialized yet.
**Polymorphism in Instance Blocks**: Instance methods are **virtual**. Even inside `Parent`'s instance block, if the object is of type `Child`, `Child`'s overridden method is called.  
⚠️ Danger: Accessing child fields in `Parent`'s block/constructor can cause `NullPointerException` because child fields aren't initialized yet.
</Aside>

## 🔀 `this()` Constructor Chaining Flow

<Code lang="java" title="Constructor chaining execution order" code={`class HttpClient {
    String host;
    int port;
    int timeout;

    // Instance block runs ONCE, before any constructor body
    {
        System.out.println("Instance block runs");
    }

    HttpClient(String host) {
        this(host, 80);                        // → chains to 2-arg constructor
        System.out.println("1-arg done");
    }

    HttpClient(String host, int port) {
        this(host, port, 3000);                // → chains to 3-arg constructor
        System.out.println("2-arg done");
    }

    HttpClient(String host, int port, int timeout) {
        this.host = host;
        this.port = port;
        this.timeout = timeout;
        System.out.println("3-arg done");      // runs first
    }
}

// new HttpClient("api.service.com") output:
// Instance block runs    ← Runs ONCE, before terminal constructor
// 3-arg done
// 2-arg done
// 1-arg done`} />

```text
Chaining execution order:
  1-arg → 2-arg → 3-arg (body runs) → 2-arg (resumes) → 1-arg (resumes)

Key rules:
  • Instance blocks + variable assignments run ONCE, before the terminal constructor
  • NOT once per constructor in the chain
  • NOT skipped when this() is used
```

## 💣 Interview Traps

<CardGrid>
  <Card title="🪤 Trap 1: Overridden Method in Parent Constructor" icon="error">
    ```java
    class Animal {
        String type = "animal";
        Animal() {
            init(); // polymorphic call → resolves to Child's override
        }
        void init() {
            System.out.println("Animal.init — type: " + type);
        }
    }

    class Dog extends Animal {
        String breed = "Labrador";
        @Override
        void init() {
            // Called from Animal() — before Dog's Phase 2 runs!
            System.out.println("Dog.init — breed: " + breed); // null ← not "Labrador"
        }
    }
    // new Dog() → Dog.init — breed: null
    ```    
    Prod scenario: `init()` calls `breed.toUpperCase()` → `NullPointerException` at startup. Stack trace points to `Animal` constructor, not `Dog`. Root cause is invisible without understanding instance flow.
    **Fix**: Never call overridable methods from a constructor. Use `private` or `final` methods instead.
  </Card>
  
  <Card title="🪤 Trap 2: Instance Block with `this()` Chaining" icon="caution">
    ```java
    class Token {
        String value;
        {
            System.out.println("Instance block runs"); // always runs, always once
        }
        Token() {
            this("default");
        }
        Token(String value) {
            this.value = value;
        }
    }
    // new Token() output:
    // Instance block runs    ← Runs ONCE, before terminal constructor
    // NOT twice. NOT zero times.
    ```
    Trap: devs assume the instance block runs per constructor in the chain, or that it's skipped when `this()` is used. Neither is true. It runs **once**, before the **terminal** constructor body.
  </Card>

  <Card title="🪤 Trap 3: `super()` Before Child Instance Blocks" icon="shield">
    ```java
    class Base {
        Base() { System.out.println("Base constructor"); }
    }
    class Derived extends Base {
        int x = 10;
        {
            System.out.println("Derived block — x: " + x); // runs AFTER Base()
        }
        Derived() {
            // super() implicit — fires first
            System.out.println("Derived constructor");
        }
    }
    // new Derived():
    // Base constructor       ← super() fires, completes entirely
    // Derived block — x: 10 ← then Derived Phase 2
    // Derived constructor    ← then Derived Phase 3
    ```
    Trap: assuming the derived class's instance block runs before the parent constructor. It doesn't. Parent fully completes (all 3 phases) before child Phase 2 begins.
  </Card>

  <Card title="🪤 Trap 4: Final Field Definite Assignment" icon="backspace">
    ```java
    class Config {
        final int port;
        {
            // port = 8080; // if commented out:
        }
        Config() {
            // Compiler checks: final field 'port' must be assigned
            // before constructor exits — in block OR constructor, but exactly once
        }
    }
    // Compile error: variable port might not have been initialized
    ```
    **Rule**: `final` instance fields must be **definitely assigned** by the end of the constructor — enforced at compile time via definite assignment analysis.
  </Card>
</CardGrid>

## 🔩 Internals — `<init>` Bytecode & TLAB

### The `<init>` Method

All instance initializer blocks + instance variable assignments are compiled into **every constructor's `<init>` method** — right after the `super()` call, before the constructor's own body.

```bash
javap -c MyClass  # Look for <init>() method(s)

<init> structure:
  1. invokespecial → super.<init>()
  2. [Phase 2 code: assignments + instance blocks, top-to-bottom]
  3. [Constructor body code]
  4. return
```

Each constructor gets its **own `<init>`** with Phase 2 inlined. If there are 3 constructors, Phase 2 is compiled **3 times** into bytecode (unless `this()` chaining eliminates duplication).

### Object Memory Layout

```text
Object on heap:
┌────────────────────────────────┐
│  object header (mark word)     │  ← GC metadata, lock state
│  klass pointer                 │  ← points to class metadata
│  [field: retries = 0 → 3]     │  ← Phase 1 default, then Phase 2 value
│  [field: timeout = 0 → 5000]  │
└────────────────────────────────┘
```

<Aside type="note">
**TLAB Zero-Fill**: Object memory is allocated and zeroed **before** `<init>` runs via the Thread-Local Allocation Buffer (TLAB). This is why Phase 1 defaults exist — the JVM allocator guarantees zero-initialized memory.
</Aside>

## 🎯 Interview Cheat Sheet

<CardGrid>
  <Card title="Execution Order" icon="information">
    ```text
    Q: What is the order of instance initialization?
    A: Parent Instance (Vars → IIB → Constructor) → Child Instance (Vars → IIB → Constructor).
    
    Q: Do instance blocks run before the constructor?
    A: Yes — Phase 2 runs before Phase 3 (constructor body).
    ```
  </Card>
  
  <Card title="Forward References" icon="shield">
    ```text
    Q: Can I read an instance variable before it's declared?
    A: Directly? No (Compile Error). Indirectly (via method)? Yes (returns default).
    
    Q: Can I write to it?
    A: Yes. Writes are allowed before declaration.
    ```
  </Card>

  <Card title="Polymorphism & Constructors" icon="rocket">
    ```text
    Q: What happens if I call an overridden method from a constructor?
    A: Child's override is called, but child fields may still be default values → NPE risk.
    
    Q: Does the instance block run with this() chaining?
    A: Yes — exactly once, before the terminal constructor body.
    ```
  </Card>

  <Card title="Final Fields" icon="caution">
    ```text
    Q: When must final instance fields be assigned?
    A: By the end of the constructor — either in an instance block or constructor body.
    
    Q: Can final fields be assigned in multiple places?
    A: No — compiler enforces definite assignment: exactly one assignment path.
    ```
  </Card>
</CardGrid>

## 🧠 Full Mental Model Summary

```text
INSTANCE CONTROL FLOW CHECKLIST

1. Trigger:
   new X() → Memory allocated → Zero-filled → <init> runs

2. Parent First:
   Parent <init> completes fully before Child <init> starts.

3. Three Phases:
   Phase 1: Identify + Default values (0, null, false)
   Phase 2: Execute assignments + instance blocks (top-to-bottom)
   Phase 3: Constructor body runs last

4. Forward Reference:
   - Direct Read before decl? ❌ Compile Error
   - Indirect Read (method)? ✅ Returns default
   - Write? ✅ Allowed

5. Polymorphism Warning:
   - Overridden methods in constructors → Child fields may be uninitialized
   - Never call overridable methods from constructors

6. Final Fields:
   - Must be definitely assigned by end of constructor
   - Compiler enforces: exactly one assignment path
```

<Aside type="tip">
**Next Steps**:
1. ✅ Avoid calling overridable methods from constructors — use `private`/`final` instead
2. ✅ Keep instance blocks simple — avoid complex logic that depends on field order
3. ✅ Use constructor parameters for required initialization, not instance blocks
4. ✅ Understand that `this()` chaining runs instance blocks only once
5. ✅ Always initialize `final` fields in all constructor paths

Mastering instance flow prevents subtle initialization bugs that cause `NullPointerException` at startup. ☕✨
</Aside>
