# Java Increment & Decrement Operators

```text
++  → increment by 1
--  → decrement by 1
```

---

## 🔄 Pre vs Post

```text
// Pre-increment — increment first, then return NEW value
++x   →   x = x + 1   →   return x   (new value)

// Post-increment — return OLD value first, then increment
x++   →   temp = x    →   x = x + 1  →   return temp (old value)

// Pre-decrement
--x   →   x = x - 1   →   return x   (new value)

// Post-decrement
x--   →   temp = x    →   x = x - 1  →   return temp (old value)
```

<Code lang="java" title="Pre vs Post behavior" code={`
int x = 5;

// Pre-increment: modify FIRST, then use
int a = ++x;  // x becomes 6 FIRST → a = 6
System.out.println(x); // 6
System.out.println(a); // 6

// Post-increment: use FIRST, then modify
int b = x++;  // b gets 6 FIRST → THEN x becomes 7
System.out.println(x); // 7
System.out.println(b); // 6
`} />

---

## 📊 Expression Behavior Table

| Expression | Initial `x` | Value of `y` | Final `x` | Explanation |
|------------|-------------|--------------|-----------|-------------|
| `y = ++x`  | 10 | 11 | 11 | Pre-increment: `x` becomes 11, then assigned to `y` |
| `y = x++`  | 10 | 10 | 11 | Post-increment: `x` (10) assigned to `y`, then `x` becomes 11 |
| `y = --x`  | 10 | 9 | 9 | Pre-decrement: `x` becomes 9, then assigned to `y` |
| `y = x--`  | 10 | 10 | 9 | Post-decrement: `x` (10) assigned to `y`, then `x` becomes 9 |

## ⚠️ Rules — Must Know

<Card title="Rule 1: Only for Variables, Not Constants" icon="error">
  Increment/decrement operators require a **modifiable reference or variable**.

  ```java
    // ✅ Valid: variable
    int x = 4;
    int y = ++x;
    System.out.println(y); // 5
    
    // ❌ Invalid: constant literal
    int y = ++4;  // ❌ C.E: unexpected type
                  // required: variable
                  // found: value
  ```
</Card>

<Card title="Rule 2: No Nesting Allowed" icon="error">
  You cannot nest `++` or `--` operators.

  ```java
    int x = 4;
    int y = ++(++x);  // ❌ C.E: unexpected type
                      // required: variable
                      // found: value (++x is a value, not a variable)
    // Reason: ++x evaluates to a value (int), not a variable reference.
    // You cannot apply ++ to a temporary value.
  ```
</Card>

<Card title="Rule 3: Cannot Apply to final Variables" icon="error">
  `final` variables are immutable — incrementing them violates their contract.

  ```java
    final int x = 4;
    x++;  // ❌ C.E: cannot assign a value to final variable 'x'
    System.out.println(x);
    // Reason: x++ expands to x = x + 1, which is an assignment.
    // final variables cannot be reassigned after initialization.

    // ⚠️ BUT: const objects/arrays CAN be mutated!
    final int[] arr = {1, 2, 3, 4, 5};
    ++arr[0]; // ✅ Allowed! arr is final, but arr[0] is not — we can modify the contents of the array, just not reassign arr itself.
    System.out.println(arr[0]); // 2
  ```
</Card>

<Card title="Rule 4: Applies to All Primitives Except boolean" icon="approve-check">
  ```java
    // ✅ Valid for numeric primitives
    byte   b = 10;   b++;    // b = 11
    short  s = 10;   s++;    // s = 11
    int    i = 10;   i++;    // i = 11
    long   l = 10L;  l++;    // l = 11
    float  f = 1.5f; f++;    // f = 2.5f
    double d = 1.5;  d++;    // d = 2.5
    char   c = 'A';  c++;    // c = 'B' (65 → 66)

    // ❌ Does NOT work on
    // boolean, String, or any reference type
    boolean flag = true;
    flag++;         // ❌ C.E: operator ++ cannot be applied to boolean
    String s = "hi";
    s++;            // ❌ C.E: operator ++ cannot be applied to String
  ```
  <Aside type="tip">
    **Why?** `boolean` represents logical state, not numeric value — incrementing has no semantic meaning.
  </Aside>
</Card>

# 🔬 Critical Distinction: `b++` vs `b = b + 1`

## The Type Promotion Trap

When arithmetic operators are applied between two operands, the result type is:

```
max(int, type_of_a, type_of_b)
```

This means **`byte + byte` produces `int`**, requiring explicit cast to assign back to `byte`.

<Code lang="java" title="❌ Arithmetic assignment fails without cast" code={`
byte a = 10;
byte b = 20;
byte c = a + b;  // ❌ C.E: possible loss of precision
                 // found: int
                 // required: byte

// ✅ Fix with explicit cast:
byte c = (byte)(a + b);
`} />

<Code lang="java" title="❌ Same issue with b = b + 1" code={`
byte b = 10;
b = b + 1;  // ❌ C.E: possible loss of precision
            // found: int
            // required: byte

// ✅ Fix:
b = (byte)(b + 1);
`} />


---

## ✅ Why `b++` Works Automatically

<Code lang="java" title="Increment operators perform implicit cast" code={`
byte b = 10;
b++;  // ✅ Compiles! No explicit cast needed
System.out.println(b); // 11

// Internally, compiler transforms:
// b++  →  b = (byte)(b + 1);
// The cast to original type is inserted AUTOMATICALLY
`} />

<Aside type="tip">
**Memory Rule**:  
`b++` is **not** exactly equivalent to `b = b + 1`.  
The increment operator includes an **implicit narrowing cast** back to the variable's original type. This is a special compiler behavior for `++`/`--` only.
</Aside>

# 🎯 Interview Traps

<Card title="Trap 1: The i = i++ Paradox" icon="error">
  ```java
    int i = 10;
    i = i++;  // What is i after this?
    
    // Step-by-step evaluation:
    // 1. i++ is post-increment: 
    //    - temp = i (temp = 10)
    //    - i = i + 1 (i becomes 11)
    //    - expression value = temp (10)
    // 2. Assignment: i = 10 (overwrites the 11!)
    // increment happened and was immediately discarded

    System.out.println(i); // 10 😱 NOT 11!
    
    // ✅ To actually increment: use ++i or just i++;
    i = ++i;  // i = 11 ✅
    // OR simply:
    i++;      // i = 11 ✅
  ```
  <Aside type="tip">
    **Interview Answer**: Post-increment returns the *original* value, which then overwrites the incremented value during assignment.
  </Aside>
</Card>

<Card title="Trap 2: Mixed Pre/Post in Expression" icon="error">
  ```java
    int x = 5;
    System.out.println(x++ + ++x);
    
    // Evaluation order (left-to-right for operands):
    // 1. x++ (post): 
    //    - use current x (5) as operand value
    //    - then x becomes 6
    // 2. ++x (pre):
    //    - x becomes 7 first
    //    - then use x (7) as operand value
    // 3. Add: 5 + 7 = 12
    
    System.out.println(x); // 12
  ```
  <Aside type="tip">
    **Key Insight**: Operand evaluation is **left-to-right**, but pre/post determines *when* the increment happens relative to *using* the value.
  </Aside>
</Card>

<Card title="Trap 3: Chained Increments in Array Index" icon="error">
  ```java
    int[] arr = {10, 20, 30};
    int i = 0;
    int val = arr[i++] + arr[i];
    
    // Step 1: i++ → use i=0 for arr[0]=10, then i becomes 1
    // Step 2: arr[i] → arr[1] = 20
    // Result: 10 + 20 = 30
    // Final i = 1
    
    System.out.println(val); // 30
    System.out.println(i);   // 1
  ```
  **Pro Tip**: Avoid complex expressions with side effects. Break them into separate statements for clarity:

  ```java
    int first = arr[i++];
    int second = arr[i];
    int val = first + second;
  ```
</Card>

<Card title="Trap 4: Loop" icon="error">
  ```java
    // All four — identical loop behavior
    for (int i = 0; i < 5; i++)  { System.out.print(i + " "); } // 0 1 2 3 4
    for (int i = 0; i < 5; ++i)  { System.out.print(i + " "); } // 0 1 2 3 4
    for (int i = 5; i > 0; i--)  { System.out.print(i + " "); } // 5 4 3 2 1
    for (int i = 5; i > 0; --i)  { System.out.print(i + " "); } // 5 4 3 2 1

    // In loop UPDATE clause — pre vs post makes NO difference
    // Update clause result is DISCARDED — only side effect (increment) matters
  ```
</Card>

<Card title="Trap 5: `i++` not atomic — thread safety" icon="error">
  ```java
    static int counter = 0;

    // Two threads calling simultaneously:
    counter++;
    // NOT atomic — three steps: read, increment, write
    // Thread A reads 5, Thread B reads 5
    // Thread A writes 6, Thread B writes 6
    // counter = 6 — one increment LOST

    // Fix:
    AtomicInteger counter = new AtomicInteger(0);
    counter.incrementAndGet();  // truly atomic
  ```
</Card>

<Card title="Trap 6 — byte/short overflow — no exception" icon="error">
  ```java
    byte b = 127;   // Byte.MAX_VALUE
    b++;
    System.out.println(b);  // -128 — silent overflow, wraps around
    // No ArithmeticException — silent
    // Same as int overflow — two's complement wrap
  ```
</Card>

<Card title="Trap 7 — char increment" icon="error">
  ```java
    char c = 'Z';
    c++;
    System.out.println(c);  // '[' — next Unicode after 'Z' (90 → 91)

    // But:
    char c2 = 'Z';
    c2 = c2 + 1;    // ❌ COMPILE ERROR — c2+1 is int, not char
    c2 = (char)(c2 + 1);  // ✅ explicit cast needed
    c2++;           // ✅ compound form handles cast implicitly
  ```
</Card>

# 🔬 Bytecode Behind `x++` and `++x`

```java
int x = 5;

int a = x++;    // post-increment
int b = ++x;    // pre-increment
```

## Concept

Both operators ultimately increment `x` by `1`.

The difference is **when the value is made available to the expression**.

* `x++` → use old value, then increment
* `++x` → increment first, then use new value

---

## JVM View

The JVM stores local variables in the **Local Variable Table** and evaluates expressions using the **Operand Stack**.

### `x++` (Post-Increment)

```text
iload_1      // push current x onto operand stack
iinc 1, 1    // increment local variable slot
istore_2     // store old value into a
```

Execution:

```text
x = 5

Operand Stack: [5]
iinc => x becomes 6

a = 5
```

---

### `++x` (Pre-Increment)

```text
iinc 1, 1    // increment local variable slot
iload_1      // push updated value onto operand stack
istore_3     // store new value into b
```

Execution:

```text
x = 6

iinc => x becomes 7
Operand Stack: [7]

b = 7
```

Result:

```java
b == 7
x == 7
```

---

## The `iinc` Instruction

```text
Opcode: 0x84

Format:
iinc <slot>, <constant>
```

Example:

```text
iinc 1, 1
```

Meaning:

```java
localVariable[1] += 1;
```

Characteristics:

* Directly updates a local variable slot
* Does not use the operand stack
* More efficient than load → add → store
* Used only for local integer variables

---

## Operand Stack = Temporary Storage

The JVM does not create a Java-level temporary variable.

Instead:

```text
Local Variable Table
        ↓
     iload
        ↓
   Operand Stack
        ↓
     istore
```

The operand stack acts as the temporary storage during expression evaluation.

---

## Thread-Safety Warning ⚠️

`iinc` is a single JVM bytecode instruction, but:

```java
x++;
```

is **not thread-safe** for shared variables.

Reason:

```text
Read
Modify
Write
```

can interleave across multiple threads.

Example:

```text
Initial x = 5

Thread A reads 5
Thread B reads 5

Thread A writes 6
Thread B writes 6

Expected: 7
Actual:   6
```

This is a **race condition**.

---

## Important Distinction

### Local Variable

```java
int x = 0;
x++;
```

May use:

```text
iinc
```

### Instance Field

```java
obj.x++;
```

Typically compiles to:

```text
getfield
iconst_1
iadd
putfield
```

No `iinc` is used.

## 🧩 DSA Angle: When to Use Which

<Card title="Pattern: Loop Counters" icon="rocket">
  Post-increment is conventional in `for` loops (though functionally identical to pre-increment for primitives):
  ```java
  // Standard pattern
  for (int i = 0; i < n; i++) {  // i++ is idiomatic
      process(arr[i]);
  }
  
  // Pre-increment also works:
  for (int i = 0; i < n; ++i) {  // Same behavior for int
      process(arr[i]);
  }
  ```
  **Note**: For iterator objects (`List.iterator()`), `++it` (pre) can be marginally more efficient than `it++` (post) because post-increment may create a temporary copy. But for primitives, **no performance difference**.
</Card>
