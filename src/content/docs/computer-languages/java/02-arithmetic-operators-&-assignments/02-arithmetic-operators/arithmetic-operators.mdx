## 🔢 Rule 1: Type Promotion in Arithmetic

> When applying any arithmetic operation between two operands `a` and `b`, the result type is always:
> ```
> max(int, type_of_a, type_of_b)
> ```

This means **smaller types are promoted to `int` or larger** before the operation.

### 💻 Character Arithmetic Examples

<Code lang="java" title="❌ Arithmetic assignment fails without cast" code={`
byte a = 10;
byte b = 20;
byte c = a + b;  // ❌ C.E: possible loss of precision
                 // found: int
                 // required: byte

// ✅ Fix with explicit cast:
byte c = (byte)(a + b);
`} />

<Code lang="java" title="❌ Same issue with b = b + 1" code={`
byte b = 10;
b = b + 1;  // ❌ C.E: possible loss of precision
            // found: int
            // required: byte

// ✅ Fix:
b = (byte)(b + 1);
`} />

<Code lang="java" title="char participates as Unicode value" code={`
'a' + 'b'            // 195 (97 + 98)
'a' + 1              // 98  (97 + 1)
'a' + 1.2            // 98.2 (97.0 + 1.2)
1 + 2 + 3 + "" + 0   // 60

// To get concatenated string, ensure one operand is String:
"" + 'a' + 'b'       // "ab"
'a' + "" + 'b'       // "ab"
`} />

<Aside type="caution">
**Assignment Trap**: Because `byte + byte → int`, you cannot assign the result back to `byte` without explicit cast:
```java
byte a = 10, b = 20;
byte c = a + b;  // ❌ C.E: possible loss of precision (int → byte)
byte c = (byte)(a + b);  // ✅ Explicit cast required
```
</Aside>

## 🔥 Rule 2: Division by Zero — Integral vs Floating Point

### Integral Arithmetic (`byte`, `short`, `int`, `long`)

> No representation for infinity → **`ArithmeticException` at runtime**.

<Code lang="java" title="Integral division by zero" code={`
10 / 0);    // 💥 Runtime: ArithmeticException: / by zero
10 % 0);    // 💥 Runtime: ArithmeticException: / by zero
`} />

### Floating Point Arithmetic (`float`, `double`)

> IEEE 754 standard defines **infinity** and **NaN** → **No exception**, special values returned.

<Code lang="java" title="Floating point division by zero" code={`
10 / 0.0                          // Infinity ✅
-10 / 0.0                         // -Infinity ✅
0.0 / 0.0                         // NaN ✅
-0.0 / 0.0                        // NaN ✅

double d = 10.0 / 0.0;            // ✅ Infinity
double e = -10.0 / 0.0;           // ✅ -Infinity
double f = 0.0 / 0.0;             // ✅ NaN
double g = 10.0 % 0.0;            // ✅ NaN

Double.isInfinite(d)              // true
Double.isNaN(f)                   // true
Double.isNaN(g)                   // true

// Access via wrapper class constants:
Float.POSITIVE_INFINITY           // Infinity
Double.NEGATIVE_INFINITY          // -Infinity
Float.NaN                         // NaN
                                  ^
                                  |
javap java.lang.Integer => no POSITIVE_INFINITY or NEGATIVE_INFINITY final keyword
javap java.lang.Double => yes POSITIVE_INFINITY or NEGATIVE_INFINITY final keyword
also in float

IEEE 754 special values:
  Infinity = number too large to represent
  -Infinity = negative overflow
  NaN = Not a Number (0.0/0.0, sqrt(-1), etc.)
`} />

## 🔬 Rule 3: NaN (Not a Number) Semantics

### Integral Arithmetic

> No representation for undefined results → **`ArithmeticException`**.

<Code lang="java" title="Integral undefined operations" code={`
0 / 0                     // 💥 Runtime: ArithmeticException: / by zero
0.0 / 0.0                 // O/P => NaN
-0.0 / 0.0                // O/P => NaN

NaN is contagious:
  NaN + 5     = NaN
  NaN * 100   = NaN
  NaN == NaN  = false  ← NaN never equals anything including itself
  Double.isNaN(x)      ← only correct way to check for NaN
`} />

### Floating Point Arithmetic

> Undefined results return **`NaN`** (Not a Number) — no exception.

<Code lang="java" title="Floating point NaN examples" code={`
0.0 / 0.0                 // NaN ✅
Math.sqrt(-1)             // NaN ✅
Infinity - Infinity       // NaN ✅
`} />

### ⚠️ NaN Comparison Rules — Critical Interview Trap

> **For ANY value `x` (including `NaN` itself), comparisons with `NaN` behave unexpectedly:**

```java
10 < Float.NaN          // false
10 <= Float.NaN         // false
10 > Float.NaN          // false
10 >= Float.NaN         // false

10 == Float.NaN         // false
Float.NaN == Float.NaN  // false

10 != Float.NaN         // true
Float.NaN != Float.NaN  // true
```

<Aside type="danger">
**Interview Gold**: `NaN == NaN` is **false** in Java (and IEEE 754). Always use `Double.isNaN(x)` or `Float.isNaN(x)` to check for NaN.
</Aside>

## ⚡ Rule 4: ArithmeticException Details

<Card title="Key Facts" icon="information">
  1. ✅ It is a **`RuntimeException`** (unchecked) — not a compile-time error.
  2. ✅ Occurs **only in integral arithmetic** (`byte`, `short`, `int`, `long`).
  3. ✅ **Never occurs in floating point** (`float`, `double`) — they return `Infinity`/`NaN`.
  4. ✅ Only triggered by **`/` (division)** and **`%` (modulus)** operators.
  5. ✅ `+`, `-`, `*` never throw `ArithmeticException` (they may overflow silently).
</Card>

<Card title="Examples" icon="error">
  ```java
  // 💥 These throw ArithmeticException:
  int a = 10 / 0;    // / by zero
  int b = 10 % 0;    // / by zero
  
  // ✅ These do NOT throw (floating point):
  double c = 10.0 / 0.0;  // Infinity
  double d = 10.0 % 0.0;  // NaN
  
  // ✅ These do NOT throw (other operators):
  int max = Integer.MAX_VALUE;
  int overflow = max + 1;  // -2147483648 (silent wrap, no exception)
  ```
</Card>

## 🔬 Integer Division — Truncates Toward Zero

```java
// Positive / positive
10 / 3   →  3     (not 3.33)
7  / 2   →  3     (not 3.5)

// Negative — truncates TOWARD ZERO (not floor)
-7 / 2   →  -3    (not -4)  ← toward zero
 7 / -2  →  -3    (not -4)  ← toward zero
-7 / -2  →   3
```

> 🔑 Java integer division **truncates toward zero** — not floor. For negative numbers these differ. `Math.floorDiv(-7, 2)` gives `-4`. `-7 / 2` gives `-3`.

## 🔬 Modulo (%) Operator

```java
// Basic
10 % 3   →  1
10 % 5   →  0
10 % 10  →  0
10 % 11  →  10  (dividend < divisor → result = dividend)

// Sign rule: result sign matches DIVIDEND (left operand)
 7 %  3  →  1   (positive dividend → positive result)
-7 %  3  → -1   (negative dividend → negative result)
 7 % -3  →  1   (positive dividend → positive result — divisor sign ignored)
-7 % -3  → -1   (negative dividend → negative result)

// Floating point modulo
10.5 % 3.0  →  1.5
-10.5 % 3.0 → -1.5
```

```
Formula: a % b = a - (trunc(a / b) * b)   (where / is truncating division)

-7 % 3:
  -7 / 3 = -2 (truncated toward zero, not -3)
  -7 % 3 = -7 - (-2 * 3) = -7 + 6 = -1

Use case: checking even/odd
  n % 2 == 0  → even  (BUT: -4 % 2 == 0 ✅ still works)
  n % 2 == 1  → odd   ❌ WRONG for negatives (-3 % 2 = -1, not 1)
  n % 2 != 0  → odd   ✅ correct for all integers
```

## 🔬 Compound Assignment Operators

```java
int x = 10;

x += 5;     // x = x + 5  = 15
x -= 3;     // x = x - 3  = 12
x *= 2;     // x = x * 2  = 24
x /= 4;     // x = x / 4  = 6
x %= 4;     // x = x % 4  = 2
```

### Hidden Cast in Compound Assignment

```java
byte b = 10;
b = b + 5;          // ❌ COMPILE ERROR — b+5 is int, not byte
b += 5;             // ✅ COMPILES — compound op includes implicit cast

// Compiler expands b += 5 as:
b = (byte)(b + 5);  // implicit narrowing cast — potential data loss!

// Danger:
byte b2 = 120;
b2 += 10;           // 130 overflows byte (max 127)
System.out.println(b2); // -126 — silent overflow, no exception
```

> 🔑 Compound operators (`+=`, `-=`, etc.) include an **implicit narrowing cast**. `byte b += 200` silently overflows. `b = b + 200` at least gives a compile error forcing you to acknowledge the cast.

## 🎯 Common Traps & Solutions

<Card title="Trap 1: Integer Division" icon="error">
  ```java
    int a = 7, b = 2;
    a / b                   // 3  NOT 3.5! 😱
    
    // ✅ Fix: Cast at least one operand to floating point
    (double) a / b          // 3.5 ✅
    a / (double) b          // 3.5 ✅
    1.0 * a / b             // 3.5 ✅
  ```
  **Rule**: If either operand is `float`/`double`, result is floating point.
</Card>

<Card title="Trap 2: Silent Integer Overflow" icon="error">
  ```java
    int max = Integer.MAX_VALUE;  // 2147483647
    System.out.println(max + 1);  // -2147483648 😱 wraps around silently!
    
    // ✅ Fix: Use long for large calculations
    long safe = (long) max + 1;   // 2147483648 ✅
    
    // ✅ Or use Math.addExact() to throw on overflow (Java 8+)
    try {
        int result = Math.addExact(max, 1);  // 💥 ArithmeticException
    } catch (ArithmeticException e) {
        System.out.println("Overflow detected!");
    }
  ```
</Card>

## 🧩 DSA Angle: Arithmetic in Algorithms

<Card title="Pattern: Safe Midpoint Calculation" icon="shield">
  Avoid overflow in binary search:
  ```java
    // ❌ Dangerous — can overflow:
    int mid = (low + high) / 2;
    
    // ✅ Safe — no overflow risk:
    int mid = low + (high - low) / 2;
    
    // ✅ Also safe (Java 8+):
    int mid = (low + high) >>> 1;  // unsigned right shift
  ```
</Card>

<Card title="Pattern: Modulus for Cyclic Indexing" icon="rocket">
  Use `%` for circular buffer/array access:
  ```java
    // Rotate array index safely:
    int next = (current + 1) % arr.length;  // wraps to 0 at end
    int prev = (current - 1 + arr.length) % arr.length;  // handles negative
    
    // Hash table indexing:
    int index = Math.abs(key.hashCode()) % tableSize;
  ```
</Card>

<Card title="Pattern: Detect Overflow in Competitive Coding" icon="backspace">
  When problem constraints suggest large numbers:
  ```java
    // If sum of n numbers (each ≤ 10⁹, n ≤ 10⁵) is needed:
    // Max sum = 10⁹ × 10⁵ = 10¹⁴ → exceeds int (2×10⁹)
    
    // ✅ Always use long for accumulators:
    long sum = 0;
    for (int val : arr) {
        sum += val;  // safe up to ~9×10¹⁸
    }
  ```
</Card>

<Card title="Underlying primitive: ALU operations + IEEE 754 + two's complement">
  ```java
    JVM arithmetic bytecodes:
      iadd, isub, imul, idiv, irem   ← int operations
      ladd, lsub, lmul, ldiv, lrem   ← long operations
      fadd, fsub, fmul, fdiv, frem   ← float operations
      dadd, dsub, dmul, ddiv, drem   ← double operations

    int division (idiv):
      Maps directly to CPU IDIV instruction
      Truncates toward zero — hardware behavior
      Throws ArithmeticException if divisor = 0
      (CPU raises divide-by-zero interrupt → JVM converts to exception)

    float division (fdiv):
      Maps to CPU FDIV instruction (IEEE 754)
      Produces Infinity / NaN for special cases
      CPU never raises interrupt for float division
      → no exception in JVM

    Overflow behavior:
      iadd overflow → CPU sets overflow flag → JVM ignores it
      Result wraps via two's complement
      No signal, no exception — JVM spec intentional

    Math.addExact():
      iadd → check overflow flag explicitly → throw if set
      JDK implementation uses HotSpot intrinsic
      Compiled to: add + jo (jump on overflow) instruction
  ```
</Card>
