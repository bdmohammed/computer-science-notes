## 🔢 Varargs (Variable Arguments) in Java — Complete Guide

> Java 1.5+ **Varargs** allows a method to accept **zero or more arguments** of the same type — without passing an array explicitly.

---

## 📌 Syntax

<Code lang="java" title="Without vs. With Varargs" code={`
// Without varargs — ugly, multiple overloads needed
void sum(int a) { }
void sum(int a, int b) { }
void sum(int a, int b, int c) { }  // 😩 never ending

// With varargs — one method handles all! ✅
void sum(int... nums) { }   // 0, 1, 2, 3... any number of ints!
`} />

| Feature | Detail |
|---------|--------|
| **Symbol** | Three dots `...` (ellipsis) |
| **Type Meaning** | `int...` = "an array of ints" (`int[]`) |
| **Internal Representation** | Compiler converts to array automatically |

## 🔬 In-Depth — How Varargs Works Under the Hood

Varargs are **Syntactic Sugar**. The compiler converts them into an **Array**.

<Code lang="java" title="Varargs = Array internally" code={`
void sum(int... nums) {
    System.out.println(nums.getClass().getName()); // [I  (int array!)
    System.out.println(nums.length);
    // 'nums' behaves exactly like int[] inside method
}`} />

## 🧱 What Compiler Does
```java
> 🔑 Varargs parameter is **always an array** inside the method. Compiler converts the call-site arguments into an array. Passing zero args = empty array (`length == 0`), NOT `null`.
```

```java
// What you write:
void log(String level, String... messages) {
    for (String msg : messages) {
        System.out.println("[" + level + "] " + msg);
    }
}

log("INFO", "started", "ready", "listening");
```

```java
What compiler generates at call site:
  log("INFO", new String[]{"started", "ready", "listening"});

What compiler generates for method signature:
  void log(String level, String[] messages)
  // varargs = syntactic sugar for array parameter
  // difference: varargs allows flexible call-site syntax

Bytecode:
  Method descriptor: (Ljava/lang/String;[Ljava/lang/String;)V
  ACC_VARARGS flag set on method in .class file
  Call site: creates new String[] on heap before invocation
```

```java
Call site cost:
  log("a", "b", "c")
  → new String[]{"a", "b", "c"}  ← heap allocation every call
  → if called in hot loop: GC pressure
  → if called with 0 args: new String[0] ← still allocates (pre-Java optimization)
```

> 🔑 Every varargs call with inline arguments = **new array allocated on heap**. In hot paths (tight loops, high-throughput), this causes measurable GC pressure.

```java
void process(int... numbers) {

    // numbers is int[] — all array operations work
    System.out.println(numbers.length);         // number of args passed
    System.out.println(Arrays.toString(numbers));

    // Null check — caller can pass null explicitly
    if (numbers == null) {
        throw new IllegalArgumentException("numbers must not be null");
    }

    // Empty check — caller passed zero args
    if (numbers.length == 0) {
        return;
    }

    // Iterate
    for (int n : numbers) {
        System.out.println(n);
    }

    // Index access
    int first = numbers[0];
    int last  = numbers[numbers.length - 1];
}
```

## ⚠️ Rules — Must Know

### Rule 1 — Varargs Must Be LAST Parameter

<Code lang="java" title="✅ Valid — varargs last" code={`
void show(String name, int... scores) { }
void show(int a, String b, double... vals) { }
`} />

<Code lang="java" title="❌ Invalid — varargs not last" code={`
void show(int... scores, String name) { }  // ❌ C.E: varargs must be last
void show(int... nums, String msg) { }      // ❌ C.E: same reason
`} />

### Rule 2 — Only ONE Varargs Per Method

<Code lang="java" title="❌ Multiple varargs not allowed" code={`
void show(int... a, int... b) { }  // ❌ C.E: only one varargs allowed per method
`} />

### Rule 3 — Varargs vs Array Parameter: Duplicate Signature

<Code lang="java" title="❌ Cannot overload varargs and array" code={`
// These TWO cause COMPILE ERROR — seen as same signature!
void sum(int[] nums) { }
void sum(int... nums) { }
// ❌ Duplicate method sum(int[]) in same class!

// Compiler treats int... and int[] as IDENTICAL signatures
`} />

### Rule 4 — Mixing Varargs with General Parameters

<Code lang="java" title="✅ Valid combinations" code={`
void methodOne(int a, int... b) { }           // ✅ valid
void methodOne(String s, int... x) { }        // ✅ valid
void methodOne(int a, String b, double... d) { } // ✅ valid
`} />

### Rule 5 — Varargs Get Lowest Priority in Overloading

Varargs methods are chosen **only if no other method matches** — like a `default` case in `switch`.

<Code lang="java" title="Overloading priority demonstration" code={`class Test {
    public static void methodOne(int i) {
        System.out.println("general method");
    }
    public static void methodOne(int... i) {
        System.out.println("var-arg method");
    }
    public static void main(String[] args) {
        methodOne();          // var-arg method (no exact match)
        methodOne(10, 20);    // var-arg method (no exact match)
        methodOne(10);        // general method (exact match wins!)
    }

    {/* Overload resolution priority:
  1. Exact match (no varargs, no boxing)
  2. Widening (int → long, etc.)
  3. Autoboxing
  4. Varargs  ← lowest priority — chosen only when nothing else matches

Varargs is always the LAST resort in overload resolution. */}
}`} />

### Rule 6 — Can Pass Array to Varargs Parameter

<Code lang="java" title="✅ Array argument accepted" code={`
class Test {
    public static void methodOne(int... i) {
        System.out.println("var-arg method");
    }
    public static void main(String[] args) {
        methodOne(new int[]{10, 20, 30});  // ✅ var-arg method    }
}`} />

### Rule 7 — Cannot Declare Both `int[]` and `int...` in Same Class

<Code lang="java" title="❌ Duplicate method signature" code={`class Test {
    public void methodOne(int[] i) {}
    public int methodOne(int... i) { return 10; }  // ❌ C.E: method already defined
}`} />

### Rule 8 — Different way to declare

<Code lang="java" title="Different way to declare" code={`
    methodOne(int... i) {}
    methodOne(int ...i) {}  
    methodOne(int...i)  {}  
    methodOne(int i...) {}  // ❌ C.E
    methodOne(int. ..i) {}  // ❌ C.E    
    methodOne(int .i..) {}  // ❌ C.E
`} />

### Rule 9 — Varargs with Generics — Heap Pollution

<Code lang="java" title="Different way to declare" code={`
// ⚠️ Compiler warning: "unchecked or unsafe operations"
void dangerous(List<String>... lists) {
    Object[] array = lists;         // List<String>[] assigned to Object[]
    array[0] = List.of(42);         // Integer list stored in String[] position
                                    // No exception here — type erased at runtime

    String s = lists[0].get(0);     // ❌ ClassCastException — 42 is not String
    // Heap pollution: List<String>[] contains List<Integer>
}

// ✅ Fix: @SafeVarargs — promise to compiler: no heap pollution here
@SafeVarargs
public final <T> List<T> flatten(List<T>... lists) {
    List<T> result = new ArrayList<>();
    for (List<T> list : lists) {
        result.addAll(list);        // safe — only reads, doesn't write wrong type
    }
    return result;
}

@SafeVarargs rules:
  ├── Suppresses heap pollution warning
  ├── You PROMISE: method doesn't store non-T values into the array
  ├── Only on: static, final, or private methods (Java 7)
  │            + constructors (Java 9+)
  └── Putting it on unsafe method = suppressed warning, runtime CCE

🔑 Generic varargs always generates a compiler warning. Add @SafeVarargs only when you truly don't write to the varargs array with incompatible types. It's a promise, not a fix.
`} />

### Rule 10 — Varargs in Common JDK APIs

<Code lang="java" title="Different way to declare" code={`
// String.format
String msg = String.format("User %s has %d orders", name, count);
// signature: format(String format, Object... args)

// Arrays.asList

// signature: asList(T... a)

// List.of (Java 9+)

// signature: of(E... elements)

// signature: addAll(Collection<? super T> c, T... elements)

// PrintWriter.printf

// EnumSet.of

`} />

# 4️⃣ Overloading with Var-Args (Interview Trap) 🚨

*This is the #1 Interview Question on this topic.*

### 🧠 Method Resolution Priority

When calling a method, Java chooses in this **strict order**:

1.  **Exact Match** (Fixed arguments) ← Highest priority
2.  **Widening** (`int` → `long`)
3.  **Autoboxing** (`int` → `Integer`)
4.  **Var-Arg** (Last priority) ← Lowest

### 💻 Example: Exact Match Wins

<Code lang="java" title="Fixed method beats varargs" code={`class Test {
    void show(int a) { System.out.println("Fixed"); }
    void show(int... a) { System.out.println("Var-Arg"); }
}

// Calling
new Test().show(10); 
// Output: "Fixed" 
// ✅ Exact match wins over Var-Arg`} />

### ⚠️ Ambiguity Error: Multiple Varargs

<Code lang="java" title="❌ Ambiguous overload" code={`class Test {
    void show(int... a) { System.out.println("Int"); }
    void show(long... a) { System.out.println("Long"); }
}

// Calling
new Test().show(10); 
// ❌ Compile Error: Reference to show is ambiguous
// Java doesn't know whether to box to int[] or long[]`} />

<Aside type="danger">**Pro Tip**: Avoid overloading methods that differ only by varargs type (`int...` vs `long...`). Use distinct method names instead to prevent ambiguity. </Aside>

## 🔬 Advanced: Array of Varargs (2D Case)

<Code lang="java" title="int[]... creates 2D array internally" code={`// Note: 
// 1. methodOne(int... x) 
//    → x becomes 1D array (int[] x)
//
// 2. methodOne(int[]... x) 
//    → x becomes 2D array (int[][] x)
//    → We pass group of 1D int[] arrays

class Test {
    public static void methodOne(int[]... x) {
        for(int[] a : x) {
            System.out.println(a[0]);
        }
    }
    public static void main(String[] args) {
        int[] l = {10, 20, 30};

**🪤 Trap 1 — Passing null to varargs — ambiguous, surprising behavior**

```java
void log(String... messages) {
    System.out.println(messages == null ? "null" : messages.length);
}

log(null);              // messages = null — prints "null"
                        // null assigned to array reference directly

log((String) null);     // messages = String[]{null} — prints "1"
                        // null cast to String → wrapped in array

                        // null cast to String[] → direct null

// Prod consequence: null check missing in varargs method
// log(null) bypasses length check → NullPointerException on messages.length
```

**🪤 Trap 3 — Varargs array is NOT a copy — mutations visible to caller**

```java
void modify(String... args) {
    args[0] = "MODIFIED";           // modifies the underlying array
}

String[] original = {"hello", "world"};
modify(original);                   // passes array directly — no copy

// When passing array to varargs: NO new array created
// When passing individual args: NEW array created — caller unaffected
modify("a", "b");                   // new array — original not affected
```

**🪤 Trap 4 — Varargs in hot loop — GC pressure**

```java

void record(String eventType, Object... tags) {

    metricsSystem.record(eventType, tags);
```

**🪤 Trap 5 — `@SafeVarargs` on non-final non-static method**

```java
class Service {

    @SafeVarargs
    public <T> List<T> combine(List<T>... lists) { }
```

**Underlying primitive: Array allocation + ACC_VARARGS flag in bytecode**

```
Method declaration in .class file:
  void log(String level, String... messages)

  Descriptor:  (Ljava/lang/String;[Ljava/lang/String;)V
  Flags:       ACC_VARARGS   ← marks method as varargs for reflection

  At call site — compiler generates array creation:
    log("INFO", "a", "b", "c")
    →
    aload_0                      // this
    ldc "INFO"                   // level
    iconst_3                     // array size = 3
    anewarray String             // new String[3]
    dup
    iconst_0
    ldc "a"
    aastore                      // array[0] = "a"
    dup
    iconst_1
    ldc "b"
    aastore                      // array[1] = "b"
    dup
    iconst_2
    ldc "c"
    aastore                      // array[2] = "c"
    invokevirtual log            // call with (String, String[])

  Reflection sees varargs:
    Method m = ...;
    m.isVarArgs()  → true       // reads ACC_VARARGS flag
    m.getParameterTypes()       // last type is String[]
    m.invoke(obj, "INFO", new String[]{"a","b","c"})  // must pass array
```

public class QueryBuilder {

    private final DataSource dataSource;

    // Varargs for flexible parameter binding
    public List<Map<String, Object>> query(
            String sql,
            Object... params) throws SQLException {

        // null guard — caller can accidentally pass null
        if (params == null) {
            params = new Object[0];
        }

        try (Connection conn = dataSource.getConnection();
             PreparedStatement stmt = conn.prepareStatement(sql)) {

            // Bind each parameter by position
            for (int i = 0; i < params.length; i++) {
                stmt.setObject(i + 1, params[i]);   // JDBC: 1-indexed
            }

            ResultSet rs = stmt.executeQuery();
            return toList(rs);
        }
    }

    // Varargs + generics — collect to set
    @SafeVarargs
    public final <T> Set<T> setOf(T... elements) {
        Set<T> set = new LinkedHashSet<>();
        for (T element : elements) {
            if (element != null) set.add(element);
        }
        return Collections.unmodifiableSet(set);
    }
}

<Aside type="tip">
**Best Practice**: Use varargs for methods where the number of arguments is naturally variable (logging, formatting, validation). Use explicit array parameters when the input is inherently a collection from another source (file I/O, API response, database result).

## 🔑 Quick Reference Summary

| Rule | Description | Example |
|------|-------------|---------|
| **Position** | Varargs must be last parameter | `void m(String s, int... nums)` ✅ |
| **Count** | Only one varargs per method | `void m(int... a, int... b)` ❌ |
| **Signature** | `int...` and `int[]` are identical to compiler | Cannot overload both |
| **Priority** | Varargs chosen last in overload resolution | Exact match > Widening > Autoboxing > Varargs |
| **Zero Args** | Creates empty array, not `null` | `sum()` → `nums = new int[0]` |
| **Null Arg** | Can pass `null` explicitly | `sum(null)` → `nums = null` |
| **Array Arg** | Can pass array directly | `sum(new int[]{1,2})` ✅ |

<Aside type="caution">
**Final Warning**: Never write `if (nums != null)` for varargs unless you explicitly allow `null` as a valid argument. By default, varargs create an empty array for zero arguments — `null` is a distinct, intentional case.
</Aside>
