## What is an Identifier?

**Definition:** An identifier is any name you give to something in your program.

| Used For            | Example                        | Identifier               |
| ------------------- | ------------------------------ | ------------------------ |
| Variables           | `age = 25`                     | `age`                    |
| Constants           | `MAX_SIZE = 100`               | `MAX_SIZE`               |
| Functions           | `def calculate_sum():`         | `calculate_sum`          |
| Classes             | `class BankAccount:`           | `BankAccount`            |
| Objects             | `user = User()`                | `user`                   |
| Methods             | `obj.deposit()`                | `deposit`                |
| Parameters          | `def greet(name):`             | `name`                   |
| Modules             | `import math`                  | `math`                   |
| Aliases             | `import numpy as np`           | `np`                     |
| Packages            | `from app.utils import helper` | `app`, `utils`, `helper` |
| Lists               | `numbers = []`                 | `numbers`                |
| Dictionaries        | `student = {}`                 | `student`                |
| Iterators           | `for item in items:`           | `item`, `items`          |
| Exception Variables | `except Exception as e:`       | `e`                      |
| Decorators          | `@staticmethod`                | `staticmethod`           |
| Labels              | ❌ Not supported                | —                        |
| Type Variables      | `T = TypeVar("T")`             | `T`                      |
| Private Convention  | `_hidden`                      | `_hidden`                |
| Name Mangling       | `__secret`                     | `__secret`               |



### Example Breakdown

```python
x = 10
print("Hello, World!")
```

| Identifier | Purpose  |
| ---------- | -------- |
| `x`        | variable |
| `print`    | function |

Things That Are NOT Identifiers ❌

| Thing       | Example                 |
| ----------- | ----------------------- |
| Keywords    | `if`, `class`, `return` |
| Operators   | `+`, `*`, `=`           |
| Literals    | `10`, `"hello"`         |
| Punctuation | `;`, `{}`, `()`         |

<Aside type="tip" title="Remember">
**Identifier = Just a NAME**  
But the compiler treats it as a **MEMORY REFERENCE**.
</Aside>

## The 6 Golden Rules ⭐

### Rule 1 — Allowed Characters

Only these types are allowed:
```
Letters     : a–z, A–Z
Digits      : 0–9
Underscore  : _
```

<Aside type="caution">
Using anything else (`Special Keyword ($, #, @, %)`, `Contain spaces`, `Contain operators`, `Reserved keyword`, `boolean literal`, `Null literal`) → **Syntax error**
</Aside>

```python
✅ total_number
❌ Total#         // C.E.
```

---

### Rule 2 — Starting Character

Cannot start with a digit (`0–9`).

Python identifiers can start with:
- ✅
    - letter
    - _
    - Unicode letter (e.g. Arabic, Hindi scripts — yes, really!)
- ❌
    - digit

```python
✅ ABC123   // Valid → treated as identifier
❌ 123ABC   // Invalid → treated as a number

# Unicode letter (e.g. Arabic, Hindi scripts — yes, CPython uses unicodedata.category() to validate each character. Category Lu, Ll, Lt, Lm, Lo, Nl → allowed as start. Nd, Pc, Mn, Mc → allowed after first char. 
# Trap: Unicode identifiers compile fine but destroy team readability and break many linters/tools. Never use in production.)
```

---

### Rule 3 — Case Sensitivity

Python is **case sensitive**.

```python
abc ≠ ABC ≠ Abc

int number = 10;   // different from →
int Number = 20;
```

---

### Rule 4 — Length Limit

Technically **no limit**, but keep it readable.

```python
numberOfStudents                            // ✅ Good
n                                           // ❌ Too vague
numberOfStudentsInEngineeringDepartment2024 // ❌ Too long
```

<Aside type="tip">
Best practice: keep identifiers **under 15 characters**.
</Aside>

---

### Rule 5 — Reserved Words

Cannot use Python **keywords** as identifiers.

```python
❌ int if = 10;  // invalid
```

---

### Rule 6 — Predefined Class Names

You **can** use predefined class names as identifiers — but avoid it.

```python
✅  String = 10;  // compiles, outputs 10
⚠️  Legal but bad practice — very confusing
```

## Special Characters Deep Dive

### 🔍 Keywords vs Identifiers vs Builtins
```
┌─────────────────────────────────────────────────┐
│               Python Names                      │
│                                                 │
│  ┌──────────────┐  ┌──────────────────────────┐ │
│  │   KEYWORDS   │  │      IDENTIFIERS         │ │
│  │  (reserved)  │  │   (you define these)     │ │
│  │              │  │                          │ │
│  │  for, while  │  │  my_var, UserClass       │ │
│  │  def, class  │  │  get_data, MAX_SIZE      │ │
│  │  if, import  │  │                          │ │
│  └──────────────┘  └──────────────────────────┘ │
│                                                 │
│  ┌──────────────────────────────────────────┐   │
│  │             BUILTINS                     │   │
│  │  (identifiers but pre-bound by Python)  │   │
│  │                                          │   │
│  │  print, len, list, dict, int, type       │   │
│  └──────────────────────────────────────────┘   │
└─────────────────────────────────────────────────┘

Builtins are just identifiers pre-bound in builtins module. You CAN rebind them. That's the trap.
```

---

### Trap 2: Shadowing builtins silently:
```python
# Somewhere in a 2000-line codebase
list = [1, 2, 3]          # you just destroyed built-in list

# 500 lines later, different function
def process(data):
    return list(data)     # 💥 TypeError: 'list' object is not callable

# No warning. No error at assignment. Blows up at call site — possibly in production, in a completely different function.

# Same trap with:
id = 101          # shadows built-in id()
type = "admin"    # shadows built-in type()
input = "data"    # shadows built-in input()
max = 0           # shadows built-in max()

# How to detect:
import builtins
print(dir(builtins))   # full list of what you should NEVER use as identifiers


```

---

### Trap 3: 🔒 Name Mangling (__double_leading) — Internals
```python
class BankAccount:
    def __init__(self):
        self.__balance = 1000    # becomes _BankAccount__balance

acc = BankAccount()
acc.__balance          # ❌ AttributeError
acc._BankAccount__balance  # ✅ still accessible — NOT true private

# Python rewrites __name to _ClassName__name at compile time. Not runtime. It's a compile-time rename, not access control.
```

## Naming Conventions

> Not enforced by the compiler — but **mandatory in real-world SDE work**.

| Used For                        | Convention                   | Example              |
| ------------------------------- | ---------------------------- | -------------------- |
| Variables                       | `snake_case`                 | `user_age`           |
| Functions                       | `snake_case`                 | `calculate_salary()` |
| Classes                         | `PascalCase`                 | `BankAccount`        |
| Constants                       | `UPPER_CASE`                 | `MAX_SIZE`           |
| Modules                         | `snake_case`                 | `file_utils.py`      |
| Packages                        | `lowercase`                  | `myapp.utils`        |
| Methods                         | `snake_case`                 | `get_data()`         |
| Private Variables               | `_single_leading_underscore` | `_hidden`            |
| Strong Internal (Name Mangling) | `__double_leading`           | `__secret`           |
| Magic/Dunder Methods            | `__double_both__`            | `__init__`           |
| Boolean Variables               | `is/has/can` prefix          | `is_active`          |
| Type Variables                  | Single uppercase             | `T`                  |
| Exceptions                      | `PascalCase` + `Error`       | `ValidationError`    |
| Files                           | `snake_case.py`              | `bank_account.py`    |
| Iterators/Throwaway Variables   | `_`                          | `_`                  |

## 🏭 Production Relevance
Minifiers (esbuild, terser) rename identifiers:
```python
// Your code:
function calculateUserDiscount(user) { ... }

// After minification:
function a(b) { ... }
// Minifiers rely entirely on identifier rules to safely rename. 
// If you use eval() or with — minifiers can't rename identifiers safely
// because the name might be looked up dynamically at runtime. This is one reason eval destroys optimization.
```

# 🔬 Under the Hood — What the Compiler Does With Identifiers

---

## 🗺️ The Full Pipeline

```
Source Code (.py)
      │
      ▼
  ┌─────────────┐
  │   Tokenizer  │  ← splits "x = 42" into tokens [NAME, OP, NUMBER]
  └─────────────┘
      │
      ▼
  ┌─────────────┐
  │    Parser    │  ← builds AST (Abstract Syntax Tree)
  └─────────────┘
      │
      ▼
  ┌──────────────────┐
  │  Symbol Table    │  ← classifies every identifier: LOCAL / GLOBAL / FREE / CELL
  │  (symtable pass) │
  └──────────────────┘
      │
      ▼
  ┌─────────────────┐
  │ Code Generator   │  ← emits bytecode instructions
  └─────────────────┘
      │
      ▼
  ┌─────────────────┐
  │  PyCodeObject   │  ← the compiled result stored in .pyc
  └─────────────────┘
      │
      ▼
  ┌─────────────────┐
  │   PVM (eval)    │  ← executes bytecode, does actual name lookup at runtime
  └─────────────────┘
```

---

## 🪙 Step 1 — Tokenizer

`x = 42` becomes a flat stream of tokens:

```
NAME   'x'
OP     '='
NUMBER '42'
NEWLINE
```

The tokenizer **does not care** what `x` means. It only recognizes the shape of the text.

```python
import tokenize, io

src = "x = 42"
tokens = tokenize.generate_tokens(io.StringIO(src).readline)
for tok in tokens:
    print(tok)

# TokenInfo(type=1 (NAME),  string='x',  ...)
# TokenInfo(type=54 (OP),   string='=',  ...)
# TokenInfo(type=2 (NUMBER),string='42', ...)
```

---

## 🌳 Step 2 — AST (Abstract Syntax Tree)

Parser converts token stream → tree of nodes.

```python
import ast

src = "x = 42"
tree = ast.parse(src)
print(ast.dump(tree, indent=2))
```

```
Module(
  body=[
    Assign(
      targets=[
        Name(id='x', ctx=Store())   ← identifier 'x', being stored
      ],
      value=Constant(value=42)
    )
  ]
)
```

> Every identifier in AST is a `Name` node. The `ctx` tells the compiler **what operation** is being done:

| ctx | Meaning |
|-----|---------|
| `Store()` | `x = ...` → writing |
| `Load()` | `print(x)` → reading |
| `Del()` | `del x` → unbinding |

---

## 🗂️ Step 3 — Symbol Table (The Critical Pass)

This is where CPython **classifies every identifier** before emitting a single bytecode.

```python
import symtable

src = """
x = 10
def foo():
    y = x + 1
    def bar():
        return y
"""

table = symtable.symtable(src, "<string>", "exec")
```

Every identifier gets classified as one of:

```
┌─────────────────────────────────────────────────────────────┐
│                    SCOPE TYPES                              │
│                                                             │
│  LOCAL   → assigned inside this function                   │
│  GLOBAL  → declared with 'global' or lives in module       │
│  FREE    → used here, assigned in enclosing function        │
│  CELL    → assigned here, used by inner (nested) function   │
│  BUILTIN → not found anywhere → falls to builtins          │
└─────────────────────────────────────────────────────────────┘
```

**In the example above:**

```
module scope:  x → GLOBAL
foo scope:     y → LOCAL (also CELL — used by bar)
               x → FREE  (comes from module)
bar scope:     y → FREE  (comes from foo)
```

> This classification is **done once at compile time**. The bytecode emitted depends entirely on this classification. The PVM never re-decides scope at runtime.

---

## ⚙️ Step 4 — Code Generator → Bytecode

Different scope classifications → **different bytecode opcodes**:

```python
import dis

def foo():
    x = 10        # LOCAL
    print(x)      # LOCAL load

dis.dis(foo)
```

```
  2   LOAD_CONST     10
      STORE_FAST     'x'    ← LOCAL: stored in array by index

  3   LOAD_GLOBAL    print
      LOAD_FAST      'x'    ← LOCAL: loaded from array by index
      CALL           1
```

| Scope | Store opcode | Load opcode | Storage |
|-------|-------------|-------------|---------|
| LOCAL | `STORE_FAST` | `LOAD_FAST` | C array (fast, index-based) |
| GLOBAL | `STORE_GLOBAL` | `LOAD_GLOBAL` | dict lookup by name |
| FREE/CELL | `STORE_DEREF` | `LOAD_DEREF` | `PyCell` object on heap |
| BUILTIN | — | `LOAD_GLOBAL` → falls to builtins dict | dict lookup |

---

## 🏎️ Why `LOAD_FAST` Is Faster Than `LOAD_GLOBAL`

```
LOCAL variable lookup:
  frame->localsplus[index]   ← direct C array index. O(1), no hashing.

GLOBAL variable lookup:
  PyDict_GetItem(globals, "name")  ← hash the string, probe the dict.
```

```python
# Benchmark trick used in real prod code
import math

def slow():
    for _ in range(1_000_000):
        math.sqrt(2)          # LOAD_GLOBAL 'math' every iteration

def fast():
    sqrt = math.sqrt          # bind to local once
    for _ in range(1_000_000):
        sqrt(2)               # LOAD_FAST 'sqrt' — array index
```

> This is a real SDE optimization used in tight loops — CPython core devs do this.

## 🔬 Step 5 — PyCodeObject (What Lives in .pyc)

After compilation, every function/module becomes a `PyCodeObject`:

```python
def foo(a, b):
    x = a + b
    return x

print(foo.__code__.co_varnames)   # ('a', 'b', 'x')  ← all local names
print(foo.__code__.co_freevars)   # ()
print(foo.__code__.co_cellvars)   # ()
print(foo.__code__.co_consts)     # (None,)
print(foo.__code__.co_code)       # raw bytecode bytes
```

| Attribute | What it stores |
|-----------|---------------|
| `co_varnames` | tuple of all LOCAL identifier names |
| `co_freevars` | FREE vars (from enclosing scope) |
| `co_cellvars` | CELL vars (shared with inner function) |
| `co_names` | GLOBAL identifier names used |
| `co_consts` | literal constants (42, "hello", None) |

> Identifier names are stored as **interned strings** inside the code object. Interning = same string object reused in memory across all uses of that name.

## 🧩 Closures — CELL + FREE Under the Hood

```python
def outer():
    x = 10          # x is CELL (shared downward)
    def inner():
        return x    # x is FREE (comes from outer)
    return inner
```

```
MEMORY LAYOUT:

outer frame:
  localsplus["x"] → PyCell { ob_ref → PyLongObject(10) }
                         ▲
inner frame:              │
  freevars["x"]  ──────── ┘  (both point to same PyCell)
```

> When `outer` returns and its frame is destroyed, `x` is NOT destroyed. The `PyCell` object keeps it alive on the heap. This is how closures "capture" variables.

## 💀 Interview Trap — `UnboundLocalError` Is a Compile-Time Decision

```python
x = 10

def foo():
    print(x)    # you'd expect: reads global x
    x = 20      # but this makes x LOCAL for entire function

foo()           # 💥 UnboundLocalError: local variable 'x' referenced before assignment
```

**Why?** The compiler sees `x = 20` → marks `x` as `LOCAL` for the **entire** function. So `print(x)` emits `LOAD_FAST` (not `LOAD_GLOBAL`). At runtime, `x` hasn't been stored yet → crash.

> The decision was made at **compile time**. The error happens at **runtime**. Senior devs get confused because it looks like a runtime scoping issue — it's actually a compile-time classification.
