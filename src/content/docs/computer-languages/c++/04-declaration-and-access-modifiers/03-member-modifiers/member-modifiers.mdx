## 🔧 Member Specifiers in C++ — Complete Guide

> In C++, members (fields and methods) are controlled by **access specifiers** (`public`, `private`, `protected`) and **storage/behavior qualifiers** (`static`, `const`, `virtual`, `constexpr`, `thread_local`). Unlike Java, C++ does not have `transient`, `volatile` (in the Java sense), or `synchronized` keywords for members.

```text
C++ Member Specifiers
│
├── Access Specifiers
│   ├── public       → accessible everywhere
│   ├── protected    → accessible in class + derived classes
│   └── private      → accessible ONLY in class (DEFAULT for 'class')
│
├── Storage & Behavior
│   ├── static       → belongs to class, not instance
│   ├── const        → method doesn't modify state / field is immutable
│   ├── virtual      → enables polymorphism (dynamic dispatch)
│   ├── override     → ensures method overrides base virtual method (C++11)
│   ├── final        → prevents further overriding (C++11)
│   ├── inline       → hint for compiler to embed code (default for class methods)
│   ├── friend       → grants access to non-members
│   └── thread_local → one copy per thread (C++11)
│
└── Invalid/Rare Combinations
    ├── virtual + static    → Contradiction (polymorphism needs instance)
    ├── virtual + constructor → Constructors cannot be virtual
    └── abstract (pure virtual) + definition → Allowed in C++ (unlike Java)
```

## 🌍 Access Specifiers: public, protected, private

C++ has three access levels. There is **no package-private**. The default access for a `class` is **private**. For a `struct`, it is **public**.

<Code lang="cpp" title="Access Specifier Example" code={`
class MyClass {
public:
    int publicVar;
    void publicFunc();

protected:
    int protectedVar;
    void protectedFunc();

private: // Default for 'class'
    int privateVar;
    void privateFunc();
};

struct MyStruct {
    int x; // Public by default!
};
`} />

### ✅ Visibility Matrix

| Access From | public | protected | private |
|-------------|--------|-----------|---------|
| Same class | ✅ Yes | ✅ Yes | ✅ Yes |
| Derived class (same/diff namespace) | ✅ Yes | ✅ Yes | ❌ No |
| Other class/namespace | ✅ Yes | ❌ No | ❌ No |

<Aside type="note">
**Java vs C++**: 
- Java `default` (package-private) has no direct C++ equivalent. Use **namespaces** or **unnamed namespaces** in `.cpp` files to hide implementation details.
- C++ `protected` allows access in derived classes regardless of namespace/package.
</Aside>

## ⚡ static Members

> Belongs to the **class**, not instances. Shared across all objects.

### 🔑 static Member Rules

    public:
        static int count; // Declaration

    std::cout << Counter::count; // 2

### 🔄 Initialization Order

Static members are initialized before `main()` starts (static storage duration). Order within a translation unit is top-to-bottom. Order across translation units is **unspecified**.

<Code lang="cpp" title="Static initialization" code={`
class Demo {
public:
    static int x;
};

// Definition outside class
int Demo::x = 10; 

// Static local (Meyer's Singleton) - Thread-safe in C++11+
int& getInstance() {
    static int instance = 42; // Initialized first time control passes through
    return instance;
}
`} />

## 🔒 const Correctness

C++ uses `const` extensively to guarantee immutability. This is a key difference from Java (where `final` is used for references).

### 🔹 const Member Functions

A `const` method promises **not to modify any member variables**.

<Code lang="cpp" title="const methods" code={`
class Box {
    double width;
public:
    // ✅ Can be called on const and non-const objects
    double getWidth() const {
        // width = 10; // ❌ Error: assignment of member 'Box::width' in read-only object
        return width;
    }
    
    // ❌ Can ONLY be called on non-const objects
    void setWidth(double w) {
        width = w;
    }
};

void printBox(const Box& b) {
    b.getWidth(); // ✅ OK
    // b.setWidth(5); // ❌ Error: passing 'const Box' as 'this' argument discards qualifiers
}
`} />

### 🔹 const Member Variables

Must be initialized in the **constructor initializer list**.

<Code lang="cpp" title="const fields" code={`
class Config {
    const int maxSize;
public:
    // ✅ Must use initializer list
    Config(int size) : maxSize(size) {}
    
    // Config() { maxSize = 10; } // ❌ Error: uninitialized member 'Config::maxSize'
};
`} />

<Aside type="tip">
**Best Practice**: Mark methods as `const` whenever they don't modify state. This allows them to be called on `const` references, improving safety and API flexibility.
</Aside>

## 🎭 virtual, override, and final

C++ requires explicit `virtual` keyword for polymorphism. Java methods are virtual by default.

### 🔑 Polymorphism Rules

<CardGrid>
  <Card title="virtual enables dynamic dispatch" icon="approve-check">
```cpp
    class Base {
    public:
        virtual void show() {
            std::cout << "Base\\n";
        }
        virtual ~Base() = default; // Always virtual destructor!
    };
    
    class Derived : public Base {
    public:
        void show() override { // 'override' is optional but recommended
            std::cout << "Derived\\n";
        }
    };
    
    Base* b = new Derived();
    b->show(); // Prints "Derived"
    delete b;
```
  </Card>
  
  <Card title="override checks signature" icon="shield">
```cpp
    class Base {
    public:
        virtual void foo(int x) {}
    };
    
    class Derived : public Base {
    public:
        // void foo(double x) override; // ❌ Error: 'foo' marked 'override' but does not override
        void foo(int x) override {} // ✅ OK
    };
```
  </Card>

  <Card title="final prevents overriding" icon="error">
```cpp
    class Base {
    public:
        virtual void bar() final {}
    };
    
    class Derived : public Base {
    public:
        // void bar() override; // ❌ Error: virtual function 'bar' declared final
    };
```
  </Card>
</CardGrid>

### Pure Virtual Functions (Abstract)

C++ uses `= 0` syntax.

<Code lang="cpp" title="Abstract class" code={`
class Shape {
public:
    virtual double area() const = 0; // Pure virtual
    virtual ~Shape() = default;
};

// Shape s; // ❌ Error: cannot declare variable of abstract type

class Circle : public Shape {
    double r;
public:
    Circle(double r) : r(r) {}
    double area() const override {
        return 3.14 * r * r;
    }
};
`} />

<Aside type="note">
**C++ Specific**: A pure virtual function **can** have an implementation in C++ (though it must still be overridden in derived classes to instantiate them). Java abstract methods cannot have bodies.
</Aside>

## 🤝 friend Keyword

Grants access to `private`/`protected` members to specific functions or classes. No Java equivalent.

<Code lang="cpp" title="friend function" code={`
class Box {
    double width;
public:
    Box(double w) : width(w) {}
    
    // Friend function can access private members
    friend void printWidth(const Box& b);

void printWidth(const Box& b) {
    std::cout << "Width: " << b.width << std::endl; // ✅ Accessing private member
}
`} />

## 💨 volatile and thread_local

### volatile in C++ vs Java

- **Java `volatile`**: Guarantees visibility across threads (happens-before relationship).
- **C++ `volatile`**: Tells compiler **not to optimize** accesses (e.g., for memory-mapped I/O). It does **NOT** guarantee thread safety or atomicity.

For thread safety in C++, use `std::atomic` or `std::mutex`.

<Code lang="cpp" title="Thread safety in C++" code={`
#include <atomic>
#include <mutex>

class Counter {
    std::atomic<int> atomicCount{0}; // Lock-free atomic
    int syncCount{0};
    std::mutex mtx;
    
public:
    void incrementAtomic() {
        atomicCount++; // Thread-safe
    }
    
    void incrementSync() {
        std::lock_guard<std::mutex> lock(mtx); // Scoped lock
        syncCount++;
    }
};

// volatile example (Hardware/I/O)
volatile int* hardwareRegister = reinterpret_cast<volatile int*>(0x4000);
int val = *hardwareRegister; // Compiler won't cache this value
`} />

### thread_local

One copy of the variable per thread.

<Code lang="cpp" title="thread_local storage" code={`
void foo() {
    thread_local int counter = 0; // Each thread gets its own counter
    counter++;
    std::cout << "Thread ID: " << std::this_thread::get_id() 
              << ", Count: " << counter << std::endl;
}
`} />

    **NO**. Use the **Factory Pattern** or **Virtual Clone** idiom instead.

## 🔑 Quick Reference Summary

### Access Specifiers

| Specifier | Accessible From |
|-----------|-----------------|
| `public` | Everywhere |
| `protected` | Class + Derived Classes |
| `private` | Class Only |

### Key Qualifiers

| Qualifier | Effect |
|-----------|--------|
| `static` | One copy per class |
| `const` | Immutable / Read-only method |
| `virtual` | Dynamic dispatch (polymorphism) |
| `override` | Compile-time check for overriding |
| `final` | Prevents further overriding |
| `friend` | Grants access to private/protected |
| `inline` | Hint to embed code (reduce call overhead) |
| `thread_local` | One copy per thread |

### Thread Safety

| Java | C++ Equivalent |
|------|----------------|
| `synchronized` | `std::mutex` + `std::lock_guard` |
| `volatile` | `std::atomic` |
| `ThreadLocal` | `thread_local` keyword |

<Aside type="caution">
**Final Checklist**:
1. ✅ Always mark base destructors as `virtual`.
2. ✅ Use `const` for methods that don't modify state.
3. ✅ Use `override` in derived classes.
4. ✅ Remember: `volatile` is NOT for threading in C++.
5. ✅ Default access for `class` is `private`.
6. ✅ Use `std::atomic` for simple thread-safe counters.
</Aside>

## 📌 What Are Method-Level Modifiers?

Keywords and qualifiers applied **directly to member functions** that control behavior, access, and calling semantics.

```
Method-Level Modifiers
│
├── CV Qualifiers (on this)
│   ├── const           → method cannot modify object
│   └── volatile        → method on volatile object
│
├── Reference Qualifiers (C++11)
│   ├── &               → callable only on lvalues
│   └── &&              → callable only on rvalues
│
├── Exception Specification
│   └── noexcept        → promises no exceptions thrown
│
├── Virtual Modifiers
│   ├── virtual         → enable runtime dispatch
│   ├── override        → must override base virtual
│   ├── final           → no further override
│   └── = 0            → pure virtual (abstract)
│
├── Generation Control
│   ├── = default       → use compiler-generated version
│   └── = delete        → disable this method
│
└── Other
    ├── static          → no 'this' pointer
    ├── inline          → hint for inlining
    ├── constexpr       → compile-time evaluation
    └── explicit        → no implicit conversion (ctors)
```

## 🔷 1. `const` — Method Cannot Modify Object

```cpp
class Counter {
    int count;
public:
    void increment() { count++; }        // non-const — modifies object
    int  get() const { return count; }   // const — read only
    void reset() const { count = 0; }   // ❌ compile error — const method
};
```

### What `const` Does to `this`

```cpp
class Foo {
    void bar() const {
        // 'this' has type: const Foo*   (const method)
        // 'this' has type: Foo*         (non-const method)
    }
};

// const method guarantees:
// 1. Cannot modify any non-mutable member
// 2. Cannot call non-const methods on *this
// 3. Can be called on const objects
// 4. Cannot call on non-const objects? → NO, can be called on both
```

### Const Correctness — Must Know

```cpp
class Buffer {
    char*  data;
    size_t size;
public:
    // ✅ Two overloads — const and non-const
    char& operator[](size_t i) {              // non-const — returns modifiable ref
        return data[i];
    }
    const char& operator[](size_t i) const {  // const — returns non-modifiable ref
        return data[i];
    }
};

Buffer       b;
const Buffer cb;

b[0]  = 'A';    // ✅ calls non-const overload
cb[0] = 'A';    // ❌ calls const overload → const char& → cannot assign

// Without const overload:
const Buffer cb;
cb[0];          // ❌ compile error — no const version of operator[]
```

### Calling Rules

```
Object type     →   Can call
────────────────────────────────────────
non-const obj   →   const + non-const methods
const obj       →   ONLY const methods

void foo(const Buffer& b) {
    b.size();           // ✅ only if size() is const
    b.push_back('x');   // ❌ non-const method on const ref
}
```

## 🔷 2. `volatile` Method Qualifier

```cpp
class HardwareRegister {
    volatile int reg;
public:
    int read() volatile {      // callable on volatile object
        return reg;
    }
    void write(int v) volatile {
        reg = v;
    }
};

volatile HardwareRegister hw;
hw.read();    // ✅ volatile method called on volatile object
```

```
volatile object → can ONLY call volatile-qualified methods
non-volatile object → can call both volatile and non-volatile methods

Analogous to const:
  const obj → only const methods
  volatile obj → only volatile methods
```

> 🔑 Almost never used in application code. Relevant in embedded systems for memory-mapped I/O registers. Not a substitute for `std::atomic`.

## 🔷 3. Reference Qualifiers `&` and `&&` (C++11)

The **most underused, most interview-important** feature.

### The Problem Without Ref Qualifiers

```cpp
class String {
public:
    std::string& value() { return data_; }  // no qualifier
    std::string data_;
};

// Both of these compile — even the dangerous one:
std::string& ref = String().value();   // ❌ dangling ref — temporary destroyed
std::string& ref = str.value();        // ✅ fine — str lives on
```

### `&` Qualifier — Callable Only on Lvalues

```cpp
class String {
public:
    std::string& value() & {    // & = lvalue ref qualifier
        return data_;
    }
    std::string data_;
};

String s;
s.value();            // ✅ s is lvalue
String().value();     // ❌ compile error — temporary is rvalue
```

### `&&` Qualifier — Callable Only on Rvalues

```cpp
class String {
public:
    std::string value() && {    // && = rvalue ref qualifier
        return std::move(data_);   // safe to move — object is temporary
    }
    std::string data_;
};

String().value();     // ✅ temporary — moves data out (efficient)
String s;
s.value();            // ❌ compile error — s is lvalue
```

### Overloading on Ref Qualifiers — Production Pattern

```cpp
class Widget {
    std::vector<Data> items_;

public:
    // Called on lvalue — return reference (no copy)
    std::vector<Data>& items() & {
        return items_;
    }

    // Called on const lvalue — return const reference
    const std::vector<Data>& items() const& {
        return items_;
    }

    // Called on rvalue (temporary) — move out (no copy)
    std::vector<Data> items() && {
        return std::move(items_);
    }
};

Widget w;
auto& ref = w.items();                    // lvalue → & overload → reference
auto  vec = Widget().items();             // rvalue → && overload → moved
const Widget cw;
const auto& cref = cw.items();           // const lvalue → const& overload
```

### Real Use — Builder Pattern

```cpp
class QueryBuilder {
    std::string query_;

public:
    QueryBuilder& where(std::string cond) & {
        query_ += " WHERE " + cond;
        return *this;               // return ref — builder on lvalue
    }

    QueryBuilder where(std::string cond) && {
        query_ += " WHERE " + cond;
        return std::move(*this);    // return value — builder is temporary
    }

    std::string build() && {        // only callable on rvalue (finalize)
        return std::move(query_);
    }
};

// Safe — no dangling references
std::string q = QueryBuilder()
    .where("age > 18")             // rvalue → && overload
    .where("active = 1")           // rvalue → && overload
    .build();                       // rvalue → && overload → moves out
```

## 🔷 4. `noexcept` — Exception Specification

```cpp
class Foo {
public:
    void safe_op() noexcept {        // guaranteed not to throw
        // if exception thrown here → std::terminate() called
        // no stack unwinding
    }

    void risky_op() noexcept(false) { // may throw (default for most functions)
        throw std::runtime_error("oops");
    }

    // Conditional noexcept
    template<typename T>
    void forward_op(T&& val)
        noexcept(noexcept(inner_op(std::forward<T>(val)))) {
        inner_op(std::forward<T>(val));
    }
};
```

### Why `noexcept` Matters — STL Impact

```cpp
class MyType {
public:
    MyType(MyType&& other) noexcept { }     // ✅ noexcept move ctor
    // vs
    MyType(MyType&& other) { }              // ❌ may throw — penalty
};

std::vector<MyType> vec;
vec.push_back(MyType{});    // may trigger reallocation

// std::vector reallocation strategy:
// If move ctor is noexcept → MOVE elements (fast, O(1) per element)
// If move ctor may throw   → COPY elements (safe, but O(n))
// = your noexcept annotation directly controls vector performance
```

```
noexcept enables:
  1. Move semantics in STL containers (vs copy fallback)
  2. Compiler optimizations (no exception table generation)
  3. Smaller binary (no unwind info for noexcept functions)
  4. Stack unwinding skipped → faster path in happy case

noexcept is a PROMISE to the compiler, not the runtime:
  if you throw inside noexcept → std::terminate() — no recovery
```

### `noexcept` Operator

```cpp
std::cout << noexcept(foo());    // true if foo() is noexcept
std::cout << noexcept(1 + 2);   // true — primitive ops never throw

// Use in templates:
template<typename T>
void process(T x) noexcept(noexcept(x.compute())) {
    x.compute();
}
// process is noexcept iff x.compute() is noexcept
```

## 🔷 5. `= 0` — Pure Virtual (Abstract Method)

```cpp
class Shape {
public:
    virtual double area() const = 0;      // pure virtual — MUST override
    virtual double perimeter() const = 0;
    virtual ~Shape() { }                   // virtual destructor — not pure
};

// Shape is now ABSTRACT — cannot instantiate
Shape s;    // ❌ compile error — abstract class

class Circle : public Shape {
    double r;
public:
    double area() const override { return 3.14159 * r * r; }
    double perimeter() const override { return 2 * 3.14159 * r; }
};

Circle c;   // ✅ all pure virtuals overridden
```

### Pure Virtual With Body — Rare But Valid

```cpp
class Base {
public:
    virtual void init() = 0;    // pure virtual
};

// Provide body anyway — derived can call it explicitly
void Base::init() {
    // default implementation — must be called explicitly
}

class Derived : public Base {
    void init() override {
        Base::init();           // ✅ explicit call to pure virtual body
        // add derived behavior
    }
};
```

## 🔷 6. `= default` and `= delete`

### `= default`

```cpp
class Foo {
public:
    Foo() = default;                        // compiler generates default ctor
    Foo(const Foo&) = default;              // compiler generates copy ctor
    Foo& operator=(const Foo&) = default;   // compiler generates copy assign
    Foo(Foo&&) = default;                   // compiler generates move ctor
    Foo& operator=(Foo&&) = default;        // compiler generates move assign
    ~Foo() = default;                       // compiler generates destructor
};
```

```
Why use = default instead of just { }?

Foo() { }         → user-defined — suppresses compiler optimizations
                    NOT trivially constructible
                    NOT a POD type

Foo() = default;  → explicitly defaulted — compiler treats as if not declared
                    IS trivially constructible
                    Faster — memcpy optimization possible
                    Can be constexpr when conditions are met
```

### `= delete`

```cpp
class NonCopyable {
public:
    NonCopyable() = default;
    NonCopyable(const NonCopyable&) = delete;             // ❌ no copy
    NonCopyable& operator=(const NonCopyable&) = delete;  // ❌ no copy assign
    NonCopyable(NonCopyable&&) = default;                  // ✅ move OK
    NonCopyable& operator=(NonCopyable&&) = default;       // ✅ move OK
};

NonCopyable a;
NonCopyable b = a;            // ❌ compile error — copy deleted
NonCopyable c = std::move(a); // ✅ move works

// Delete ANY function — not just special members:
class Singleton {
public:
    static Singleton& get();
    Singleton(const Singleton&) = delete;
    void* operator new(size_t) = delete;    // prevent heap allocation
};

// Prevent implicit conversion:
void foo(int x);
void foo(double) = delete;   // calling foo(3.14) → compile error
foo(3.14);                   // ❌ deleted overload chosen — error
foo(3);                      // ✅ int overload
```

## 🔷 7. `inline` on Methods

```cpp
class Math {
public:
    // Defined inside class body → implicitly inline
    int square(int x) { return x * x; }

    // Explicitly inline — defined outside class
    inline int cube(int x);
};

inline int Math::cube(int x) {
    return x * x * x;
}
```

```
Method defined inside class body → implicitly inline
inline = hint to compiler to expand call site (may ignore)
inline = ODR relaxation — definition can appear in multiple TUs

Key difference:
  Without inline: definition in .cpp → one definition, no inlining across TUs
  With inline:    definition in header → inlinable everywhere
```

## 🔬 Under the Hood — Method Qualifiers in Assembly

### `const` Method — `this` Pointer Type

```cpp
class Foo {
    int x;
public:
    void modify() { x = 5; }          // this: Foo*
    int  read() const { return x; }   // this: const Foo*
};
```

```asm
; modify() — this is Foo* (rdi register)
modify:
    mov DWORD PTR [rdi], 5   ; write through this

; read() const — this is const Foo* (same register, compiler enforces)
read:
    mov eax, DWORD PTR [rdi] ; read through this
    ret
; No runtime difference — const is compile-time enforcement only
```

### `noexcept` — Exception Table Impact

```asm
; Without noexcept: compiler generates LSDA (Landing pad descriptors)
; for stack unwinding — adds to binary size and slight overhead

; With noexcept: no landing pad generated
; Function is smaller, exception handling code eliminated
; On exception: direct call to std::terminate (no unwinding)
```

### Ref Qualifier `&&` — How Overload Resolution Works

```
Widget().items()  → expression type = rvalue → selects && overload
w.items()         → expression type = lvalue → selects & overload
std::move(w).items() → cast to rvalue → selects && overload
```

## 🏭 Real-World Production Scenario

**`noexcept` missing → vector copies instead of moves:**

```cpp
// ❌ Prod performance bug in a game engine:
class Mesh {
    std::vector<float> vertices;  // 100K floats
public:
    Mesh(Mesh&& other) {          // move ctor — forgot noexcept
        vertices = std::move(other.vertices);
    }
};

std::vector<Mesh> meshes;
meshes.reserve(10);
meshes.push_back(Mesh{});   // ok
meshes.push_back(Mesh{});   // triggers realloc
// vector must move all Mesh objects to new memory
// but move ctor is NOT noexcept → vector COPIES instead
// each copy = 400KB memcpy for 100K floats
// 10 meshes = 4MB of unnecessary copying during realloc
// game hitches every time mesh vector grows

// ✅ Fix: one word changes behavior entirely
Mesh(Mesh&& other) noexcept {
    vertices = std::move(other.vertices);
}
// now vector moves → 3 pointer swaps → near-zero cost
```

**Ref qualifier prevents dangling reference:**

```cpp
// ❌ Without ref qualifier — compiles, runtime UB
class Config {
    std::string data_;
public:
    const std::string& data() { return data_; }
};

const std::string& ref = Config().data();  // compiles!
std::cout << ref;                          // UB — Config() destroyed

// ✅ With lvalue ref qualifier
const std::string& data() const& { return data_; }
std::string data() &&       { return std::move(data_); }

const std::string& ref = Config().data();  // ❌ compile error — saved
```

## 🎯 Interview Traps

**Trap 1:**
```cpp
class Foo {
    int x = 0;
public:
    void set(int v) const { x = v; }   // compiles?
};
```
> ❌ Compile error — `x` is not `mutable`, `set` is `const`. Cannot modify `x` in a `const` method. Add `mutable int x` or remove `const`.

**Trap 2:**
```cpp
class Foo {
public:
    void bar() & { std::cout << "lvalue"; }
    void bar() && { std::cout << "rvalue"; }
};
Foo f;
std::move(f).bar();     // which overload?
f.bar();                // which overload?
Foo().bar();            // which overload?
```
> `std::move(f).bar()` → `&&` overload ("rvalue"). `f.bar()` → `&` overload ("lvalue"). `Foo().bar()` → `&&` overload ("rvalue" — temporary).

**Trap 3:**
```cpp
class Base {
public:
    virtual void f() noexcept { }
};
class Derived : public Base {
public:
    void f() override { }    // valid override?
};
```
> ✅ **Valid** — `Derived::f` overrides `Base::f`. But `Derived::f` is NOT `noexcept`. Calling via `Base*` — exception can escape when `Derived::f` throws. **Weakening** noexcept in override is allowed but dangerous. Add `noexcept` to `Derived::f` too.

**Trap 4:**
```cpp
struct Foo {
    Foo() = default;
    Foo(int x) { }
};
// Is Foo trivially constructible?
```
> **No** — once you declare ANY user constructor, the default constructor must be `= default` explicitly. But even `= default` with another user-defined constructor means it's no longer trivially default constructible IF the `= default` is not the only constructor... Actually: `Foo() = default` with another user ctor → `Foo` is NOT trivially default constructible because presence of non-trivial user-provided `Foo(int)` changes things. This is subtle — use `std::is_trivially_default_constructible_v<Foo>` to check.

**Trap 5:**
```cpp
class Foo {
public:
    void bar() noexcept {
        throw std::runtime_error("oops");   // what happens?
    }
};
```
> `std::terminate()` is called **immediately** — no exception propagation, no stack unwinding, no catch block reached. Program dies. `noexcept` is a contract — violating it ends the program, not throws to caller.

## 📊 Method Modifier Quick Reference

| Modifier | Position | Effect |
|---|---|---|
| `const` | after params | `this` is `const T*` — read only |
| `volatile` | after params | `this` is `volatile T*` |
| `&` | after cv-qual | callable on lvalue only |
| `&&` | after cv-qual | callable on rvalue only |
| `noexcept` | after ref-qual | no exceptions — terminate if thrown |
| `override` | after noexcept | must override base virtual |
| `final` | after noexcept | no further override |
| `= 0` | replaces body | pure virtual — must override |
| `= default` | replaces body | compiler-generated implementation |
| `= delete` | replaces body | calling this is compile error |
| `virtual` | before return | runtime dispatch via vtable |
| `static` | before return | no `this` pointer |
| `inline` | before return | ODR relaxation + inlining hint |
| `constexpr` | before return | compile-time evaluation |
| `explicit` | before return | no implicit conversion (ctor/conv) |
