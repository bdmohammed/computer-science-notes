## ⚡ Short Circuit Operators in C++

```text
&&   short circuit AND (same as Java)
||   short circuit OR (same as Java)
```

> **Short circuit** means: **skip evaluating the right operand if the result is already determined by the left operand**.
> 
> ⚠️ **Critical C++ Difference**: Java throws exceptions (NPE, ArithmeticException) on errors. C++ has **undefined behavior** — no safety net!

<Code lang="cpp" title="&& — skip right if left is false (C++)" code={`
#include <iostream>

int main() {
    int x = 0;
    
    // && → if LEFT is false, RIGHT is NOT evaluated!
    if (x != 0 && 10/x > 1) {  // 10/x never runs! ✅ no crash
        std::cout << "safe\\n";
    } else {
        std::cout << "short-circuited\\n";  // This prints
    }
    
    // Because x != 0 is false, the entire && expression is false.
    // C++ skips 10/x > 1 → prevents undefined behavior!
    
    return 0;
}
`} />

<Code lang="cpp" title="|| — skip right if left is true (C++)" code={`
#include <iostream>
#include <optional>
#include <string>

int main() {
    // C++: No null for values — use std::optional for nullable patterns
    std::optional<std::string> s;  // empty optional
    
    // || → if LEFT is true, RIGHT is NOT evaluated!
    if (!s.has_value() || s->empty()) {  // s->empty() never called if !s.has_value() ✅
        std::cout << "empty or nullopt\\n";
    }
    
    // Because !s.has_value() is true, the entire || expression is true.
    // C++ skips s->empty() → prevents undefined behavior!
    
    // ✅ Modern C++: Use std::optional for safe nullable patterns
    if (s && !s->empty()) {  // s converts to bool: true if has_value
        std::cout << "Has value: " << *s << '\\n';
    }
    
    return 0;
}
`} />

<Aside type="danger">
**🔥 Critical C++ Difference from Java**:  
- Java: `obj.method()` on null → `NullPointerException` (catchable)  
- C++: Dereferencing null pointer → **undefined behavior** (may crash, corrupt memory, or "work")  

✅ **Rule**: Always check pointers/optionals **first** in `&&` expressions:
```cpp
// ✅ Safe: check first
if (ptr != nullptr && ptr->isValid()) { ... }
if (opt && opt->isValid()) { ... }  // std::optional

// ❌ Dangerous: method call first
if (ptr->isValid() && ptr != nullptr) { ... }  // 💥 UB if ptr is nullptr!
```
</Aside>

### 🧠 Evaluation Rules — Same as Java

| Operator | When is Right Operand Evaluated? |
|----------|----------------------------------|
| `x && y` | ✅ Only if `x` is **true** (if `x` is false, result is false — skip `y`) |
| `x \|\| y` | ✅ Only if `x` is **false** (if `x` is true, result is true — skip `y`) |
| `x & y` | ✅ Always — no short circuit |
| `x \| y` | ✅ Always — no short circuit |

<Code lang="cpp" title="Danger: & does NOT short circuit — C++" code={`
#include <iostream>

int main() {
    int x = 0;
    
    // & and | → BOTH sides always evaluated (no short circuit!)
    // ⚠️ Division by zero on integers = Undefined Behavior in C++!
    // if (x != 0 & 10/x > 1) {  // 💥 UB! Don't do this!
    
    // ✅ Always prefer && for boolean conditions:
    if (x != 0 && 10/x > 1) {  // Safe: 10/x skipped when x == 0
        std::cout << "safe\\n";
    }
    
    // ⚠️ C++ Gotcha: bool & bool promotes to int!
    bool a = true, b = false;
    int result = a & b;  // result is int: 0 (not bool!)
    std::cout << std::boolalpha << (result == 0) << '\\n';  // true
    
    // ✅ Prefer && for boolean logic — returns bool, short-circuits:
    bool safeResult = a && b;  // false (bool), short-circuits if a is false
    
    return 0;
}
`} />

<Aside type="caution">
**⚠️ C++ Gotcha**: `bool & bool` and `bool | bool` **promote to `int`** (0 or 1), not `bool`!

```cpp
bool a = true, b = false;
auto r1 = a & b;   // r1 is int: 0
auto r2 = a && b;  // r2 is bool: false

if (a & b) { }     // ⚠️ Works but confusing — int in boolean context
if (a && b) { }    // ✅ Clear and idiomatic — bool in boolean context
```

✅ **Rule**: Use `&&`/`||` for boolean logic; reserve `&`/`|` for bitwise operations on integers.
</Aside>

## 🔢 Side Effects & Evaluation Order — C++ Interview Trap

When operands have **side effects** (like `++x`), short circuit behavior changes the final state — same as Java, but with C++ UB considerations.

<Code lang="cpp" title="Increment operators reveal evaluation order — C++" code={`
#include <iostream>

int main() {
    // Test with different operators:
    // Condition: (++x < 10) [op] (++y > 15)
    
    // Case 1: & (always eval both) — bool promotes to int!
    {
        int x = 10, y = 15;
        // Note: & on bool returns int, so we cast result to bool for if
        if (static_cast<bool>((++x < 10) & (++y > 15))) { x++; } else { y++; }
        std::cout << "&  → x=" << x << ", y=" << y << '\\n';  // x=11, y=17
    }
    
    // Case 2: | (always eval both)
    {
        int x = 10, y = 15;
        if (static_cast<bool>((++x < 10) | (++y > 15))) { x++; } else { y++; }
        std::cout << "|  → x=" << x << ", y=" << y << '\\n';  // x=12, y=16
    }
    
    // Case 3: && (short circuit: skip right if left false)
    {
        int x = 10, y = 15;
        if ((++x < 10) && (++y > 15)) { x++; } else { y++; }
        std::cout << "&& → x=" << x << ", y=" << y << '\\n';  // x=11, y=16 (y NOT incremented in condition!)
    }
    
    // Case 4: || (short circuit: skip right if left true)
    {
        int x = 10, y = 15;
        if ((++x < 10) || (++y > 15)) { x++; } else { y++; }
        std::cout << "|| → x=" << x << ", y=" << y << '\\n';  // x=12, y=16
    }
    
    return 0;
}
`} />

### 📊 Results Summary Table — Same as Java

```text
┌──────────┬─────────┬─────────┬─────────┐
│ Operator │ Final x │ Final y │ Why?                              │
├──────────┼─────────┼─────────┼─────────────────────────────────┤
│    &     │   11    │   17    │ Both sides evaluated (bool→int)  │
│    |     │   12    │   16    │ Both sides evaluated (bool→int)  │

│   ||     │   12    │   16    │ Right evaluated (left false)     │

```

<Aside type="danger">
**🔥 Interview Trap**: Questions with `++` in conditions test your understanding of:
1. Short circuit evaluation order (same as Java)
2. When side effects occur
3. **C++ Specific**: Undefined behavior vs exceptions — `10/0` is UB, not a catchable exception!

✅ **Pro Tip**: Avoid side effects in condition expressions — extract to separate statements for clarity:
```cpp
// ❌ Hard to reason about:
if (++x < 10 && ++y > 15) { ... }

// ✅ Clear and maintainable:
++x;
++y;
if (x < 10 && y > 15) { ... }
```
</Aside>

## 🔁 Boolean Complement (`!`) Operator — C++ Same as Java

> The `!` operator **inverts a boolean value** — and **only works on boolean types** (same as Java).

<Code lang="cpp" title="Boolean NOT examples — C++" code={`
#include <iostream>

int main() {
    std::cout << std::boolalpha;
    
    std::cout << !true << '\\n';    // false
    std::cout << !false << '\\n';   // true
    
    // Chaining NOTs:
    std::cout << !!true << '\\n';   // true (double negation)
    std::cout << !!!false << '\\n'; // true (odd number of ! = invert)
    
    // ❌ Invalid on non-boolean types (same as Java):
    // std::cout << !4 << '\\n';       // ❌ Error: operand of ! must be bool or convertible
    // std::cout << !"text" << '\\n';  // ❌ Error: "text" is const char*, not bool
    
    // ✅ C++: pointers convert to bool implicitly
    int* ptr = nullptr;
    if (!ptr) { std::cout << "ptr is null\\n"; }  // !ptr = true if nullptr
    
    // ✅ C++: std::optional converts to bool
    std::optional<int> opt;
    if (!opt) { std::cout << "opt has no value\\n"; }  // !opt = true if nullopt
    
    return 0;
}
`} />

<Aside type="note">
**C++ Idiom**: `!ptr` is idiomatic for null checks (ptr converts to bool implicitly).  
✅ **Modern C++**: Prefer `if (!ptr)` over `if (ptr == nullptr)` — clearer and equally safe.  
⚠️ **Warning**: Implicit bool conversion can hide bugs — enable `-Wpointer-bool-conversion` to catch unintended conversions.
</Aside>

## 🎯 Interview Cheat Sheet — C++ Edition

<CardGrid>
  <Card title="Q: When is the right operand of && evaluated in C++?" icon="information">
    **Only if the left operand is `true`** (same as Java).  
    If left is `false`, the result is already `false` — right is skipped.  
    ✅ **C++ Specific**: Skipping prevents **undefined behavior** (not just exceptions).
  </Card>
  
  <Card title="Q: When is the right operand of || evaluated in C++?" icon="information">
    **Only if the left operand is `false`** (same as Java).  
    If left is `true`, the result is already `true` — right is skipped.
  </Card>

  <Card title="Q: Why prefer && over & for boolean conditions in C++?" icon="approve-check">
    1. ✅ **Safety**: Prevents evaluating risky expressions (nullptr dereference, division by zero → UB)  
    2. ✅ **Performance**: Skips unnecessary computation  
    3. ✅ **Type Safety**: `&&` returns `bool`; `&` on bool returns `int` (confusing!)  
    4. ✅ **Intent**: Clearly signals conditional logic, not bitwise math
  </Card>

  <Card title="Q: Can && be used with integers in C++?" icon="error">
    **NO ❌** — `&&` and `||` work **only on boolean or contextually convertible to bool** (pointers, optionals).  
    For integers, use `&` and `|` for bitwise operations.  
    ✅ **C++20**: Use `requires` expressions for compile-time boolean logic on types.
  </Card>

  <Card title="Q: What is the output? `int x=10; if(++x<10 && x/0>1)` in C++?" icon="backspace">
    **"Else branch"** (assuming else prints).  
    - `++x < 10` → `11 < 10` = `false`  
    - Because left is `false`, `&&` short-circuits — `x/0>1` is **never evaluated**  
    - No undefined behavior — safe!  
    - Condition is `false` → else branch executes  
    ⚠️ **Critical**: If `&` were used instead of `&&`, `x/0` would be evaluated → **undefined behavior**!
  </Card>

  <Card title="Q: Does ! work on non-boolean types in C++?" icon="caution">
    **Only on types contextually convertible to bool**:  
    ✅ `!ptr` — pointer to bool conversion (nullptr → true)  
    ✅ `!opt` — std::optional to bool conversion (nullopt → true)  
    ❌ `!4`, `!"text"` — compile error (no bool conversion)  
    ✅ **Rule**: `!` works on bool, pointers, optionals, iterators — anything with `operator bool()` or implicit bool conversion.
  </Card>

  <Card title="Q: C++20 requires expressions and short-circuit?" icon="rocket">
  ```cpp
  #include <concepts>
  
  template<typename T>
  concept Printable = requires(T t) {
      { std::cout << t } -> std::same_as<std::ostream&>;
  };
  
  // requires expressions short-circuit: if first requirement fails, rest skipped
  template<typename T>
  concept Advanced = requires(T t) {
      { t.value() } -> std::convertible_to<int>;  // Checked first
      requires Printable<T>;                       // Only checked if first passes
      { t.print() } -> std::same_as<void>;         // Only checked if both above pass
  };
  ```
  ✅ **Interview Gold**: `requires` clauses short-circuit like `&&` — efficient compile-time logic!
  </Card>

## 🧩 DSA & Practical Patterns — C++ Edition

<CardGrid>
  <Card title="Pattern: Early Exit with Short Circuit — C++ Style" icon="rocket">
    Use `||` to skip expensive checks when a simple condition suffices:
```cpp
    bool isValid(const Input& in) {
        // Quick rejections first (cheap checks)
        if (!in.has_value() || in->isEmpty() || in->isBanned()) {
```

    Combine preconditions cleanly:
```cpp

        // All conditions must pass — && short-circuits on first failure
        if (user != nullptr 
            && user->isActive() 
            && order != nullptr 
            && order->isPaid()
            && inventory.hasStock(order->getItem())) {
            
            ship(order);  // All guards passed — safe to proceed
        }
    }
    
    // ✅ Modern C++: Use std::optional to avoid raw pointers
    void process(std::optional<User> user, std::optional<Order> order) {
        if (user && user->isActive() 
            && order && order->isPaid()
            && inventory.hasStock(order->getItem())) {
            ship(order.value());
        }
    }
    // Each check protects the next — no nested if hell!
```
  </Card>

  <Card title="Pattern: std::all_of / std::any_of for Range Short-Circuit" icon="approve-check">
    Use STL algorithms for short-circuit evaluation over ranges:
```cpp
    #include <algorithm>
    #include <vector>
    
    std::vector<int> values = {2, 4, 6, 8};
    
    // ✅ Short-circuit: stops at first false (like && chain)
    bool allEven = std::all_of(values.begin(), values.end(), 
                               [](int n) { return n % 2 == 0; });
    
    // ✅ Short-circuit: stops at first true (like || chain)
    bool hasNegative = std::any_of(values.begin(), values.end(),
                                   [](int n) { return n < 0; });
    
    // ✅ C++20 ranges: even cleaner
    #if __cplusplus >= 202002L
    #include <ranges>
    bool allEven2 = std::ranges::all_of(values, [](int n) { return n % 2 == 0; });
    #endif
    
    // ✅ Performance: O(n) worst-case, but often stops early — same as manual && chain
```
  </Card>
</CardGrid>

<Aside type="tip">
**Performance Note**: While short-circuit operators are faster when they skip work, **don't prematurely optimize**. Write clear, safe conditions first:
```cpp
// ✅ Clear and safe:
if (ptr != nullptr && ptr->isValid() && ptr->getValue() > 0) { ... }

// ❌ Over-optimized and hard to read:
if (ptr != nullptr) { 
    if (ptr->isValid()) { 
        if (ptr->getValue() > 0) { ... } 
    } 
}
```
Modern C++ compilers optimize boolean expressions well — prioritize readability, correctness, and **avoiding undefined behavior**.
</Aside>

## 🔑 Quick Reference Summary — C++ Short Circuit

| Scenario | Use `&&` / `||` | Use `&` / `|` | Why? |
|----------|----------------|---------------|------|
| Nullptr-safe method call | ✅ `ptr != nullptr && ptr->method()` | ❌ | Short circuit prevents UB |
| Bitwise flag check | ❌ | ✅ `(flags & READ_FLAG) != 0` | Need bitwise operation |
| Performance-critical condition | ✅ (if right side is expensive) | ❌ | Skip unnecessary work |
| Both sides must run (side effects) | ❌ | ✅ `log() & validate()` | Non-short-circuit ensures both execute |
| Boolean logic in `if`/`while` | ✅ Always | ❌ Rarely | Clarity, safety, correct return type (bool vs int) |
| Bit manipulation on integers | ❌ Not allowed | ✅ `x & 1`, `x \| MASK` | Only bitwise ops work on integers |
| std::optional checks | ✅ `opt && opt->isValid()` | ❌ | Short circuit + bool return type |
| Pointer null checks | ✅ `ptr && ptr->method()` | ❌ | Idiomatic C++ null check |

<Aside type="caution">
**🔥 Final Checklist for C++ Short Circuit**:
1. ✅ Use `&&`/`||` for **boolean conditions** — they're safer, faster, and return `bool` (not `int`)
2. ✅ Put **nullptr/validity checks first** to leverage short-circuit safety (prevent UB!)
3. ✅ Use `&`/`|` for **bitwise operations** on integers — not for boolean logic
4. ✅ Remember: `&`/`|` on bool **return `int`** (0 or 1), not `bool` — confusing!
5. ✅ `!` works on **bool, pointers, std::optional** — anything with bool conversion
6. ✅ Avoid side effects (`++`, method calls) in condition expressions — extract for clarity
7. ✅ **C++ Specific**: Short circuit prevents **undefined behavior**, not just exceptions
8. ✅ Enable `-Wbool-operation -Wpointer-bool-conversion` to catch type confusion
</Aside>

```text
✅ BASIC RULES:
   • && / ||: Short-circuit, return bool, only for bool/convertible types
   • & / | on bool: NO short-circuit, return int (0/1), confusing — avoid for logic!
   • & / | on int: Bitwise operations, no short-circuit
   • !: Works on bool, pointers, std::optional — anything with bool conversion

✅ SAFETY PATTERNS:
   • nullptr checks first: if (ptr && ptr->isValid()) { ... }
   • std::optional chaining: if (opt && opt->isValid()) { ... }
   • Division safety: if (divisor != 0 && dividend/divisor > x) { ... }
   • Remember: Skipping prevents UNDEFINED BEHAVIOR, not just exceptions!

✅ MODERN C++ FEATURES:
   • std::optional: Use for nullable values — converts to bool, short-circuit safe
   • std::all_of / std::any_of: Short-circuit evaluation over ranges (C++11)
   • std::ranges (C++20): Cleaner syntax for algorithm short-circuit
   • requires expressions (C++20): Compile-time short-circuit for concepts

✅ TYPE SAFETY NOTES:
   • bool && bool → bool (clear, idiomatic)
   • bool & bool → int (0 or 1) — confusing! Prefer && for logic
   • Pointers convert to bool: if (ptr) = if (ptr != nullptr)
   • std::optional converts to bool: if (opt) = if (opt.has_value())

✅ COMPILER FLAGS FOR SAFETY:
   • -Wbool-operation          — catch bool &/| confusion
   • -Wpointer-bool-conversion — catch unintended pointer→bool conversions
   • -Wlogical-not-parentheses — catch !a && b vs !(a && b) confusion
   • -Wall -Wextra             — catch all common issues

✅ DSA BEST PRACTICES:
   • Use && for guard clauses: if (ptr && ptr->valid() && ptr->ready()) { ... }
   • Use std::all_of for "all elements satisfy" with short-circuit
   • Use std::optional to avoid raw pointer null checks
   • Avoid side effects in conditions: extract ++, method calls for clarity
   • Prefer early returns over nested ifs — short-circuit helps!
```

> 3. **Type difference**: `bool & bool → int` vs `bool && bool → bool` — prefer `&&` for clarity  
> 4. **Modern C++ patterns**: `std::optional`, `std::all_of`, `requires` expressions for safe, expressive short-circuit logic

## 📌 What Is Short-Circuit Evaluation?

```
If the result of a logical expression can be determined
from the LEFT operand alone,
the RIGHT operand is NEVER evaluated.
```

| Operator | Rule | Right side skipped when |
|---|---|---|
| `&&` (AND) | both must be true | left is `false` |
| `\|\|` (OR) | at least one must be true | left is `true` |

```cpp
false && anything    // → false — right never evaluated
true  || anything    // → true  — right never evaluated

true  && anything    // → evaluate right (result depends on it)
false || anything    // → evaluate right (result depends on it)
```

---

## 🔢 Logical AND `&&`

```cpp
bool result = A && B;

Evaluation:
  1. Evaluate A
  2. If A == false → result = false, B is NEVER evaluated
  3. If A == true  → evaluate B, result = B
```

```cpp
int x = 0;
bool r = (x != 0) && (10 / x > 2);   // ✅ safe
//                        ↑
//        never reached — x != 0 is false, short-circuits
//        without short-circuit: 10/0 = UB (division by zero)
```

---

## 🔌 Logical OR `||`

```cpp
bool result = A || B;

Evaluation:
  1. Evaluate A
  2. If A == true  → result = true, B is NEVER evaluated
  3. If A == false → evaluate B, result = B
```

```cpp
std::string s = cache_lookup(key);
bool found = !s.empty() || (s = db_lookup(key), !s.empty());
//                              ↑
//                    expensive DB call — only runs if cache missed
```

## 📐 Sequencing — The Formal Guarantee

> C++ standard mandates: the left operand of `&&` and `||` is **sequenced before** the right operand.

```cpp
// This is defined behavior — not UB:
int i = 0;
bool r = (++i > 0) && (++i > 1);
//        ↑ evaluates first     ↑ evaluates second
// i=1 after left, i=2 after right if left was true
// safe — sequenced
```

```
Sequence point at && and ||:
  Left operand fully evaluated (all side effects complete)
  THEN decision made
  THEN right operand evaluated (if needed)

This is STRONGER than most binary operators.
a + b has no sequencing between a and b.
a && b guarantees left-before-right.
```

## 🔬 Under the Hood — Assembly

```cpp
bool a = foo();
bool b = bar();
bool r = a && b;
```

```asm
; x86-64 — short-circuit via conditional jump

call foo          ; evaluate a
test al, al       ; test if a == 0 (false)
jz   .false       ; if zero (false) → jump to false, skip bar()

call bar          ; evaluate b (only if a was true)
test al, al
jz   .false

.true:
  mov al, 1
  jmp .done

.false:
  mov al, 0

.done:
```

```
Short-circuit IS a conditional branch at the machine level.
The right operand's code is simply never reached when skipped.
No special instruction — just a jump over the right operand's code.
```

### Branch Prediction Impact

```
&&/|| generate conditional branches.
CPU branch predictor tries to predict which path.

Predictable pattern (same result each time):
  → near-zero cost (branch predicted correctly)

Unpredictable pattern (random result each time):
  → ~15 cycle branch misprediction penalty each time

For SIMD/tight loops: sometimes branchless code is faster
  → use bitwise & and | instead (no short-circuit, no branch)
```

## 🔑 The Null Pointer Guard — Most Common Use

```cpp
// ✅ Classic null-check pattern
Node* p = get_node();
if (p != nullptr && p->value > 0) {
    // p->value safe — p is guaranteed non-null here
}

// If short-circuit didn't exist:
// p->value would be evaluated even when p == nullptr
// → dereference nullptr → SIGSEGV

// Same pattern, pointer as bool:
if (p && p->value > 0) { }    // ✅ pointer → bool conversion
```

## 🔄 Side Effects in Short-Circuit — Critical

```cpp
int x = 0;

// Side effect in right operand — may or may not run
bool r = false && (x = 5, true);
std::cout << x;   // → 0 — right never evaluated, x unchanged

bool r = true && (x = 5, true);
std::cout << x;   // → 5 — right evaluated, x modified

// Function calls as side effects
bool r = false && expensive_computation();
// expensive_computation() NEVER called — real perf win

bool r = true || log_and_return_true();
// log_and_return_true() NEVER called — no log entry
// ← this is a real bug: expected logging skipped silently
```

## 🔄 Chained Short-Circuit

```cpp
// Multiple && — stops at first false
if (p != nullptr && p->next != nullptr && p->next->value > 0) {
    // safe nested dereference — each checked before use
}

// Multiple || — stops at first true
bool valid = is_cached(key)
          || is_in_memory(key)
          || load_from_disk(key);   // only if both above fail
// Ordered by cost: cheapest check first
```

## ☣️ Operator Overloading KILLS Short-Circuit

```cpp
// For user-defined types:
struct Bool {
    bool val;
    Bool operator&&(const Bool& other) { return {val && other.val}; }
    Bool operator||(const Bool& other) { return {val || other.val}; }
};

Bool a{false};
Bool b = expensive();   // ← CALLED even when a is false!

Bool r = a && b;        // ❌ NO short-circuit
                        // Both a and b fully evaluated BEFORE operator&&
                        // operator&&(a, b) — both args passed first
```

```
Short-circuit ONLY guaranteed for:
  ✅ built-in && and || on scalar types
  ❌ overloaded operator&& and operator||
     → both sides ALWAYS evaluated (function call semantics)

This is why overloading && and || is considered bad practice.
```

> 🔴 **This is a famous C++ design mistake.** The language lets you overload `&&` and `||` but cannot preserve short-circuit semantics through function calls. C++17 added `std::experimental::optional`-style operators to work around this.

```cpp
// Ternary: condition ? A : B
// Only ONE of A or B is evaluated — never both

int x = 0;
int r = (x != 0) ? (10 / x) : -1;   // ✅ safe — 10/x never reached
```

## 🔃 `&&` vs `&` / `||` vs `|` — Critical Distinction

| | `&&` / `\|\|` | `&` / `\|` |
|---|---|---|
| Short-circuit | ✅ yes | ❌ no — both sides always evaluated |
| Works on | `bool`, scalars | integers (bitwise), bool |
| Sequence guarantee | ✅ left before right | ❌ unspecified |
| Side effects in right | may be skipped | always runs |
| Performance | branch (may mispredict) | branchless (always same cost) |

```cpp
bool a = check1();
bool b = check2();   // expensive

// Short-circuit: check2() skipped if check1() false
if (a && b) { }

// No short-circuit: check2() ALWAYS runs
if (a & b)  { }     // ⚠️ valid for bool but no short-circuit
                     // used intentionally for branchless code
```

```cpp
// Branchless pattern (intentional no short-circuit):
// When branch misprediction is more expensive than the computation
bool r = is_valid(x) & (compute(x) > 0);
//                   ↑
//       bitwise AND — compute(x) always runs
//       but no branch → CPU executes both sides in parallel
//       faster when compute(x) is cheap and branch is unpredictable
```

## 🏭 Real-World Production Scenarios

### Scenario 1 — Lazy Initialization

```cpp
class Config {
    mutable std::optional<Settings> cached;

    const Settings& get() const {
        // Short-circuit: load() only called if !cached
        return (cached || (cached = load(), true), *cached);
    }
};
```

### Scenario 2 — Validation Chain

```cpp
// ❌ Without short-circuit — checks run even after failure
bool valid = validate_length(input)
           & validate_charset(input)    // runs even if length invalid
           & validate_checksum(input);  // runs even if charset invalid

// ✅ With short-circuit — fails fast, skips expensive checks
bool valid = validate_length(input)
          && validate_charset(input)    // skipped if length invalid
          && validate_checksum(input);  // skipped if charset invalid
```

### Scenario 3 — Silent Skip Bug in Logging

```cpp
// ❌ Bug: log_error has side effect — sometimes silently skipped
bool ok = result.success() || log_error(result) || retry(result);
//                                 ↑
//            skipped when success() is true
//            no log entry for successful path
//            if you wanted to always log, this is a bug

// ✅ Explicit ordering when side effects matter
bool success = result.success();
if (!success) log_error(result);
bool ok = success || retry(result);
```

### Scenario 4 — Iterator Safety

```cpp
// ✅ Safe iteration with short-circuit guard
while (it != end && *it != target) {
    ++it;
}
// if it == end first: *it never dereferenced (UB)
// short-circuit ensures end check before dereference

// ❌ Reversed — UB when it == end
while (*it != target && it != end) {
    // *it evaluated when it == end → UB
}
```

## 🎯 Interview Traps

**Trap 1:**
```cpp
int i = 0;
bool r = (i++ > 0) || (i++ > 0);
std::cout << i;   // → ?
```
> `i` starts at 0. Left `i++ > 0` → `0 > 0` = false, i becomes 1. Since false, right is evaluated: `1 > 0` = true, i becomes 2. `r = true`. `i = 2`. If left had been true, i would be 1.

**Trap 2:**
```cpp
struct Wrapper {
    bool val;
    bool operator&&(const Wrapper& o) { return val && o.val; }
};

int x = 0;
Wrapper a{false};
Wrapper b{(x = 5, true)};   // x = 5 runs?
```
> **Yes** — `x = 5` runs. `Wrapper b{...}` is constructed **before** `operator&&` is called. Both sides evaluated before the function call. `x = 5`. No short-circuit.

**Trap 3:**
```cpp
int* p = nullptr;
bool r = p || *p == 5;   // UB?
```
> ✅ **Safe**. `p` is `nullptr` → converts to `false`... wait. `nullptr` converts to `bool false`. `false ||` → evaluates right. `*p` → dereferences nullptr → **UB**. Actually wait - `p` is `nullptr`, as `bool` it's `false`. `false ||` means right IS evaluated. So `*p == 5` IS reached → UB. The guard must be `&&`, not `||`.

**Trap 4:**
```cpp
bool r = true | false;   // type of r?
```
> `true | false` = `1 | 0` = `1` (bitwise OR on promoted ints) → converted to `bool true`. But `|` is **bitwise** — both sides always evaluated, result is `int` then narrowed to `bool`. Legal but wrong tool for logical OR.

**Trap 5:**
```cpp
// Does this guarantee left-to-right?
foo() && bar() && baz()
```
> ✅ Yes — `(foo() && bar()) && baz()`. `foo()` runs first, fully. If true, `bar()` runs. If that's true, `baz()` runs. Strict left-to-right sequencing guaranteed by the standard for `&&` and `||`.
