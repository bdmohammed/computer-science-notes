## 🎭 Abstraction in C++ — Complete Guide

> **Abstraction** is the OOP principle of **hiding complex implementation details** and exposing only essential features. In C++, this is achieved primarily through **Abstract Base Classes (ABCs)** and, in modern C++ (C++20), **Concepts**.

```text
Abstraction in C++
│
├── Mechanisms
│   ├── Abstract Base Class (ABC) → Runtime polymorphism (vtable)
│   │   └── Pure Virtual Functions (= 0)
│   ├── PIMPL Idiom             → Compile-time hiding (Opaque Pointer)
│   └── C++20 Concepts          → Compile-time constraints (Static polymorphism)
│
├── Key Differences from Java
│   ├── No 'interface' keyword (use ABCs)
│   ├── Multiple inheritance supported (careful with diamonds!)
│   ├── No default methods in ABCs (until C++11/14 workarounds)
│   └── Header/Source separation aids information hiding
│
└── Related Concepts
    ├── Encapsulation (private/protected members)
    ├── Polymorphism (virtual dispatch)
    └── Dependency Injection (via pointers/references)
```

```cpp
// ❌ Without abstraction — client depends on concrete implementation
class StripePaymentProcessor {
public:
    void process(double amount) {
        // Direct Stripe API logic — hard to change, test, or extend
        connectToStripe();
        charge(amount);
    }
};

// ✅ With abstraction — client depends on contract
class PaymentMethod {
public:
    virtual ~PaymentMethod() = default; // Essential for polymorphism!
    virtual void process(double amount) = 0; // Pure virtual
};

class StripePayment : public PaymentMethod {
public:
    void process(double amount) override {
        // HOW to do it — hidden from client
        connectToStripe();
        charge(amount);
    }
};

// Client code — unchanged when adding new payment methods
class CheckoutService {
    std::unique_ptr<PaymentMethod> payment; // Depend on abstraction!
public:
    CheckoutService(std::unique_ptr<PaymentMethod> p) : payment(std::move(p)) {}
    
    void checkout(double amount) {
        payment->process(amount); // Polymorphic call
    }
};
```

<Aside type="tip">
**Key Insight**: In C++, Abstraction is not just about `virtual` functions. It's also about **Header Files**. By declaring only public methods in `.h` and hiding private data in `.cpp` (or using PIMPL), you achieve **Information Hiding** at the compilation level.
</Aside>

## 🗂️ Two Mechanisms for Abstraction in C++

> C++ uses **Abstract Base Classes** for runtime polymorphism and **Concepts** (C++20) for compile-time constraints.

### 🔑 Abstract Base Class vs Interface (ABC)

```cpp
// Abstract Base Class — IS-A + Shared Behavior
class Vehicle {
protected:
    int speed; // Shared state
public:
    virtual ~Vehicle() = default;
    
    // Concrete method
    void refuel() {
        std::cout << "Refueling...\n";
    }
    
    // Pure virtual — subclass MUST implement
    virtual void start() = 0;
};

// "Interface" — CAN-DO Capability
class Trackable {
public:
    virtual ~Trackable() = default;
    virtual Location getLocation() const = 0;
};

// Car IS-A Vehicle, CAN-DO Trackable
class Car : public Vehicle, public Trackable {
public:
    void start() override { speed = 0; std::cout << "Engine start\n"; }
    Location getLocation() const override { return gps.current(); }
};
```

#include <vector>
#include <memory>

// Interface 1
class Flyable {
public:
    virtual ~Flyable() = default;
    virtual void fly() const = 0;
};

// Interface 2
class Swimmable {
public:
    virtual ~Swimmable() = default;
    virtual void swim() const = 0;
};

// Duck implements BOTH

public:
    void fly() const override { std::cout << "Flapping wings\n"; }
    void swim() const override { std::cout << "Paddling feet\n"; }
};

// Usage
int main() {
    std::vector<std::unique_ptr<Flyable>> flyers;
    flyers.push_back(std::make_unique<Duck>());
    
    for (const auto& f : flyers) {
        f->fly(); // Polymorphic call
    }
    return 0;
}
`} />

<Aside type="note">
**Design Heuristic**:  
- Use **ABC** when classes are **related** (IS-A) and share **state**.  
- Use **Pure ABC (Interface)** when classes are **unrelated** but need the **same capability**.  
- C++ supports **Multiple Inheritance**, so a class can implement multiple interfaces safely (watch for Diamond Problem).
</Aside>

### 🎯 Rules & Pitfalls

<CardGrid>
  <Card title="Rule: Virtual Destructor is Mandatory" icon="error">
    ```cpp
    class Base {
    public:
        virtual ~Base() = default; // ✅ Essential!
        virtual void foo() = 0;
    };
    
    // If you delete a derived object via a base pointer
    // without a virtual destructor, behavior is UNDEFINED.
    // Derived destructors won't run → memory leaks!
    ```
  </Card>
  
  <Card title="Rule: Pure Virtual Syntax" icon="approve-check">
    ```cpp
    class Shape {
    public:
        virtual double area() const = 0; // Pure virtual
    };
    
    // class Circle : public Shape { }; // ❌ Error: Circle is still abstract
    
    class Circle : public Shape {
    public:
        double area() const override { return 3.14 * r * r; } // ✅ Now concrete
    };
    ```
  </Card>

  <Card title="Pitfall: Calling Virtual from Constructor" icon="caution">
    ```cpp
    class Base {
    public:
        Base() { init(); } // ❌ Dangerous!
        virtual void init() = 0;
    };
    
    class Derived : public Base {
    public:
        void init() override { /* ... */ }
    };
    
    // When Base() runs, Derived part is NOT constructed yet.
    // Calling init() will call Base::init() (if defined) or crash.
    // ✅ Fix: Use two-phase construction or factory methods.
    ```
  </Card>
</CardGrid>

## 🔌 Modern C++: Concepts (C++20)

> **Concepts** provide **compile-time abstraction**. They constrain template parameters, offering better error messages and static polymorphism (zero overhead).

<Code lang="cpp" title="C++20 Concepts" code={`
#include <concepts>
#include <iostream>

// Define a concept (constraint)
template<typename T>
concept Printable = requires(T t) {
    { std::cout << t } -> std::same_as<std::ostream&>;
};

// Use the concept in a function
void printAll(const Printable auto& item) {
    std::cout << item << std::endl;
}

// Compile-time error if type doesn't satisfy concept
// printAll(std::vector<int>{}); // Error if vector doesn't have operator<<

// Concept for sorting
template<typename T>
concept Sortable = requires(T a, T b) {
    { a < b } -> std::convertible_to<bool>;
};

template<Sortable T>
void sort(T& a, T& b) {
    if (b < a) std::swap(a, b);
}
`} />

<Aside type="tip">
**ABC vs Concepts**:
- **ABC**: Runtime polymorphism. You can store different types in a `vector<Base*>`. Cost: Vtable lookup.
- **Concepts**: Compile-time polymorphism. Types must be known at compile time. Cost: Zero overhead (inlined).
</Aside>

## 🛡️ The PIMPL Idiom (Pointer to Implementation)

> A powerful C++ technique to hide **private data members** from the header file, reducing compile-time dependencies.

<Code lang="cpp" title="PIMPL Example" code={`
// --- Widget.h ---
#include <memory>

class Widget {
public:
    Widget();
    ~Widget(); // Must be defined in .cpp
    
    void doSomething();

private:
    struct Impl; // Forward declaration
    std::unique_ptr<Impl> pImpl; // Opaque pointer
};

// --- Widget.cpp ---
#include "Widget.h"
#include <iostream>

struct Widget::Impl {
    int secretData = 42;
    void work() { std::cout << "Working\\n"; }
};

Widget::Widget() : pImpl(std::make_unique<Impl>()) {}
Widget::~Widget() = default;

void Widget::doSomething() {
    pImpl->work();
}
`} />

<CardGrid>
  <Card title="Benefits of PIMPL" icon="rocket">
    - ✅ **Binary Compatibility**: Changing private members doesn't require recompiling clients.
    - ✅ **Compile Speed**: Header includes are minimized.
    - ✅ **True Hiding**: Private members are invisible to users of the header.
  </Card>
  
  <Card title="Costs of PIMPL" icon="caution">
    - ⚠️ **Heap Allocation**: `Impl` is on the heap.
    - ⚠️ **Indirection**: Extra pointer dereference.
  </Card>
</CardGrid>

## 🔑 Quick Reference Summary

### ABC Rules

| Rule | Detail |
|------|--------|
| **Pure Virtual** | `virtual void f() = 0;` |
| **Virtual Destructor** | `virtual ~Base() = default;` |
| **Override** | Use `override` keyword in derived classes |
| **Final** | Use `final` to prevent further overriding |
| **Access** | Must be `public` to be part of the interface |

### Java vs C++ Mapping

| Java | C++ Equivalent |
|------|----------------|
| `interface` | `class` with pure virtual funcs |
| `implements` | `public Base` |
| `extends` (interface) | `public virtual Base` |
| `default` method | Regular virtual method with body |
| `instanceof` | `dynamic_cast` |

<Aside type="caution">
**Final Checklist**:
1. ✅ Always add `virtual ~Base() = default;`.
2. ✅ Use `override` in derived classes.
3. ✅ Use `virtual public` for diamond inheritance.
4. ✅ Prefer **C++20 Concepts** for generic code (zero overhead).
5. ✅ Avoid data members in pure interfaces.
6. ✅ Remember: C++ access is **private** by default!
</Aside>

## 📌 What Is Abstraction?

**Hiding complexity behind a simple interface** — showing WHAT something does, not HOW it does it.

Abstraction = "What" not "How"

## 🧭 Abstraction vs Encapsulation vs Data Hiding

> These three are always confused. Clear them once and for all.

```
┌─────────────────────────────────────────────────────────────────────┐
│                                                                     │
│  ABSTRACTION                                                        │
│  "What does this do?"                                               │
│  Designing the interface — what operations are exposed              │
│  CONCEPT level — independent of implementation                      │
│                                                                     │
│   ┌─────────────────────────────────────────────────────────────┐  │
│   │  ENCAPSULATION                                              │  │
│   │  "Bundling data + behavior together"                        │  │
│   │  Keeping related things in one unit (class)                 │  │
│   │  STRUCTURAL level — class/struct                            │  │
│   │                                                             │  │
│   │   ┌─────────────────────────────────────────────────────┐  │  │
│   │   │  DATA HIDING                                        │  │  │
│   │   │  "Who can see this?"                                │  │  │
│   │   │  Access control — private/protected/public          │  │  │
│   │   │  VISIBILITY level — access modifiers                │  │  │
│   │   └─────────────────────────────────────────────────────┘  │  │
│   └─────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────┘
```

```cpp
class Stack {
    // DATA HIDING: internal storage is private
    std::vector<int> data_;

    // ENCAPSULATION: data + operations bundled in one class

public:
    // ABSTRACTION: "push something" — HOW is irrelevant to caller
    void push(int val) { data_.push_back(val); }
    void pop()         { data_.pop_back(); }
    int  top()  const  { return data_.back(); }
    bool empty() const { return data_.empty(); }
};
// User sees: push/pop/top/empty
// User doesn't know: vector internally, how memory grows, etc.
```

## 🔷 1. Abstract Class — Runtime Abstraction

```cpp
// The WHAT — pure interface, no HOW
class ISort {
public:
    virtual void sort(std::vector<int>& data) = 0;
    virtual std::string name() const = 0;
    virtual ~ISort() = default;
};

// Multiple HOWs — all hidden behind same interface
class QuickSort : public ISort {
public:
    void sort(std::vector<int>& data) override {
        std::sort(data.begin(), data.end());  // HOW: quicksort
    }
    std::string name() const override { return "QuickSort"; }
};

class MergeSort : public ISort {
public:
    void sort(std::vector<int>& data) override {
        // HOW: merge sort — completely different
        merge_sort_impl(data, 0, data.size() - 1);
    }
    std::string name() const override { return "MergeSort"; }
};

class RadixSort : public ISort {
public:
    void sort(std::vector<int>& data) override {
        radix_sort_impl(data);   // HOW: radix — completely different
    }
    std::string name() const override { return "RadixSort"; }
};

// User — completely decoupled from HOW
void benchmark(ISort& sorter, std::vector<int> data) {
    auto t0 = now();
    sorter.sort(data);           // WHAT: sort — doesn't know HOW
    auto t1 = now();
    std::cout << sorter.name() << ": " << (t1-t0) << "ms\n";
}
```

## 🔷 3. Template Abstraction — Compile-Time

```cpp
// ❌ Without abstraction — specific types, code duplication
int    max_int(int a, int b)       { return a > b ? a : b; }
double max_double(double a,double b){ return a > b ? a : b; }
float  max_float(float a, float b)  { return a > b ? a : b; }

// ✅ Template abstraction — same WHAT, any type
template<typename T>
T max_val(T a, T b) {
    return a > b ? a : b;    // WHAT: get the larger value
                              // HOW: comparison — but T-independent
}

max_val(3, 5);           // int
max_val(3.14, 2.71);     // double
max_val("abc"s, "xyz"s); // std::string
```

### Template = Zero-Cost Abstraction

```
max_val<int>(3, 5):
  Compiler instantiates concrete int version
  → compiles to identical assembly as max_int(3, 5)
  → ZERO overhead from the abstraction layer

max_val<double>(3.14, 2.71):
  Compiler instantiates concrete double version
  → compiles to identical assembly as max_double()

Abstraction cost: ZERO — paid at compile time, not runtime
```

## 🔷 4. Concepts (C++20) — Named Abstraction Constraints

```cpp
// Define WHAT a type must support — abstract constraint
template<typename T>
concept Sortable = requires(T container) {
    { container.begin() } -> std::random_access_iterator;
    { container.end()   } -> std::random_access_iterator;
    { container.size()  } -> std::convertible_to<std::size_t>;
};

template<typename T>
concept Numeric = std::integral<T> || std::floating_point<T>;

template<typename T>
concept Printable = requires(T t, std::ostream& os) {
    { os << t } -> std::same_as<std::ostream&>;
};

// Use abstraction — WHAT the function needs, not HOW T works
template<Sortable T>
void sort_and_print(T& container)
    requires Printable<typename T::value_type>
{
    std::sort(container.begin(), container.end());
    for (const auto& x : container)
        std::cout << x << " ";
}

sort_and_print(std::vector<int>{3,1,4,1,5});     // ✅
sort_and_print(std::list<int>{3,1,4,1,5});        // ❌ list not random-access
                                                   //    clear error at call site
```

## 🔷 6. Iterator Abstraction

Iterators abstract over **HOW a container is traversed**.

```cpp
// WHAT: traverse elements in order
// HOW: completely hidden — array? linked list? tree? hash map?

template<typename Iterator>
void print_all(Iterator begin, Iterator end) {
    for (auto it = begin; it != end; ++it)
        std::cout << *it << " ";
}

// All of these work — completely different HOW under the hood:
std::vector<int>      v = {1,2,3};  print_all(v.begin(), v.end());
std::list<int>        l = {1,2,3};  print_all(l.begin(), l.end());
std::set<int>         s = {1,2,3};  print_all(s.begin(), s.end());
int                   a[] = {1,2,3};print_all(a, a+3);

// Iterator = abstraction over traversal mechanism
// print_all doesn't know: array? linked list? tree? BST?
// print_all doesn't care: it knows WHAT (step through elements)
```

## 🔷 7. `std::function` — Callable Abstraction

```cpp
// ❌ Tied to specific callable type
void apply(void(*func)(int), int val) {
    func(val);            // only raw function pointers
}

// ✅ Abstracted — works with ANY callable
void apply(std::function<void(int)> func, int val) {
    func(val);            // WHAT: call something with int
}                         // HOW: function? lambda? functor? method?

// All of these work:
apply([](int x) { std::cout << x; }, 42);               // lambda
apply(&printf_wrapper, 42);                              // function pointer
apply(std::bind(&Logger::log, &logger, _1), 42);        // bound method
apply(Functor{}, 42);                                    // functor object
```

// std::sort — the WHAT

## 🔷 9. Zero-Cost Abstraction — C++'s Core Promise

```cpp
// High-level abstraction:
std::vector<int> v = {1, 2, 3, 4, 5};
int sum = std::accumulate(v.begin(), v.end(), 0);

// What the compiler actually generates (with -O2):
// xor eax, eax
// add eax, 1
// add eax, 2
// add eax, 3
// add eax, 4
// add eax, 5
// = 15
// The entire abstraction compiled away — direct computation

// Compare to Python:
# list = [1,2,3,4,5]
# sum(list)  → Python runtime loop, reference counting, object allocation
# NOT zero-cost — significant runtime overhead
```

```
Zero-cost abstraction principle (Bjarne Stroustrup):
"What you don't use, you don't pay for.
 What you do use, you couldn't hand-code better."

C++ abstractions that are zero-cost:
  - templates (resolved at compile time)
  - inline functions (eliminated by compiler)
  - constexpr (computed at compile time)
  - RAII destructors (same as manual free())
  - std::array (identical to C array)
  - iterators (compile to pointer arithmetic)

C++ abstractions that have SOME cost:
  - virtual functions (~2-5ns per call, prevents inlining)
  - std::function (type erasure overhead)
  - std::shared_ptr (atomic ref count)
  - exceptions (table overhead, slow throw path)
```

## 🔬 Under the Hood — Abstraction Cost

### Zero-Cost: Template vs Virtual

```cpp
// Template abstraction — zero cost
template<typename Sorter>
void do_sort(Sorter& s, std::vector<int>& v) {
    s.sort(v);    // resolved at compile time — direct call
}

// Assembly:
// call QuickSort::sort   (direct — no indirection)
// inlinable — compiler may eliminate call entirely
```

```cpp
// Virtual abstraction — small cost
void do_sort(ISort& s, std::vector<int>& v) {
    s.sort(v);    // resolved at runtime — vtable lookup
}

// Assembly:
// mov rax, [s]          ; load vptr
// call [rax + offset]   ; indirect call via vtable
// NOT inlinable
```

```
Template dispatch:  1 direct call instruction
Virtual dispatch:   1 load + 1 indirect call + prevents inlining
                  = ~2-5 ns penalty per call

For 1 million calls:
  Template: ~1ms
  Virtual:  ~3-6ms difference — matters in tight loops
```

## 🏭 Real-World Production Scenario

**Payment processor abstraction:**

```cpp
// ❌ No abstraction — tightly coupled to Stripe
class OrderService {
    StripeAPI stripe_;
public:
    bool process_payment(double amount, const CreditCard& card) {
        auto result = stripe_.charge(card.number, card.cvv,
                                     card.expiry, amount * 100);
        return result.status == "succeeded";
    }
};
// Switching to PayPal: rewrite OrderService + all tests
// Adding Stripe + PayPal: massive if-else everywhere

// ✅ Abstraction layer
class IPaymentGateway {
public:
    virtual bool charge(double amount, const PaymentMethod& method) = 0;
    virtual bool refund(const std::string& txn_id, double amount)   = 0;
    virtual std::string name() const noexcept = 0;
    virtual ~IPaymentGateway() = default;
};

class StripeGateway : public IPaymentGateway {
    StripeAPI stripe_;
public:
    bool charge(double amount, const PaymentMethod& m) override {
        return stripe_.charge(m.token, amount * 100).status == "succeeded";
    }
    bool refund(const std::string& id, double amount) override {
        return stripe_.refund(id, amount * 100).success;
    }
    std::string name() const noexcept override { return "Stripe"; }
};

class PayPalGateway : public IPaymentGateway {
    PayPalSDK paypal_;
public:
    bool charge(double amount, const PaymentMethod& m) override {
        return paypal_.execute_payment(m.token, amount).approved;
    }
    // ... refund ...
    std::string name() const noexcept override { return "PayPal"; }
};

class OrderService {
    IPaymentGateway& gateway_;    // depends on abstraction
public:
    explicit OrderService(IPaymentGateway& gw) : gateway_(gw) { }

    bool process_payment(double amount, const PaymentMethod& method) {
        return gateway_.charge(amount, method);  // WHAT — not HOW
    }
};

// Swap gateways at runtime or compile time — OrderService unchanged
StripeGateway stripe;
OrderService  orders(stripe);

// A/B test: route some users to PayPal
PayPalGateway paypal;
OrderService  orders2(paypal);

// Add new gateway: write one class, zero changes to OrderService
```

## 🎯 Interview Traps

**Trap 1:**
```
"What's the difference between abstraction and encapsulation?"
```
> Abstraction = **WHAT** — designing the interface, hiding complexity behind a name. Encapsulation = **HOW they're bundled** — putting data and behavior together in a class. You can have encapsulation without abstraction (bundled but no interface). Abstraction uses encapsulation as a tool.

**Trap 2:**
```cpp
template<typename T>
void process(T& obj) { obj.compute(); }

class Foo { public: void compute() { } };
class Bar { public: void compute() { } };

process(Foo{});   // works
process(Bar{});   // works
// Is this an abstraction?
```
> **Yes** — implicit interface via duck typing. Both `Foo` and `Bar` satisfy the implicit "has `compute()`" interface. This is **template abstraction** — the constraint exists, it's just not named. C++20 Concepts make it **explicit** (`requires { t.compute(); }`).

**Trap 3:**
```
"Is virtual dispatch a zero-cost abstraction?"
```
> **No** — virtual dispatch has measurable runtime cost (~2-5ns per call, prevents inlining, indirect branch prediction miss). Templates and constexpr functions are zero-cost. Virtual functions trade cost for runtime flexibility. Both are valid tradeoffs — context determines which to use.

**Trap 4:**
```cpp
class Animal {
public:
    virtual void speak() = 0;
    virtual ~Animal() = default;
};

// Is Animal an abstraction or just an abstract class?
```
> Both — but **not synonyms**. An **abstract class** is a C++ mechanism (has pure virtual). **Abstraction** is a design principle (hiding HOW). `Animal` is an abstraction because it defines WHAT animals do (`speak`) without specifying HOW. The pure virtual mechanism is what enforces this in C++.

**Trap 5:**
```cpp
struct Point { int x, y; };
// Does Point have abstraction?
```
> **No** — `Point` is transparent. `x` and `y` ARE the interface AND the implementation. There's no gap between WHAT and HOW. A `class Point` with `getX()`/`getY()` backed by `double x, double y` internally → yes, small abstraction (int vs double hidden). Trivial data types rarely benefit from abstraction.

| Mechanism | When Resolved | Cost | Polymorphism | Best For |
|---|---|---|---|---|
| Abstract class | Runtime | vtable overhead | Runtime | Plugin systems, DI |
| Templates | Compile time | Zero | Compile time | Generic algorithms |
| Concepts (C++20) | Compile time | Zero | Compile time | Constrained templates |
| `std::function` | Runtime | Type erasure overhead | Runtime | Callbacks, strategies |
| Iterators | Compile time | Zero | Compile time | Container traversal |
| Lambdas | Compile time | Zero (if inlined) | Compile time | Inline behavior |
