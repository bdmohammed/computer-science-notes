## 🔐 Data Hiding & Encapsulation in C++ — Complete Guide

> **Data Hiding** (Encapsulation) in C++ restricts direct access to an object's internal state. Unlike Java, C++ relies on **Access Specifiers** (`public`, `private`, `protected`) and **Header/Source separation** to achieve true information hiding.

```text
Data Hiding in C++
│
├── Core Mechanism
│   └── Access Specifiers
│       ├── private      → class/friends only (DEFAULT for 'class')
│       ├── protected    → class + derived classes
│       └── public       → everywhere
│
├── How It's Achieved
│   ├── Private member variables
│   ├── Public interface (methods)
│   ├── Const-correctness (read-only guarantees)
│   ├── Friend classes/functions (controlled breaches)
│   └── PIMPL Idiom (Opaque Pointer) → True binary-level hiding
│
├── Levels of Hiding
│   ├── Member level (private/protected)
│   ├── File level (Unnamed namespaces / static functions)
│   └── Linkage level (Internal vs External linkage)
│
└── Related Concepts
    ├── Encapsulation    (bundling data + methods)
    ├── Immutability     (const members/methods)
    └── Information Hiding (hiding implementation details via .cpp files)
```

```cpp
// ❌ Without data hiding — fragile and unsafe
struct BankAccount {
    double balance;  // Anyone can modify directly!
};

BankAccount acc;
acc.balance = -1000000;  // ❌ Invalid state — no validation!

// ✅ With data hiding — safe and maintainable
class BankAccount {
private:
    double balance;  // Hidden from outside
    
public:
    double getBalance() const { return balance; }  // Read access
    
    void deposit(double amount) {  // Controlled write access
        if (amount > 0) balance += amount;
        else throw std::invalid_argument("Amount must be positive");
    }
};
```

<Aside type="tip">
**Key Insight**: In C++, Data Hiding is not just about `private`. It's also about **compilation firewalls**. By hiding implementation details in `.cpp` files (or using PIMPL), you reduce compile-time dependencies and binary coupling.
</Aside>

## 🗂️ Access Specifiers — The Foundation

### 💻 Practical Access Control

<Code lang="cpp" title="Layered access control" code={`
#include <string>
#include <iostream>

class User {
private:
    std::string passwordHash; // 🔒 Core secret
    
    // Private helper
    bool isValidEmail(const std::string& email) const {
        return email.find('@') != std::string::npos;
    }

protected:
    std::string username;     // 🛡️ Accessible to subclasses
    void onLogin() {          // Hook for subclasses
        std::cout << "User logged in\\n";
    }

public:
    User(const std::string& user) : username(user) {}

    // 🌍 Public API
    const std::string& getUsername() const { return username; }
    
    void updateUsername(const std::string& newName) {
        if (!newName.empty()) {
            username = newName;
        }
    }
};

class Admin : public User {
public:
    Admin(const std::string& user) : User(user) {}
    
    void adminLogin() {
        // Can access protected members
        onLogin(); 
        std::cout << "Admin privileges granted for " << username << "\\n";
        
        // Cannot access private members
        // passwordHash = "..."; // ❌ Error
    }
};
`} />

**Golden Rule**: Start with **`private`**. Only expose what is absolutely necessary. This minimizes the "surface area" of your class, making refactoring safer and easier.
</Aside>

## 🔑 Getters, Setters & Const-Correctness

In C++, **Const-Correctness** is a powerful tool for encapsulation. It allows you to expose read-only access without needing explicit "getter" naming conventions if you design carefully, though getters are still common.

### 🧱 Basic Getter/Setter Pattern

<Code lang="cpp" title="Encapsulated field with validation" code={`
#include <stdexcept>
#include <string>

class Product {
private:
    std::string name;
    double price;
    
public:
    // ✅ Const Getter — promises not to modify object
    const std::string& getName() const {
        return name;
    }
    
    // ✅ Setter with validation
    void setPrice(double newPrice) {
        if (newPrice < 0) {
            throw std::invalid_argument("Price cannot be negative");
        }
        price = newPrice;
    }
    
    double getPrice() const {
        return price;
    }
};
`} />

### ⚠️ Common Pitfalls: Returning References

<CardGrid>
  <Card title="Pitfall 1: Exposing Internal State via Reference" icon="error">
```cpp
    class Team {
        std::vector<std::string> members;
    public:
        // ❌ Dangerous: Caller gets direct access to internal vector
        std::vector<std::string>& getMembers() {
            return members; 
        }
    };
    
    // Usage:
    Team team;
    team.getMembers().push_back("Hacker"); // 😱 Bypasses logic!
    
    // ✅ Safe: Return copy (for small data) or const reference (if lifetime managed)
    // Option 1: Copy
    std::vector<std::string> getMembers() const {
        return members; 
    }
    
    // Option 2: Const Reference (Read-only, but watch dangling refs)
    const std::vector<std::string>& getMembers() const {
        return members;
    }
```
  </Card>
  
  <Card title="Pitfall 2: Const Correctness Violations" icon="error">
```cpp
    class Box {
        int width;
    public:
        // ❌ Non-const method called on const object
        void setWidth(int w) { width = w; }
        
        // ✅ Const method
        int getWidth() const { return width; }
    };
    
    void printBox(const Box& b) {
        // b.setWidth(10); // ❌ Error: passing 'const Box' as 'this' discards qualifiers
        std::cout << b.getWidth(); // ✅ OK
    }
```
  </Card>
</CardGrid>

<Aside type="tip">
**Modern C++ Tip**: Prefer returning `std::string_view` (C++17) for read-only string access to avoid copies, but ensure the underlying string outlives the view.
</Aside>

## 🛡️ Advanced Encapsulation Patterns

### 🔹 The PIMPL Idiom (Pointer to Implementation)

This is the **C++ Superpower** for data hiding. It completely hides private members from the header file, reducing compile-time dependencies.

<Code lang="cpp" title="PIMPL Idiom Example" code={`
// --- Widget.h (Public Interface) ---
#include <memory>

class Widget {
public:
    Widget();
    ~Widget(); // Must be defined in .cpp if using unique_ptr with incomplete type
    
    void doSomething();

private:
    // Forward declaration only! No one knows what Impl looks like.
    struct Impl; 
    std::unique_ptr<Impl> pImpl; // Opaque pointer
};

// --- Widget.cpp (Implementation) ---
#include "Widget.h"
#include <iostream>

// Full definition hidden in .cpp
struct Widget::Impl {
    int secretData = 42;
    void work() {
        std::cout << "Working with " << secretData << "\\n";
    }
};

Widget::Widget() : pImpl(std::make_unique<Impl>()) {}
Widget::~Widget() = default; // Unique_ptr needs complete type here

void Widget::doSomething() {
    pImpl->work(); // Delegate to implementation
}
`} />

<CardGrid>
  <Card title="Benefits of PIMPL" icon="rocket">
    - ✅ **Binary Compatibility**: Changing private members doesn't require recompiling clients.
    - ✅ **Compile Speed**: Header includes are minimized.
    - ✅ **True Hiding**: Private members are invisible to users of the header.
  </Card>
  
  <Card title="Costs of PIMPL" icon="caution">
    - ⚠️ **Heap Allocation**: `Impl` is on the heap.
    - ⚠️ **Indirection**: Extra pointer dereference.
    - ⚠️ **Boilerplate**: More code to write/maintain.
  </Card>
</CardGrid>

### 🔹 Immutable Objects (Const Members)

<Code lang="cpp" title="Immutable Value Object" code={`
#include <string>

class Point {

## 🤝 Friend Keyword — Controlled Breach

C++ allows specific external functions or classes to access `private` data. Use sparingly.

<Code lang="cpp" title="Friend Function" code={`
class Box {
    double width;
public:
    Box(double w) : width(w) {}
    
    // Friend function can access private members
    friend void printWidth(const Box& b);
};

void printWidth(const Box& b) {
    // ✅ Allowed: friend accessing private member
    std::cout << "Width: " << b.width << std::endl;
}
`} />

## 🔑 Quick Reference Summary

### Access Specifiers

| Specifier | Accessible From |
|-----------|-----------------|
| `private` | Class + Friends |
| `protected` | Class + Derived Classes + Friends |
| `public` | Everywhere |

### Encapsulation Checklist

| Scenario | Recommended Approach |
|----------|---------------------|
| Simple Data Bundle | `struct` with public members |
| Invariant-heavy Object | `class` with private members + validation |
| Heavy Compile Dependencies | PIMPL Idiom |
| Read-Only Access | `const` methods / `const` references |
| Helper Functions | `private` static methods or Unnamed Namespace |

<Aside type="caution">
**Final Checklist**:
1. ✅ Default to `private`.
2. ✅ Use `const` for read-only methods.
3. ✅ Avoid returning non-const references to internal state.
4. ✅ Consider PIMPL for large libraries.
5. ✅ Use `friend` only when necessary (e.g., operator overloading).
</Aside>

## 📌 What Is Data Hiding?

Restricting **direct access to internal data** — exposing only what is necessary through a controlled interface.

```
Data Hiding ≠ Encryption
Data Hiding = Compile-time access control
             + ABI stability
             + Implementation freedom
             + Invariant enforcement
```

```
Without data hiding:           With data hiding:
┌────────────────────┐         ┌────────────────────┐
│ BankAccount        │         │ BankAccount        │
│  balance = 1000   │◄─anyone  │  [balance hidden]  │
│  overdraft = -500 │          │                    │
│  pin = 1234       │          │  deposit()  ───►   │
└────────────────────┘         │  withdraw() ───►   │
                               │  balance()  ───►   │
                               └────────────────────┘
                                      ▲ controlled access only
```

## 🗺️ Mechanisms Map

```
Data Hiding in C++
│
├── Class-Level
│   ├── private members          → hidden from outside + derived
│   ├── protected members        → hidden from outside, visible to derived
│   └── friend declarations      → controlled, named breach

├── File-Level

├── ABI-Level
│   └── PIMPL idiom              → hide implementation details from header
│
└── Compile-Time
    └── Concepts / type traits   → hide behind static interface
```

## 🔷 1. Access Modifiers — Primary Mechanism

### Private — Strongest Hiding

```cpp
class BankAccount {
private:                         // hidden from everyone
    double   balance_;
    uint32_t pin_;
    std::vector<Transaction> history_;

public:                          // controlled interface
    explicit BankAccount(uint32_t pin, double initial = 0.0)
        : pin_(pin), balance_(initial) { }

    bool deposit(double amount) {
        if (amount <= 0) return false;    // enforce invariant
        balance_ += amount;
        history_.emplace_back(amount, TransactionType::DEPOSIT);
        return true;
    }

    bool withdraw(double amount, uint32_t pin) {
        if (pin != pin_) return false;    // auth check
        if (amount > balance_) return false;  // invariant
        balance_ -= amount;
        history_.emplace_back(amount, TransactionType::WITHDRAWAL);
        return true;
    }

    double balance(uint32_t pin) const {
        if (pin != pin_) return -1.0;     // auth check
        return balance_;
    }
    // No direct access to balance_, pin_, history_
    // Only valid operations allowed — invariants enforced
};

BankAccount acc(1234, 1000.0);
acc.balance_ = 9999999;    // ❌ compile error — private
acc.pin_ = 0000;           // ❌ compile error — private
acc.deposit(500.0);        // ✅ controlled interface
```

### What Private Enforces

```
1. Invariant protection — balance can never go negative
   without going through withdraw() validation

2. State consistency — history always matches balance changes
   impossible to change balance without recording it

3. Implementation freedom — internal representation can change
   (balance_ could become int cents later)
   callers are unaffected — they only use the interface

4. Thread safety boundaries — can add mutex to only private section
```

## 🔷 2. Getter / Setter Pattern

```cpp
class Temperature {
    double celsius_;

public:
    explicit Temperature(double c) : celsius_(c) { }

    // Getter — read-only access
    double celsius()    const { return celsius_; }
    double fahrenheit() const { return celsius_ * 9.0/5.0 + 32; }
    double kelvin()     const { return celsius_ + 273.15; }

    // Setter — validated write access
    void set_celsius(double c) {
        if (c < -273.15)
            throw std::domain_error("Below absolute zero");
        celsius_ = c;
    }

    void set_fahrenheit(double f) {
        set_celsius((f - 32) * 5.0/9.0);   // converts + validates
    }
};

Temperature t(100.0);
t.celsius_ = -999;          // ❌ compile error — private
t.set_celsius(-999);        // ❌ throws — enforced invariant
t.set_celsius(37.0);        // ✅ valid
std::cout << t.fahrenheit(); // ✅ computed on-the-fly from celsius_
```

### When NOT to Use Getters/Setters

```cpp
// ❌ Trivial getters/setters = data hiding theater
class Point {
    int x_, y_;
public:
    int  getX() { return x_; }
    void setX(int x) { x_ = x; }   // no validation
    int  getY() { return y_; }
    void setY(int y) { y_ = y; }   // no validation
};
// This is NOT data hiding — it's just public access with extra steps
// x_ might as well be public

// ✅ Use public members for simple value types with no invariants
struct Point {
    int x, y;   // public — simple data, no invariants needed
};

// ✅ Use private + interface when invariants exist
class Rect {
    int x_, y_, width_, height_;
public:
    void set_size(int w, int h) {
        if (w <= 0 || h <= 0) throw std::invalid_argument("...");
        width_ = w; height_ = h;
    }
};
```

## 🔷 3. PIMPL Idiom — ABI-Level Hiding

**P**ointer to **Impl**ementation — the most powerful data hiding pattern in C++.

### The Problem It Solves

```cpp
// ❌ Without PIMPL — private members in header
// widget.hpp:
#include <string>
#include <vector>
#include <boost/regex.hpp>   // heavy include — ALL users pay this cost
#include <openssl/ssl.h>     // exposes implementation detail

class Widget {
public:
    void process();
private:
    std::string              name_;     // private — but visible in header!
    std::vector<int>         cache_;    // change this → recompile EVERYONE
    boost::regex             pattern_;  // adds boost dependency to ALL users
    SSL*                     ssl_;      // exposes OpenSSL to ALL users
};

// Problems:
// 1. Implementation details in public header → recompile all users on change
// 2. Heavy includes in header → slow build for everyone
// 3. ABI changes when private members added/removed
```

### PIMPL Solution

```cpp
// widget.hpp — public header (thin, stable)
class Widget {
public:
    explicit Widget(const std::string& name);
    ~Widget();                       // must be in .cpp (Impl is incomplete here)
    Widget(Widget&&) noexcept;
    Widget& operator=(Widget&&) noexcept;
    Widget(const Widget&);
    Widget& operator=(const Widget&);

    void process();
    std::string name() const;

private:
    struct Impl;                     // forward declare — Impl is hidden
    std::unique_ptr<Impl> pimpl_;   // pointer to hidden implementation
};

// widget.cpp — private implementation (users never see this)
#include "widget.hpp"
#include <string>
#include <vector>
#include <boost/regex.hpp>    // heavy includes ONLY in .cpp
#include <openssl/ssl.h>

struct Widget::Impl {          // full definition hidden in .cpp
    std::string   name;
    std::vector<int> cache;
    boost::regex  pattern;
    SSL*          ssl;

    explicit Impl(const std::string& n) : name(n) { }
};

Widget::Widget(const std::string& n)
    : pimpl_(std::make_unique<Impl>(n)) { }

Widget::~Widget() = default;   // must be here — Impl complete in .cpp

Widget::Widget(Widget&&) noexcept = default;
Widget& Widget::operator=(Widget&&) noexcept = default;

Widget::Widget(const Widget& o)
    : pimpl_(std::make_unique<Impl>(*o.pimpl_)) { }

Widget& Widget::operator=(const Widget& o) {
    if (this != &o)
        pimpl_ = std::make_unique<Impl>(*o.pimpl_);
    return *this;
}

void Widget::process() {
    pimpl_->cache.push_back(42);    // access impl through pimpl_
    // ... actual implementation
}
```

### PIMPL Memory Layout

```
Widget object (on stack or heap):
┌──────────────────────────────┐
│  pimpl_ (8 bytes — pointer)  │──►┌──────────────────────┐
└──────────────────────────────┘   │  Widget::Impl        │
                                   │  name_   (string)    │
                                   │  cache_  (vector)    │
                                   │  pattern_(regex)     │
                                   │  ssl_    (SSL*)      │
                                   └──────────────────────┘

Users only see the pointer (8 bytes).
Implementation details completely invisible.
Adding fields to Impl → no recompile of users.
```

### PIMPL Benefits Table

| Benefit | Detail |
|---|---|
| ABI stability | Add fields to `Impl` without breaking binary compatibility |
| Compile time | Remove heavy `#include` from header — users don't pay the cost |
| Implementation hiding | `Impl` fields never visible to users |
| Reduced dependencies | Header only needs forward declarations |
| Faster incremental builds | Only `widget.cpp` recompiles when impl changes |

### PIMPL Costs

| Cost | Detail |
|---|---|
| Heap allocation | `Impl` always on heap — `unique_ptr` → allocation |
| Indirection | Every method call: `pimpl_->method()` → one extra pointer deref |
| Code verbosity | Rule of Five must be written manually |
| `unique_ptr<Impl>` in header | Incomplete type — destructor must be in `.cpp` |

## 🔷 4. Anonymous Namespace — File-Level Hiding

```cpp
// utils.cpp
namespace {                        // anonymous namespace
    // Everything here has INTERNAL LINKAGE
    // Invisible to ALL other translation units

    int helper_counter = 0;        // not visible outside utils.cpp
    void internal_helper() { }     // not visible outside utils.cpp

    struct InternalState {
        // completely hidden struct
    };
}

// Available in this file:
void public_function() {
    internal_helper();             // ✅ same TU
    helper_counter++;              // ✅ same TU
}

// other.cpp — cannot see or access:
extern void internal_helper();    // ❌ linker error — no such symbol
```

```
Anonymous namespace → internal linkage for all contained entities
Equivalent to marking everything static (for free functions/variables)
Preferred over static in modern C++ for file-level hiding
```

## 🔷 5. `static` — Function/File Level Hiding (Legacy)

```cpp
// module.cpp
static int file_counter = 0;           // internal linkage — file-private
static void file_helper() { }          // internal linkage — file-private

// Same as anonymous namespace for these cases
// Prefer anonymous namespace in modern C++
```

## 🔷 6. `friend` — Controlled, Named Breach

```cpp
class Matrix {
    std::vector<double> data_;
    int rows_, cols_;

    // Explicit permission — named, intentional
    friend Matrix multiply(const Matrix& a, const Matrix& b);
    friend class MatrixSerializer;    // entire class gets access
    friend std::ostream& operator<<(std::ostream&, const Matrix&);

public:
    Matrix(int r, int c) : rows_(r), cols_(c), data_(r*c, 0.0) { }
    double operator()(int r, int c) const;
};

// multiply can access data_ directly — performance-critical
Matrix multiply(const Matrix& a, const Matrix& b) {
    Matrix result(a.rows_, b.cols_);
    for (int i = 0; i < a.rows_; i++)
        for (int j = 0; j < b.cols_; j++)
            for (int k = 0; k < a.cols_; k++)
                result.data_[i*b.cols_+j] += a.data_[i*a.cols_+k]
                                           * b.data_[k*b.cols_+j];
    return result;
}
```

## 🔷 7. Opaque Types — C-Compatible Data Hiding

```cpp
// api.h — C-compatible public header
```

## 🔬 Under the Hood — Access Control

```cpp
class Foo {
    int secret = 42;
public:
    int value = 10;
};

Foo f;
f.value;    // ✅
f.secret;   // ❌ compile error
```

```
Access control is PURELY COMPILE-TIME:

Memory layout of Foo:
┌──────────────┐
│  secret (4B) │  offset +0
├──────────────┤
│  value  (4B) │  offset +4
└──────────────┘

'private' does NOT:
  → encrypt the memory
  → change memory layout
  → add runtime checks
  → prevent reading via pointer arithmetic

What 'private' DOES:
  → makes accessing the member a compile error
  → disappears completely in the binary

Consequence:
  reinterpret_cast<int*>(&f)[0]  → 42  (reads secret!)
  This is UB — but proves access control is compile-time only
```

```cpp
// Classic hack (UB but works in practice):
struct Hack { int secret; int value; };
Foo f;
int stolen = reinterpret_cast<Hack*>(&f)->secret;  // 42 — UB but "works"

// Lesson: data hiding = interface contract, not runtime security
```

## 🏭 Real-World Production Scenarios

### Scenario 1 — PIMPL Saves ABI Compatibility

```cpp
// v1: library shipped to customers
// widget.hpp:
class Widget {
    struct Impl;
    std::unique_ptr<Impl> pimpl_;
public:
    void process();
};

// v1: widget.cpp (customers have only the .so/.dll)
struct Widget::Impl {
    int x;
};

// v2: add field to Impl — NO ABI BREAK
struct Widget::Impl {
    int x;
    int y;          // ← added
    std::string z;  // ← added
};
// Customer .so recompiles widget.cpp only
// Customer code that uses Widget: ZERO RECOMPILATION needed
// Without PIMPL: adding any private member = recompile all customers

// Real impact at Qt, Chrome, all major C++ libraries use PIMPL
```

### Scenario 2 — Missing Data Hiding → Race Condition

```cpp
// ❌ No data hiding — threads bypass interface
struct Counter {
    int value = 0;  // public
    void increment() { value++; }
};

Counter c;
// Thread 1:
c.value = c.value + 1;    // direct access — no mutex
// Thread 2:
c.value = c.value + 1;    // race condition — UB

// ✅ Data hiding enforces mutex usage
class Counter {
    int        value_ = 0;
    std::mutex mtx_;
public:
    void increment() {
        std::lock_guard lock(mtx_);
        value_++;               // ONLY path to modify value_
    }
    int get() const {
        std::lock_guard lock(mtx_);
        return value_;
    }
    // No way to bypass mutex — data hiding enforces it
};
```

## 🎯 Interview Traps

**Trap 1:**
```cpp
class Foo {
    int x = 42;
};

int main() {
    Foo f;
    int* p = (int*)&f;
    std::cout << *p;   // prints 42?
}
```
> **UB** — accessing private member via pointer arithmetic violates strict aliasing and access control. But in practice: prints `42` on all major compilers. `private` is compile-time only — memory layout unchanged. This is UB, not a workaround.

**Trap 2:**
```cpp
class Base {
    int secret = 99;  // private
};
class Derived : public Base {
    void hack() {
        // can derived access Base::secret?
        // even via some trick?
    }
};
```
> ❌ No — `private` members are inaccessible even to derived classes. `protected` would allow it. Even `friend` on `Derived` doesn't help — `friend` is not inherited.

**Trap 3:**
```cpp
// Why does unique_ptr<Impl> destructor need to be in .cpp?
class Widget {
    struct Impl;
    std::unique_ptr<Impl> pimpl_;
public:
    ~Widget();   // declaration in header
};
```
> `unique_ptr<Impl>` destructor calls `delete` on `Impl*`. `delete` requires the type to be **complete** (needs full definition). In the header, `Impl` is only forward-declared (incomplete). The destructor must be defined in the `.cpp` where `Impl` is fully defined. Putting `~Widget() = default` in the header → compile error: "use of undefined type `Impl`".

**Trap 4:**
```cpp
class Foo {
public:
    void f() { secret(); }  // public method calls private
private:
    void secret() { std::cout << "secret\n"; }
};

Foo f;
f.f();      // prints "secret"?
```
> ✅ Yes — `f()` is public, `secret()` is private. Public methods can call private methods freely — access control is about **who calls**, not what's called internally. `f.secret()` from outside = ❌. `f.f()` calling `this->secret()` = ✅.

**Trap 5:**
```cpp
// PIMPL with unique_ptr — is it copyable?
class Widget {
    struct Impl;
    std::unique_ptr<Impl> pimpl_;
public:
    Widget();
    ~Widget();
};
Widget a;
Widget b = a;   // compiles?
```
> ❌ **Compile error** — `unique_ptr` has deleted copy constructor. PIMPL with `unique_ptr` is **move-only** by default. To make it copyable: explicitly write copy ctor/assign in `.cpp` that deep-copies `*pimpl_`. OR use `shared_ptr` instead (then copy = shared ownership, not deep copy).

## 📊 Data Hiding Mechanisms Comparison

| Mechanism | Scope | Overhead | ABI Stable | Use When |
|---|---|---|---|---|
| `private` member | class | zero | ❌ (in header) | invariant enforcement |
| `protected` member | class + derived | zero | ❌ | share with derived only |
| PIMPL | class | 1 heap alloc + 1 deref | ✅ | library APIs, ABI stability |
| Anonymous namespace | file | zero | N/A | file-private helpers |
| `static` (free) | file | zero | N/A | legacy file-private |
| Opaque pointer | API boundary | 1 deref | ✅ | C-compatible APIs |
