## 📦 Encapsulation in C++ — Complete Guide

> **Encapsulation** means **bundling data (members) + methods (behavior) together** into a single unit (class) and **controlling access** to that data. In C++, this is enforced by **Access Specifiers** (`private`, `protected`, `public`) and **Const-Correctness**.

---

## 📌 Core Idea

```text
Without Encapsulation:
Data and methods scattered everywhere
Anyone can access and corrupt anything 😩

With Encapsulation:
┌─────────────────────────────────────┐
│           CLASS (Capsule)           │
│                                     │
│  🔒 private data    ← hidden inside │
│  ✅ public methods  ← controlled    │
│                       gateway       │
└─────────────────────────────────────┘
Outside world ONLY goes through methods
Never touches data directly!
```

<Aside type="tip">
**Key Insight**: In C++, Encapsulation is not just about `private`. It's also about **Information Hiding** via Header files. By hiding implementation details in `.cpp` files (or using PIMPL), you reduce compile-time dependencies and binary coupling.
</Aside>

## 🔬 How It Works — Before & After

<Code lang="cpp" title="❌ Without Encapsulation — dangerous!" code={`
struct Student {
    std::string name;
    int age;
    double marks;
};

Student s;
s.age   = -100;    // 😱 invalid age — nobody stopped it!
s.marks = 999999;  // 😱 impossible marks — nobody stopped it!
s.name  = "";      // 😱 empty name — may cause issues later!
`} />

<Code lang="cpp" title="✅ With Encapsulation — safe and validated!" code={`
#include <string>
#include <stdexcept>

class Student {
private:
    // Step 1: Make fields PRIVATE — hidden from outside
    std::string name_;
    int age_;
    double marks_;

public:
    // Step 2: Provide PUBLIC controlled access

    // Getters — safe read access (const methods!)
    const std::string& getName() const { return name_; }
    int getAge() const { return age_; }
    double getMarks() const { return marks_; }

    // Setters — write access WITH validation
    void setName(const std::string& name) {
        if (name.empty()) {
            throw std::invalid_argument("Name cannot be empty!");
        }
        name_ = name;
    }

    void setAge(int age) {
        if (age < 0 || age > 150) {
            throw std::out_of_range("Invalid age: " + std::to_string(age));
        }
        age_ = age;
    }

    void setMarks(double marks) {
        if (marks < 0.0 || marks > 100.0) {
            throw std::out_of_range("Marks must be 0-100!");
        }
        marks_ = marks;
    }
};

// Usage — validation enforced!
int main() {
    Student s;
    try {
        s.setAge(-100);  // ❌ Exception thrown — blocked! ✅
    } catch (const std::exception& e) {
        // Handle error
    }
    s.setAge(20);    // ✅ Valid — goes through validation
    return 0;
}
`} />

## 🔬 In-Depth — What Encapsulation Gives You

<CardGrid>
  <Card title="Benefit 1: Validation" icon="shield">
    ```cpp
    Setter checks data before storing.
    Bad data NEVER enters your object.
    
    Example:
    void setAge(int age) {
        if (age < 0 || age > 150) {
            throw std::out_of_range("Invalid");
        }
        age_ = age;  // Only valid values reach the field
    }
    ```
  </Card>
  
  <Card title="Benefit 2: Flexibility (PIMPL)" icon="rocket">
    ```cpp
    Change internal implementation freely.
    External API stays same — nobody's code breaks.
    
    Example:
    // Header:
    class Impl; // Forward declaration
    std::unique_ptr<Impl> pImpl;
    
    // Source:
    struct Impl { /* detailed state */ };
    
    // You can change Impl without recompiling clients!
    ```
  </Card>

  <Card title="Benefit 3: Read-Only / Write-Only Control" icon="information">
    ```cpp
    Only getter → read-only field (immutable after construction)
    Only setter → write-only field (e.g., password hash)
    Both → full controlled access
    
    Example:
    class User {
        const std::string id_; // Const member
    public:
        User(std::string id) : id_(std::move(id)) {}
        const std::string& getId() const { return id_; } // Read-only ✅
        // No setId() → Immutable ID
    };
    ```
  </Card>

  <Card title="Benefit 4: Maintainability" icon="approve-check">
    ```cpp
    Centralized change — update one place.
    All callers automatically get new behavior.
    
    Example:
    void setPrice(double price) {
        // Add tax calculation in ONE place
        price_ = price * 1.18;  // All callers get tax automatically
    }
    ```
  </Card>

## 🔄 Types of Access via Encapsulation

<Code lang="cpp" title="Controlled access patterns in practice" code={`
#include <string>

class Employee {
    std::string id_;
    std::string name_;
    double salary_;
    std::string passwordHash_;

public:
    // 1️⃣ Read-Only — getter only (no setter!)
    const std::string& getId() const { return id_; }
    // id_ set once via constructor, never changed → immutable

    // 2️⃣ Write-Only — setter only (no getter!)
    void setPassword(const std::string& pwd) {
        // Hash before store!
        passwordHash_ = hashFunction(pwd); 
    }
    // No getPassword() — password never exposed! ✅ Security

    // 3️⃣ Full Access — getter + setter with validation
    double getSalary() const { return salary_; }
    void setSalary(double salary) {
        if (salary < 0) {
            throw std::invalid_argument("Salary can't be negative!");
        }
        salary_ = salary;
    }

    // 4️⃣ Computed — getter calculates, no direct field
    double getAnnualSalary() const {
        return salary_ * 12;  // Computed — no annualSalary field!
    }

    // Constructor — initialize immutable fields
    Employee(std::string id, std::string name) 
        : id_(std::move(id)), name_(std::move(name)), salary_(0.0) {}
};
`} />

<Aside type="note">
**Design Tip**: Favor **const members** and **const methods** where possible.  
Immutable objects are inherently thread-safe, easier to reason about, and prevent accidental mutation.
</Aside>

## 🏗️ Encapsulation with Constructor — Immutable Patterns

<Code lang="cpp" title="BankAccount — encapsulated with constructor validation" code={`
#include <string>
#include <stdexcept>

class BankAccount {
private:
    const long accountNumber_;  // const → immutable after construction
    const std::string owner_;   // const → immutable
    double balance_;            // mutable via controlled methods

public:
    // Constructor — sets initial state safely with validation
    BankAccount(long accNo, std::string owner, double initialDeposit)
        : accountNumber_(accNo), owner_(std::move(owner)), balance_(0.0) 
    {
        if (initialDeposit < 0) {
            throw std::invalid_argument("Initial deposit can't be negative!");
        }
        if (owner_.empty()) {
            throw std::invalid_argument("Owner name required!");
        }
        balance_ = initialDeposit;
    }

    // Read-only access for immutable fields
    long getAccountNumber() const { return accountNumber_; }
    const std::string& getOwner() const { return owner_; }

    // Read access for mutable field
    double getBalance() const { return balance_; }

    // Controlled mutation — deposit with validation
    void deposit(double amount) {
        if (amount <= 0) {
            throw std::invalid_argument("Deposit must be positive!");
        }
        balance_ += amount;
    }

    // Controlled mutation — withdraw with validation + business rule
    void withdraw(double amount) {
        if (amount <= 0) {
            throw std::invalid_argument("Amount must be positive!");
        }
        if (amount > balance_) {
            throw std::runtime_error("Insufficient balance!");
        }
        balance_ -= amount;
    }

    // Computed property — no direct field
    bool isOverdrawn() const {
        return balance_ < 0;
    }
};
`} />

<Aside type="caution">
**Immutable Field Pattern**:  
Use `const` members + **no setter** + **constructor initialization** for fields that should never change after object creation.  
This creates **immutable objects** — thread-safe and easier to reason about.
</Aside>

## ⚠️ Common Encapsulation Pitfalls

<CardGrid>
  <Card title="Pitfall 1: Exposing Mutable Collections" icon="error">
    ```cpp
    class Team {
        std::vector<std::string> members_;
    public:
        // ❌ Dangerous: Caller can modify internal vector!
        std::vector<std::string>& getMembers() {
            return members_; 
        }
    };
    
    // Usage:
    Team team;
    team.getMembers().push_back("Hacker");  // 😱 Bypasses business logic!
    
    // ✅ Safe alternatives:
    // Option 1: Return const reference (Read-only view)
    const std::vector<std::string>& getMembers() const {
        return members_;
    }
    
    // Option 2: Return copy (Safe but expensive)
    std::vector<std::string> getMembers() const {
        return members_;
    }
    
    // Option 3: Provide controlled add/remove methods
    void addMember(const std::string& name) { /* validation */ }
    ```
  </Card>
  
  <Card title="Pitfall 2: Returning Pointers/Refs to Internal State" icon="error">
    ```cpp
    class Event {
        std::string description_;
    public:
        // ❌ Dangerous: Caller gets non-const ref
        std::string& getDescription() {
            return description_; 
        }
        
        // ✅ Safe: Return const ref or value
        const std::string& getDescription() const {
            return description_;
        }
    };
    ```
  </Card>

  <Card title="Pitfall 3: Over-Encapsulation — Getters/Setters for Everything" icon="caution">
    ```cpp
    // ❌ Over-engineered: Simple data holder doesn't need full encapsulation
    class Point {
        int x_; int y_;
    public:
        int getX() const { return x_; }
        void setX(int x) { x_ = x; }
        // ...
    };
    
    // ✅ Better: Immutable value object or struct
    struct Point {
        int x;
        int y;
    };
    // Or use a class with no setters if immutability is desired
    ```
  </Card>
</CardGrid>

## 🛡️ Advanced Pattern: PIMPL Idiom

> The **Pointer to Implementation** idiom completely hides private data from the header file. This is the ultimate form of encapsulation in C++.

<Code lang="cpp" title="PIMPL Example" code={`
// --- Widget.h ---
#include <memory>

class Widget {
public:
    Widget();
    ~Widget(); // Must be defined in .cpp
    
    void doSomething();

private:
    struct Impl; // Forward declaration
    std::unique_ptr<Impl> pImpl; // Opaque pointer
};

// --- Widget.cpp ---
#include "Widget.h"
#include <iostream>

struct Widget::Impl {
    int secretData = 42;
    void work() { std::cout << "Working\\n"; }
};

Widget::Widget() : pImpl(std::make_unique<Impl>()) {}
Widget::~Widget() = default;

void Widget::doSomething() {
    pImpl->work();
}
`} />

<CardGrid>
  <Card title="Benefits of PIMPL" icon="rocket">
    - ✅ **Binary Compatibility**: Changing private members doesn't require recompiling clients.
    - ✅ **Compile Speed**: Header includes are minimized.
    - ✅ **True Hiding**: Private members are invisible to users of the header.
  </Card>
  
  <Card title="Costs of PIMPL" icon="caution">
    - ⚠️ **Heap Allocation**: `Impl` is on the heap.
    - ⚠️ **Indirection**: Extra pointer dereference.
  </Card>
</CardGrid>

  </Card>
  
  <Card title="Q: How is Encapsulation achieved in C++?" icon="approve-check">
    1. Make members `private`  
    2. Provide public getters/setters with validation  
    3. Use constructors to initialize immutable state  
    4. Use `const` methods for read-only access  
    5. (Advanced) Use PIMPL to hide implementation details
  </Card>

  <Card title="Q: Difference between Encapsulation and Abstraction?" icon="information">
    - **Encapsulation**: Data + methods bundled + access control → **HOW it's stored** is hidden  
    - **Abstraction**: Implementation logic hidden → **HOW it works** is hidden (via virtual functions/interfaces)  
    ✅ They complement each other — encapsulation enables abstraction.
  </Card>

  <Card title="Q: Can a class be fully encapsulated?" icon="approve-check">
    **YES ✅** — all members `private`, no public members whatsoever (except methods).  
    Every access through methods. Maximum protection.  
    Example: `std::string` — internal buffer is hidden.
  </Card>

  <Card title="Q: What if a class has only getters — no setters?" icon="information">
    Class becomes **IMMUTABLE** — object state can't change after construction.  
    ✅ Benefits: Thread-safe, safe to share, predictable behavior.  
    Example: `std::string` (mostly), custom value objects.
  </Card>

  <Card title="Q: Is it mandatory to have both getter and setter?" icon="approve-check">
    **NO ❌** — depends on design:  
    - Read-only → getter only (e.g., `getId()`)  
    - Write-only → setter only (e.g., `setPassword()`)  
    - Full access → both with validation
  </Card>

  <Card title="Q: What is tight encapsulation?" icon="shield">
    **ALL members private, NO public members whatsoever**.  
    Every access through methods. Maximum protection.  
    ✅ Preferred in production code — minimizes surface area for bugs.
  </Card>

## 🧩 DSA Angle — Encapsulation in Data Structures

<CardGrid>
  <Card title="Pattern: Encapsulated LinkedList — clean and safe" icon="rocket">
    ```cpp
    template<typename T>
    class LinkedList {
        // Hidden internal node class — not exposed to clients
        struct Node {
            T data;
            Node* next;
            Node(const T& d) : data(d), next(nullptr) {}
        };

        // Hidden internal state — encapsulated
        Node* head_;
        int size_;

    public:
        LinkedList() : head_(nullptr), size_(0) {}
        ~LinkedList() { /* cleanup */ }

        // Controlled operations ONLY — public API
        void addFirst(const T& data) {
            Node* node = new Node(data);
            node->next = head_;
            head_ = node;
            size_++;
        }

        T removeFirst() {
            if (!head_) throw std::runtime_error("List is empty!");
            T data = head_->data;
            Node* temp = head_;
            head_ = head_->next;
            delete temp;
            size_--;
            return data;
        }

        // Read-only accessors — no direct field exposure
        int size() const { return size_; }
        bool isEmpty() const { return size_ == 0; }

        // ❌ Nobody can touch head_, size_, Node directly
        // ✅ Only through controlled, validated methods
    };
    ```
  </Card>
  
  <Card title="Pattern: Encapsulated Graph for Algorithm Reuse" icon="shield">
    ```cpp
    class Graph {
        // Hidden internal representation — could be adjacency list, matrix, etc.
        int vertices_;
        std::vector<std::vector<int>> adj_;
        
    public:
        Graph(int v) : vertices_(v), adj_(v) {}
        
        // Controlled modifications
        void addEdge(int src, int dest) {
            if (src >= 0 && src < vertices_ && dest >= 0 && dest < vertices_) {
                adj_[src].push_back(dest);
            }
        }
        
        // Read-only access for algorithms
        const std::vector<int>& getNeighbors(int vertex) const {
            return adj_[vertex];
        }
        
        int getVertexCount() const { return vertices_; }
    };
    
    // BFS Algorithm — uses public API only
    std::vector<int> bfs(const Graph& g, int start) {
        // ... implementation uses g.getNeighbors() ...
    }
    ```

</CardGrid>

**DSA Pro Tip**: Encapsulation enables **algorithm reuse**.  
- Write BFS/DFS once against `Graph` interface — works with adjacency list, matrix, or custom representations  
- Hide internal node structure — clients can't corrupt the data structure  
- Validate operations — prevent invalid graph states (e.g., out-of-bounds access)

## 🔑 Quick Reference Summary

### Encapsulation Checklist

| Scenario | Recommended Approach |
|----------|---------------------|
| Simple data holder | `struct` with public members |
| Mutable domain object | Private fields + validated setters + business methods |
| Configuration | Immutable class + Constructor injection |
| Internal helper | `private` methods |
| Extension point | `protected` methods |
| Public API | `public` methods with clear contracts + validation |
| Mutable collection field | Return `const&` or copy |
| Mutable object field | Return `const&` or copy |

### Access Control Patterns

| Pattern | Fields | Methods | Use Case |
|---------|--------|---------|----------|
| **Read-Only** | `private const` | Getter only | Immutable IDs, timestamps |
| **Write-Only** | `private` | Setter only | Passwords, secrets |
| **Full Access** | `private` | Getter + validated setter | Mutable business data |
| **Computed** | None (or private) | Getter only (calculates) | Derived values, aggregates |
| **Controlled Mutation** | `private` | Business methods (no raw setters) | State machines, workflows |

### Common Pitfalls & Fixes

| Pitfall | Risk | Fix |
|---------|------|-----|
| Public mutable field | Invalid state, thread issues | Make `private` + validated setter |
| Getter returns mutable ref | Caller modifies internal state | Return `const&` or copy |
| Setter accepts mutable obj without copy | Caller retains reference, can mutate later | Copy in setter |
| Over-encapsulation (getters for everything) | Anemic domain model, logic leakage | Expose behavior, not just data |

<Aside type="caution">
**Final Checklist for Encapsulation Design**:
1. ✅ Start with `private` — relax access only when necessary
2. ✅ Validate inputs at public boundaries (constructors, setters, methods)
3. ✅ Return const references or copies for mutable state
4. ✅ Prefer immutability for value objects, config, DTOs
5. ✅ Encapsulate invariants within the class — don't leak validation to callers
6. ✅ Use modern features: `std::optional`, `std::unique_ptr`, `const` correctness
</Aside>

## 📌 What Is Encapsulation?

**Bundling data and the operations that act on that data into a single unit**, while controlling how that data is accessed and modified.

```
Encapsulation = DATA + BEHAVIOR in one unit
              + invariant enforcement
              + controlled access

WITHOUT encapsulation:        WITH encapsulation:
┌──────────────────────┐      ┌──────────────────────────────┐
│  float x, y, z;      │      │  class Vector3D {            │
│  float magnitude;    │      │    float x, y, z;            │
│                      │      │    float magnitude_;  ← in sync│
│  // caller must:     │      │  public:                     │
│  // - update mag     │      │    Vector3D(float,float,float)│
│  // - after EVERY    │      │    float magnitude() const;  │
│  // - x,y,z change   │      │    void normalize();         │
│  // guaranteed?  ❌  │      │  };  // always consistent ✅ │
└──────────────────────┘      └──────────────────────────────┘
```

## 🧭 Encapsulation vs Abstraction vs Data Hiding

```
ENCAPSULATION  = "Bundle related data + behavior together"
                  → structural principle → class/struct

ABSTRACTION    = "Show WHAT, hide HOW"
                  → design principle → interface design

DATA HIDING    = "Control who sees what"
                  → visibility principle → access modifiers

Relation:
  Encapsulation USES data hiding as a tool.
  Encapsulation ENABLES abstraction.
  You can have encapsulation WITHOUT full data hiding (all-public struct).
  You can have data hiding WITHOUT encapsulation (file-static variables).
```

```cpp
struct Point { int x, y; };   // encapsulation (bundled) — no data hiding
                                // not an abstraction (transparent)

class BankAccount {            // encapsulation + data hiding + abstraction
    double balance_;           // hidden
public:
    void deposit(double);      // abstraction of "add money"
};
```

## 🗺️ Mechanisms of Encapsulation

```
Encapsulation in C++
│
├── Class / Struct            → bundle data + behavior
├── Constructor               → enforce initial state invariant
├── Destructor                → enforce cleanup invariant
├── const methods             → read-without-modify invariant
├── Access modifiers          → enforce modification rules
├── Operator overloading      → natural syntax on encapsulated type
└── Copy/Move semantics       → encapsulate ownership transfer
```

## 🔷 1. The Bundle — Class as Unit

```cpp
// ❌ No encapsulation — scattered data, no guarantees
float connection_ip[4];
int   connection_port;
bool  connection_active;
int   connection_timeout_ms;
// Who ensures port is 0-65535?
// Who ensures timeout is positive?
// Who ensures active flag matches actual socket state?
// Nobody — caller must enforce everything

// ✅ Encapsulation — data + behavior + invariants in one unit
class Connection {
    uint32_t ip_;
    uint16_t port_;         // type enforces 0-65535 range
    bool     active_;
    int      timeout_ms_;
    int      socket_fd_;

public:
    Connection(uint32_t ip, uint16_t port, int timeout_ms = 5000)
        : ip_(ip)
        , port_(port)
        , active_(false)
        , timeout_ms_(timeout_ms > 0 ? timeout_ms : 5000)  // invariant
        , socket_fd_(-1)
    { }

    bool connect();
    void disconnect();
    bool send(const std::byte* data, size_t len);
    bool is_active() const { return active_; }
    uint16_t port() const { return port_; }

    // Invariant: can't send on inactive connection
    // Invariant: port always 0-65535 (enforced by type)
    // Invariant: timeout always positive (enforced by constructor)
};
```

## 🔷 2. Invariant Enforcement — The Heart of Encapsulation

An **invariant** is a condition that must always be true about an object's state.

```cpp
class Date {
    int year_, month_, day_;

    // Invariant: 1 <= month_ <= 12
    // Invariant: 1 <= day_ <= days_in_month(month_, year_)
    // Invariant: year_ >= 1 (for Gregorian calendar)

    static bool is_valid(int y, int m, int d) {
        if (m < 1 || m > 12) return false;
        if (d < 1 || d > days_in_month(m, y)) return false;
        if (y < 1) return false;
        return true;
    }

public:
    // Constructor ESTABLISHES invariant
    Date(int y, int m, int d) {
        if (!is_valid(y, m, d))
            throw std::invalid_argument("Invalid date");
        year_ = y; month_ = m; day_ = d;
    }

    // Methods MAINTAIN invariant
    void add_days(int n) {
        // ... complex logic ...
        // invariant guaranteed after every call
    }

    void set_month(int m) {
        if (m < 1 || m > 12)
            throw std::out_of_range("Month must be 1-12");
        // check day still valid for new month
        if (day_ > days_in_month(m, year_))
            day_ = days_in_month(m, year_);   // adjust day
        month_ = m;
        // invariant maintained
    }

    // Read-only access — cannot break invariant
    int year()  const { return year_; }
    int month() const { return month_; }
    int day()   const { return day_; }
};

Date d(2024, 2, 30);   // ❌ throws — invalid date
Date d(2024, 2, 28);   // ✅
d.set_month(13);        // ❌ throws — invariant protected
```

## 🔷 3. Const Correctness — Encapsulating Read vs Write

```cpp
class Matrix {
    std::vector<double> data_;
    int rows_, cols_;

public:
    // Non-const — modifies matrix
    double& operator()(int r, int c) {
        return data_[r * cols_ + c];
    }

    // Const — read only, callable on const Matrix
    const double& operator()(int r, int c) const {
        return data_[r * cols_ + c];
    }

    // Const method — can compute without modifying
    double determinant() const {
        // read-only computation
    }

    // Non-const method — modifies state
    void invert() {
        // modifies data_
    }
};

const Matrix m = identity(4);
m(0, 0);            // ✅ const overload
double d = m.determinant(); // ✅ const method

Matrix m2 = identity(4);
m2(0, 0) = 5.0;     // ✅ non-const overload
m2.invert();         // ✅ non-const method
```

## 🔷 4. Constructor as Invariant Enforcer

```cpp
// ❌ Two-phase initialization — invariant not enforced at construction
class Config {
public:
    std::string host;
    int         port;
    bool        initialized = false;

    void init(const std::string& h, int p) {
        host = h; port = p; initialized = true;
    }
    // Can use Config before init() is called — broken state
};

Config cfg;
cfg.host;    // ❌ empty string — object in broken state
cfg.port;    // ❌ 0 or garbage

// ✅ Single-phase — invariant from construction
class Config {
    std::string host_;
    int         port_;

public:
    Config(std::string host, int port)
        : host_(std::move(host))
        , port_(port)
    {
        if (host_.empty())
            throw std::invalid_argument("host cannot be empty");
        if (port <= 0 || port > 65535)
            throw std::invalid_argument("invalid port");
        // invariant established — object ALWAYS valid after construction
    }

    const std::string& host() const { return host_; }
    int port() const { return port_; }
};

// Either construction succeeds (valid state) or throws (no object)
```

## 🔷 5. Encapsulation with RAII

RAII is encapsulation applied to **resource lifetime**.

```cpp
// ❌ No encapsulation of resource management
FILE* f = fopen("data.txt", "r");
// ... code ...
// ... forgot fclose() → resource leak
// ... exception thrown → fclose() never reached

// ✅ Encapsulate resource + lifetime
class FileHandle {
    FILE* file_;

public:
    explicit FileHandle(const char* path, const char* mode)
        : file_(fopen(path, mode)) {
        if (!file_)
            throw std::runtime_error(
                std::string("Cannot open: ") + path);
    }

    // DESTRUCTOR ENFORCES INVARIANT: file ALWAYS closed
    ~FileHandle() {
        if (file_) fclose(file_);
    }

    // No copy — resource ownership
    FileHandle(const FileHandle&)            = delete;
    FileHandle& operator=(const FileHandle&) = delete;

    // Move — transfer ownership
    FileHandle(FileHandle&& o) noexcept
        : file_(std::exchange(o.file_, nullptr)) { }

    // Interface
    FILE* get() const { return file_; }
    operator bool() const { return file_ != nullptr; }
};

{
    FileHandle f("data.txt", "r");
    // ... use f ...
}   // ← destructor called automatically — file closed
    // ← even if exception thrown — guaranteed
```

## 🔷 6. Encapsulation and Operator Overloading

```cpp
class Fraction {
    int num_, den_;     // encapsulated

    void reduce() {     // private — implementation detail
        int g = std::gcd(std::abs(num_), den_);
        num_ /= g; den_ /= g;
        if (den_ < 0) { num_ = -num_; den_ = -den_; }
    }

public:
    Fraction(int n, int d) : num_(n), den_(d) {
        if (d == 0) throw std::domain_error("denominator zero");
        reduce();      // invariant: always in lowest terms
    }

    // Natural syntax — encapsulated operations
    Fraction operator+(const Fraction& o) const {
        return Fraction(num_ * o.den_ + o.num_ * den_, den_ * o.den_);
    }
    Fraction operator*(const Fraction& o) const {
        return Fraction(num_ * o.num_, den_ * o.den_);
    }
    bool operator==(const Fraction& o) const {
        return num_ == o.num_ && den_ == o.den_;  // always reduced
    }
    friend std::ostream& operator<<(std::ostream& os, const Fraction& f) {
        return os << f.num_ << "/" << f.den_;
    }
};

Fraction a(1, 2), b(1, 3);
Fraction c = a + b;           // ✅ natural syntax
std::cout << c;               // → 5/6 (automatically reduced)
Fraction bad(1, 0);           // ❌ throws — invariant enforced
```

## 🔷 7. Good vs Bad Encapsulation

```cpp
// ❌ Bad encapsulation 1 — trivial getters/setters, no invariants
class BadPerson {
    std::string name_;
    int age_;
public:
    std::string getName() { return name_; }
    void setName(std::string n) { name_ = n; }
    int getAge() { return age_; }
    void setAge(int a) { age_ = a; }
    // age_ could be -999 — no invariant
    // name_ could be empty — no invariant
    // This is public access with extra typing
};

// ❌ Bad encapsulation 2 — returns mutable reference to internals
class BadStack {
    std::vector<int> data_;
public:
    std::vector<int>& data() { return data_; }  // ← exposes internals!
};

BadStack s;
s.data().clear();     // bypass push/pop entirely — breaks invariants

// ✅ Good encapsulation — invariants enforced, no internal exposure
class Stack {
    std::vector<int> data_;
    size_t max_size_;

public:
    explicit Stack(size_t max = 1000) : max_size_(max) { }

    void push(int val) {
        if (data_.size() >= max_size_)
            throw std::overflow_error("Stack full");
        data_.push_back(val);
    }

    void pop() {
        if (data_.empty())
            throw std::underflow_error("Stack empty");
        data_.pop_back();
    }

    int top() const {
        if (data_.empty())
            throw std::underflow_error("Stack empty");
        return data_.back();
    }

    bool  empty() const { return data_.empty(); }
    size_t size() const { return data_.size(); }
    // No exposure of data_ — invariants always maintained
};
```

## 🔷 8. Encapsulation in Templates

```cpp
// Generic encapsulated container
template<typename T, size_t MAX_SIZE>
class BoundedQueue {
    std::array<T, MAX_SIZE> buffer_;
    size_t head_ = 0;
    size_t tail_ = 0;
    size_t count_ = 0;

    // Invariant: count_ == logical size
    // Invariant: head_ and tail_ always valid indices
    // Invariant: count_ <= MAX_SIZE

public:
    bool enqueue(const T& val) {
        if (count_ == MAX_SIZE) return false;
        buffer_[tail_] = val;
        tail_ = (tail_ + 1) % MAX_SIZE;   // wrap around
        ++count_;
        return true;
    }

    bool dequeue(T& out) {
        if (count_ == 0) return false;
        out = std::move(buffer_[head_]);
        head_ = (head_ + 1) % MAX_SIZE;
        --count_;
        return true;
    }

    size_t size()     const { return count_; }
    bool   empty()    const { return count_ == 0; }
    bool   full()     const { return count_ == MAX_SIZE; }

    // No exposure of buffer_, head_, tail_
    // Ring buffer mechanics completely encapsulated
};
```

## 🔬 Under the Hood — What Encapsulation Costs

```cpp
class Encapsulated {
    int value_;
public:
    int get() const { return value_; }
    void set(int v) { value_ = v; }
};

struct Bare {
    int value;
};
```

```asm
; Encapsulated::get() — with optimization (-O2):
get:
    mov eax, DWORD PTR [rdi]   ; load value_
    ret

; Encapsulated::set() — with optimization:
set:
    mov DWORD PTR [rdi], esi   ; store v to value_
    ret

; Direct struct access:
    mov eax, DWORD PTR [rdi]   ; identical instruction

; ZERO DIFFERENCE in generated code
; Encapsulation cost with optimization: 0 ns
; Access modifiers: compile-time only — zero binary impact
; Inline getter/setter: eliminated entirely
```

```
Object layout is identical:
Encapsulated: [value_]
Bare:         [value]
Same memory, same access pattern, same assembly
Encapsulation overhead = zero at runtime
```

## 🔷 9. Breaking Encapsulation — Anti-Patterns

```cpp
// ❌ Anti-pattern 1: returning non-const reference to internals
class Vector {
    double x_, y_;
public:
    double& x() { return x_; }   // gives direct write access
    // caller can set x_ to NaN, infinity — breaks invariants
};

// ❌ Anti-pattern 2: storing pointer/reference given by caller
class Widget {
    int* external_ptr;
public:
    void set_data(int* p) { external_ptr = p; }
    // Widget stores pointer to external data
    // external data deleted → Widget has dangling pointer
    // Widget doesn't own the data — encapsulation broken
};

// ❌ Anti-pattern 3: public mutable data + behavioral methods
class Timer {
public:
    int elapsed_ms = 0;    // public — anyone can set
    void start() { }
    void stop()  { elapsed_ms = measure(); }
    // start()/stop() pair can be bypassed: timer.elapsed_ms = 9999
};

// ❌ Anti-pattern 4: friend overuse
class Account {
    double balance_;
    friend class AccountHacker;   // grants full access — encapsulation gone
};
```

## 🏭 Real-World Production Scenario

**Encapsulation prevents billion-dollar production bug:**

```cpp
// ❌ 2012 — Knight Capital Group incident pattern:
// No encapsulation — global mutable state, no invariants
int  order_quantity = 0;
bool use_legacy_mode = false;
double price_limit = 0.0;

void execute_trade() {
    // Multiple teams modify these globals directly
    // order_quantity sometimes set to 0 — divide by zero
    // use_legacy_mode set by feature flag AND by error handler
    // no invariant: what combinations are valid?
    // result: $440 million loss in 45 minutes from wrong state

// ✅ Encapsulated trading engine:
class TradeOrder {
    int      quantity_;
    double   price_limit_;
    TradeMode mode_;
    bool     validated_;

    // Invariant: quantity > 0
    // Invariant: price_limit > 0
    // Invariant: once validated, cannot be modified
    // Invariant: mode is a valid enum value

public:
    TradeOrder(int qty, double limit, TradeMode mode)
        : quantity_(qty)
        , price_limit_(limit)
        , mode_(mode)

        if (qty <= 0)    throw std::invalid_argument("qty must be positive");
        if (limit <= 0)  throw std::invalid_argument("limit must be positive");

        // cross-field validation
        validated_ = true;   // lock further modification
    }

    void execute() const {
        if (!validated_)
            throw std::logic_error("Order must be validated before execution");
        // execute — state guaranteed valid
    }
    // No public setters — order is immutable after construction
    // Invariants enforced at EVERY state transition
};
```

## 🎯 Interview Traps

**Trap 1:**
```
"What is encapsulation? Is it the same as data hiding?"
```
> **No.** Encapsulation = bundling data + behavior in one unit (the class). Data hiding = controlling access via private/protected. Data hiding is one TOOL used to achieve encapsulation. You can have encapsulation without data hiding (`struct Point { int x, y; };`) — data is bundled, just not hidden.

**Trap 2:**
```cpp
class Foo {
    std::vector<int>& items_;
public:
    explicit Foo(std::vector<int>& v) : items_(v) { }
    void add(int x) { items_.push_back(x); }
    int size() const { return items_.size(); }
};
// Is this good encapsulation?
```
> ❌ **No.** `Foo` stores a reference to external data it doesn't own. The caller can modify `items_` directly (bypassing `add()`), and can destroy the vector while `Foo` still holds a reference (dangling). Encapsulation broken — `Foo` doesn't control its own state. Should store `std::vector<int>` by value.

**Trap 3:**
```cpp
class Counter {
    mutable int count_ = 0;
public:
    void increment() const { count_++; }   // const method modifies!
    int get() const { return count_; }
};
// Does this break encapsulation?
```
> **Not necessarily.** `mutable` is for "implementation details not part of logical state" (caches, counters, mutexes). If `count_` IS the logical state of `Counter`, making `increment()` `const` breaks the contract (const = "doesn't change state"). If `count_` were a debug counter hidden from the logical interface → `mutable` is appropriate. Context matters.

**Trap 4:**
```
"Can encapsulation be achieved with a struct?"
```
> **Yes** — `struct` can have private members, constructors, methods, invariants — everything a `class` can. The only difference is default access (`public` vs `private`). `struct` with all private members = full encapsulation. Many production types (e.g., `std::pair`, `std::optional` internals) use `struct` with encapsulation.

**Trap 5:**
```cpp
class Config {
    std::string host_;
    int port_;
public:
    Config() = default;
    void set_host(std::string h) { host_ = h; }
    void set_port(int p) { port_ = p; }
    bool is_valid() const { return !host_.empty() && port_ > 0; }
};
// What invariant problem exists?
```
> **Two-phase init problem.** After `Config()` — object is in invalid state (`host_` empty, `port_` = 0). Caller must call `set_host` + `set_port` AND check `is_valid()`. Nothing enforces this. Object can be used in invalid state. Fix: constructor that takes required parameters and validates them, making `is_valid()` always true after construction.

## 📊 Encapsulation Quality Checklist

```
✅ GOOD ENCAPSULATION:
   □ Object invariants always true after construction
   □ No invalid state reachable through public interface
   □ Public interface describes WHAT, not HOW
   □ Internal implementation can change without API change
   □ No public mutable references to internal state
   □ Constructor establishes ALL invariants
   □ Every setter validates before modifying

❌ BAD ENCAPSULATION:
   □ Trivial getters/setters with no validation
   □ Public data with methods that "should" be called
   □ Two-phase initialization (construct then init())
   □ Returns mutable reference/pointer to internals
   □ Stores reference/pointer to caller-owned data
   □ Methods that assume other methods were called first
```
