## 📦 What is a Variable in C++?

A **Variable** is a named region of storage that holds a value. Every variable has a **type**, which dictates:
1.  The kind of data it can hold (and its size via `sizeof`).
2.  What operations are valid on it.
3.  Its **storage duration** and **scope** (lifetime rules).

<Code lang="cpp" title="Variable structure" code={`
┌─────────────────────────────────────────────────────┐
│  Variable = Name + Type + Value + Address + Lifetime │
└─────────────────────────────────────────────────────┘

int age = 25;
 ↑    ↑    ↑
type name value

int age = 25;
 │   │     │
 │   │     └── value (25)
 │   └──── type (int) → determines size + valid operations
 └──────── name (age) → identifier → disappears after compile
`} />

> 🎯 **C++ Key Difference**: Unlike Java, C++ gives you **explicit control** over memory: stack vs. heap, pointers vs. references, and **no garbage collector**. With power comes responsibility — uninitialized variables = **undefined behavior**!

## The Foundational Divide: Value Types vs. Reference Types

C++ distinguishes variables by **how they store/access data** — and by **storage duration**.

### 🔵 Value Type Variable (Primitive / POD)

Stores the **actual value directly** in its storage location (usually stack).

<Code lang="cpp" title="Value type — value lives directly in storage" code={`int age = 25;

// STACK (if local)
// ┌─────────────┐
// │  age │  25  │  ← value itself is here
// └─────────────┘`} />

### 🟠 Pointer Variable

Stores a **memory address** that can point to an object — explicit indirection with `*` and `&`.

<Code lang="cpp" title="Pointer — stack holds address, heap may hold object" code={`int* pAge = new int(25);  // Heap allocation

// STACK                      HEAP
// ┌──────────────────┐       ┌─────────────────┐
// │ pAge │ 0x7fff... ─┼──────▶│      25         │
// └──────────────────┘       └─────────────────┘
//    (holds address)           (actual value)

delete pAge;  // ✅ Manual cleanup required!
`} />

### 🔗 Reference Variable (C++ Only!)

An **alias** for an existing variable — no indirection syntax, but behaves like a pointer under the hood.

<Code lang="cpp" title="Reference — alias, not a pointer" code={`
int age = 25;
int& ref = age;  // ref is an ALIAS for age

ref = 99;        // modifies age directly!
std::cout << age; // 99 ✅

// Memory: ref and age share the SAME storage location
// No extra address stored — compiler optimizes away
`} />

---

| Feature | Value Type (`int`) | Pointer (`int*`) | Reference (`int&`) |
|---------|-------------------|------------------|-------------------|
| **Stores** | Actual value | Memory address | Alias (no storage) |
| **Memory Location** | Stack / Heap / Data | Stack (holds address) | None (compiler alias) |
| **Reassignable** | ✅ Yes | ✅ Yes (`p = &x`) | ❌ No (bound at init) |
| **Can be `nullptr`** | N/A | ✅ Yes | ❌ No (must bind to valid object) |
| **Syntax to access** | `x` | `*p` or `p->member` | `ref` (same as original) |
| **Default init (local)** | ❌ Garbage! | ❌ Garbage pointer! | ❌ Must initialize |
| **Default init (global)** | ✅ Zero | ✅ `nullptr` | N/A (must bind) |
| **Copy behavior** | Independent value | Copies address (shallow) | Copies alias (same target) |

### Copy Behaviour — The Real Difference

<Tabs>
  <TabItem label="Value Copy — Independent">
    <Code lang="cpp" title="Each variable gets its own copy of the value" code={`
      int a = 10;
      int b = a;    // b gets a COPY of the value
      b = 99;       // changing b does NOT affect a

      std::cout << a; // 10 ✅ unchanged
      std::cout << b; // 99
    `} />

    <Aside type="note">
      Value types are **value-independent** — modifying one never affects the other. This is the default in C++.
    </Aside>
  </TabItem>

  <TabItem label="Pointer Copy — Shared Object">
    <Code lang="cpp" title="Both pointers point to the SAME heap object" code={`int* p1 = new int[3]{1, 2, 3};
int* p2 = p1;          // copies the ADDRESS, not the data!

p2[0] = 999;           // modifies the SAME object on heap

std::cout << p1[0];    // 999 😱 p1 also affected!
std::cout << p2[0];    // 999

// p1 ──────────▶ [999, 2, 3]  ← same heap object
// p2 ──────────▶ [999, 2, 3]  ← both point here!

delete[] p1;  // ✅ Clean up once!
// delete[] p2; // ❌ Double-free = UB!
`} />

    <Aside type="caution">
      Assigning a pointer copies the **address**, not the data. Both pointers now point to the **same object**. Manage ownership carefully — prefer `std::unique_ptr`!
    </Aside>
  </TabItem>

  <TabItem label="Reference — True Alias">
    <Code lang="cpp" title="Reference is not a copy — it's the same variable" code={`int x = 10;
int& ref = x;   // ref is an alias for x

ref = 99;       // modifies x directly
std::cout << x; // 99 ✅

// You cannot rebind a reference:
int y = 5;
// ref = y;     // ❌ This assigns y's VALUE to x, does NOT rebind ref!
// ref now still aliases x, which now holds 5
`} />

    <Aside type="tip">
      References **cannot be reseated** after initialization. If you need rebindable indirection, use a pointer or `std::reference_wrapper`.
    </Aside>
  </TabItem>

  <TabItem label="Deep Copy ✅">
    <Code lang="cpp" title="Manual deep copy for independent objects" code={`// Raw pointers (manual):
int* p1 = new int[3]{1,2,3};
int* p2 = new int[3];
std::copy(p1, p1+3, p2);  // now independent

// Modern C++: prefer std::vector (handles deep copy automatically)
#include <vector>
std::vector<int> v1 = {1,2,3};
std::vector<int> v2 = v1;  // ✅ Deep copy — v1 and v2 independent
`} />
  </TabItem>
</Tabs>

## 🗂️ Classification by Storage Duration & Scope

In C++, variables are classified by **storage duration** (lifetime) and **scope** (visibility). This is more nuanced than Java.

```cpp
C++ Variables
│
├── By Storage Duration
│   ├── Automatic (local)      ← stack, method/block scope
│   ├── Static                 ← data segment, program lifetime
│   ├── Thread-local           ← per-thread storage (C++11)
│   └── Dynamic (heap)         ← new/delete, manual lifetime
│
├── By Scope
│   ├── Block scope            ← { } inside functions
│   ├── Function prototype scope ← parameters in declaration
│   ├── Function scope         ← labels (rare)
│   ├── Class scope            ← members, static members
│   └── Namespace / Global scope ← outside all functions
│
├── By Type Qualifiers
│   ├── const                  ← runtime immutable
│   ├── constexpr              ← compile-time constant (C++11)
│   ├── consteval              ← must be compile-time (C++20)
│   ├── mutable                ← modifiable even in const methods
│   └── volatile               ← hardware/I/O side effects
│
└── By Type Inference (C++11+)
    ├── auto                   ← deduce type from initializer
    └── decltype               ← deduce type from expression
```
```
Variables
│
├── By Storage Class
│   ├── auto          → local, stack, default for locals
│   ├── static        → persists entire program
│   ├── extern        → declared here, defined elsewhere
│   ├── register      → hint to use register (deprecated C++17)
│   └── thread_local  → one copy per thread (C++11)
│
├── By Scope
│   ├── Local         → inside a function/block
│   ├── Global        → outside all functions
│   ├── Namespace     → inside a namespace
│   └── Class         → member variables
│
├── By Linkage
│   ├── No linkage    → local variables
│   ├── Internal      → static globals (file scope only)
│   └── External      → global variables (visible to linker)
│
├── By Lifetime
│   ├── Automatic     → stack, born/dies with scope
│   ├── Static        → lives entire program
│   ├── Dynamic       → heap, you control lifetime
│   └── Thread-local  → lives per thread
│
└── By Mutability
    ├── const         → runtime constant
    ├── constexpr     → compile-time constant
    ├── constinit     → guaranteed static init (C++20)
    ├── volatile      → no optimization on reads/writes
    └── mutable       → modifiable inside const object
```

#### 🔤 Four Core Variable Categories (by Storage Duration)

```
┌──────────────────┬────────────────────────┬────────────┬──────────────┬────────────────┐
│ Category         │ Where Declared         │ Default?   │ Memory       │ Lifetime       │
├──────────────────┼────────────────────────┼────────────┼──────────────┼────────────────┤
│ Automatic (local)│ function / block       │ ❌ Garbage!│ Stack        │ block exit     │
│ Static           │ global / static keyword│ ✅ Zero    │ Data/BSS     │ program end    │
│ Thread-local     │ thread_local keyword   │ ✅ Zero    │ TLS segment  │ thread exit    │
│ Dynamic          │ new / make_unique      │ ❌ Garbage!│ Heap         │ until delete   │
└──────────────────┴────────────────────────┴────────────┴──────────────┴────────────────┘
```

```cpp
// Global scope (static storage duration)
int globalCount = 0;  // ✅ Zero-initialized if not explicitly set

class OrderService {
public:
    // Instance member (automatic storage when object is on stack)
    int retryCount = 3;  // ✅ In-class initializer (C++11)

    // Static member (static storage duration)
    static inline int totalOrders = 0;  // ✅ C++17 inline static

    // Parameter (automatic storage)
    Order createOrder(const std::string& customerId) {  // ← customerId is parameter

        // Local variable (automatic) — MUST initialize!
        std::string status = "PENDING";  // ✅ initialized

        return Order(customerId, status);
    }
};

// ⚠️ CRITICAL: Local variables in C++ are NOT zero-initialized!
// Reading an uninitialized local = Undefined Behavior (not compile error!)
```

> 🔑 **Key Difference from Java**:  
> - Java: Local variables → compile error if read uninitialized.  
> - C++: Local variables → **undefined behavior** if read uninitialized (compiler may not warn!).  
> ✅ **Rule**: Always initialize local variables in C++: `int x{};` or `int x = 0;`.

### 1️⃣ Automatic Variables (Local / Block Scope)

Declared **inside a function, block, or as a parameter**. Stored on the **stack**.

- **Lifetime:** Exists only while the block executes.
- **Initialization:** ⚠️ **NO default value** — contains garbage! Reading before write = **Undefined Behavior**.
- **Modifiers:** `const`, `constexpr` (if init is constant), `register` (deprecated), `mutable` (not applicable).
- **Scope:** Block-scoped (C++ has no function-level scope like Java).

<Code lang="cpp" title="Local variable — must initialize!" code={`
void process() {
    int x;  // ⚠️ UNINITIALIZED — contains garbage!
    // std::cout << x;  // 💥 Undefined Behavior! (may print garbage, crash, or "work")

    // ✅ Safe: initialize at declaration
    int y = 10;
    std::cout << y;  // ✅ 10

    // ✅ Modern C++: uniform initialization (prevents narrowing)
    int z{20};       // ✅ Preferred style (C++11)

    // Scope — block-scoped (stricter than Java)
    if (true) {
        int w = 5;   // w lives only in this block
        std::cout << w;  // ✅
    }
    // std::cout << w;  // ❌ Compile error: 'w' not declared in this scope
}
// 'x', 'y', 'z' are DESTROYED when function exits (stack unwind)
`} />

<Aside type="danger">
  **Undefined Behavior, not compile error.** C++ trusts you — if you read an uninitialized local, anything can happen:

  ```cpp
  void calculate(bool flag) {
      int x;  // ⚠️ garbage
      if (flag) {
          x = 10;
      }
      // std::cout << x;  // 💥 UB if flag==false! May print garbage or crash

      // ✅ Fix: initialize at declaration
      int x = 0;  // safe default
      if (flag) {
          x = 10;
      }
      std::cout << x;  // ✅ safe
  }
  ```

  🎯 **Compiler warnings**: Enable `-Wuninitialized` (GCC/Clang) to catch many cases, but the compiler cannot prove all paths statically.
</Aside>

<Tabs>
  <TabItem label="Scope trap — for loop (C++17)">
    <Code lang="cpp" title="Loop variable scope — C++17 init-statement" code={`// Pre-C++17: j visible after loop (common bug!)
for (int j = 0; j < 3; ++j) { /*...*/ }
// std::cout << j;  // ✅ Compiles (j still in scope) — often unintended!

// C++17: init-statement confines j to loop
if (int j = 0; j < 3) { /*...*/ }  // ❌ Wrong syntax example

// ✅ Correct C++17 pattern for confined scope:
for (int j = 0, limit = 3; j < limit; ++j) {
    // j and limit only visible here
}
// std::cout << j;  // ❌ Compile error: j not declared

// ✅ Even better: range-based for or std::views (C++20)
`} />
  </TabItem>

  <TabItem label="Uniform initialization ✅">
    <Code lang="cpp" title="Brace init prevents narrowing and ensures zero-init" code={`int a{};           // ✅ Zero-initialized: 0
int b{10};         // ✅ Value-initialized: 10
// int c{3.14};    // ❌ Compile error: narrowing double→int (C++11)

std::vector<int> v{1,2,3};  // ✅ List initialization
std::array<int,3> arr{4,5,6}; // ✅ Aggregate initialization
`} />

    <Aside type="tip">
      Always prefer **brace initialization `{}`** in modern C++ — it prevents narrowing conversions and ensures consistent initialization semantics.
    </Aside>
  </TabItem>

  <TabItem label="Allowed specifiers">
    <Code lang="cpp" title="Common specifiers for local variables" code={`const int x = 10;      // ✅ Runtime immutable
constexpr int y = 20;  // ✅ Compile-time constant (if init is constexpr)
static int z = 30;     // ✅ Static storage, but block scope (retains value between calls)
thread_local int t = 40; // ✅ C++11: one copy per thread

// ❌ Invalid on locals:
// public/private/protected → only for class members
// virtual/override → only for methods
`} />
  </TabItem>
</Tabs>

### 2️⃣ Static Storage Duration Variables

Declared with `static` keyword **inside a function** or **at namespace/class scope**.

- **Lifetime:** Entire program execution.
- **Initialization:** Zero-initialized first, then constant-initialized if possible, then dynamic-initialized (order matters!).
- **Storage:** Data segment (`.data` / `.bss`), not stack or heap.
- **Access:** Direct by name (if in scope) or via class name for static members.

<Code lang="cpp" title="Static local — retains value between calls" code={`
void counter() {
    static int count = 0;  // Initialized ONLY ONCE, first time function is called
    ++count;
    std::cout << count << " ";
}

counter();  // 1
counter();  // 2
counter();  // 3 — count persists across calls!
`} />

<Code lang="cpp" title="Static member — one copy per class" code={`
class Student {
public:
    std::string name;                // instance member — each object has own copy
    static inline int count = 0;     // C++17: inline static (no separate definition needed)

    Student(std::string n) : name(std::move(n)) {
        ++count;                     // modifies the ONE shared copy
    }
};

Student s1("Alice");
Student s2("Bob");
std::cout << Student::count;  // 2 ✅ — access via class name
`} />

<Code lang="cpp" title="Memory layout" code={`// DATA SEGMENT (.bss / .data)
// ┌──────────────────────────────────┐
// │   Student::count = 2             │  ← ONE copy for entire program
// └──────────────────────────────────┘
//
// STACK (if objects are local)
// ┌─────────────┐     ┌─────────────┐
// │  s1 object  │     │  s2 object  │
// │  name=Alice │     │  name=Bob   │
// └─────────────┘     └─────────────┘
//       ↑ both share the static member — no copy per object
`} />

<Aside type="note">
  - Static variables are **zero-initialized** before any other initialization (C++ guarantee).
  - **Initialization order** across translation units is **unspecified** — avoid dependencies! Use "construct on first use" idiom or `std::call_once`.
  - Stored in **data segment** — not on stack or heap.
  - Accessible from any scope where the name is visible.
  - Preferred access for class statics: **`ClassName::member`** (not via object).
</Aside>

<Aside type="danger">
  **Static Initialization Order Fiasco**:
  ```cpp
  // file1.cpp
  extern int x;
  int y = x + 1;  // ⚠️ What if x is in file2.cpp and not initialized yet?

  // file2.cpp
  int x = 42;
  ```
  ✅ **Fix**: Use function-local static ("Meyer's singleton"):
  ```cpp
  int& getX() {
      static int x = 42;  // Initialized on first call, thread-safe (C++11)
      return x;
  }
  ```
</Aside>

### 3️⃣ Dynamic Storage Duration (Heap) Variables

Allocated with `new` / `new[]` or (preferably) smart pointers. Lifetime controlled manually or via RAII.

- **Lifetime:** From `new` until `delete` (or smart pointer destruction).
- **Initialization:** **NOT zero-initialized** by default! Use `new T{}` for value-initialization.
- **Storage:** Free store (heap).
- **Access:** Via pointer or reference.

<Code lang="cpp" title="Dynamic allocation — manual vs RAII" code={`
// ❌ Raw new/delete — error-prone
int* raw = new int(42);      // ✅ Value-initialized to 42
int* raw2 = new int;         // ⚠️ UNINITIALIZED — garbage value!
// std::cout << *raw2;       // 💥 Undefined Behavior
delete raw;
delete raw2;

// ✅ Modern C++: std::unique_ptr (C++11) — automatic cleanup
#include <memory>
auto smart = std::make_unique<int>(42);  // ✅ Exception-safe, no leak
// *smart = 99;  // ✅ Use like normal pointer

// ✅ For arrays: std::vector (preferred) or std::unique_ptr<T[]>
std::vector<int> vec(5, 0);  // ✅ 5 zeros, auto-resizable, RAII
`} />

<Aside type="tip">
  **RAII Rule**: Prefer **smart pointers** (`std::unique_ptr`, `std::shared_ptr`) or **containers** (`std::vector`, `std::string`) over raw `new`/`delete`. They automatically clean up, even if exceptions occur.
</Aside>

### 4️⃣ Parameter Variables

Variables passed into a **function** — behavior depends on **passing mechanism**:

| Passing Style | Syntax | Effect | Use Case |
|--------------|--------|--------|----------|
| **Pass-by-value** | `void f(int x)` | Copy of value | Small types, no mutation needed |
| **Pass-by-reference** | `void f(int& x)` | Alias to original | Large objects, mutation needed |
| **Pass-by-const-reference** | `void f(const int& x)` | Read-only alias | Large objects, no mutation |
| **Pass-by-pointer** | `void f(int* x)` | Address (can be null) | Optional parameters, C interop |
| **Pass-by-rvalue-reference** | `void f(int&& x)` | Bind to temporaries | Move semantics (C++11) |

<Tabs>
  <TabItem label="Pass-by-value — copy">
    <Code lang="cpp" title="Changing the parameter does NOT affect the caller" code={`void change(int x) {
    x = 100;       // modifies only the LOCAL copy
}

int n = 10;
change(n);
std::cout << n;    // 10 — unchanged ✅`} />
  </TabItem>

  <TabItem label="Pass-by-reference — shared">
    <Code lang="cpp" title="Modifying the parameter DOES affect the caller" code={`void modify(int& x) {
    x = 999;       // modifies the ORIGINAL variable
}

int n = 10;
modify(n);
std::cout << n;    // 999 ✅`} />
  </TabItem>

  <TabItem label="Pass-by-const-reference — efficient read">
    <Code lang="cpp" title="Avoid copy, prevent mutation" code={`void print(const std::string& s) {
    // s[0] = 'X';  // ❌ Compile error: const
    std::cout << s;
}

std::string huge = "..." * 10000;
print(huge);  // ✅ No copy, efficient, safe
`} />
  </TabItem>

  <TabItem label="Pass-by-pointer — nullable">
    <Code lang="cpp" title="Pointer can be nullptr — check before use" code={`void process(int* p) {
    if (p == nullptr) return;  // ✅ Null check
    *p = 42;                   // Modify original
}

int x = 10;
process(&x);    // ✅ Pass address
process(nullptr); // ✅ Safe — handled in function
`} />
  </TabItem>
</Tabs>

<Aside type="tip">
  **C++ Rule of Thumb for Parameters**:
  - Small types (`int`, `double`, pointers): **pass-by-value**.
  - Large types (`std::string`, `std::vector`, custom classes): **pass-by-const-reference** for read-only, **pass-by-reference** for mutation.
  - Optional/nullable: **pass-by-pointer** or `std::optional<T>` (C++17).
  - Want to steal resources: **pass-by-rvalue-reference** (`T&&`) + `std::move`.
</Aside>

## 🧠 Advanced Concepts & Interview Traps

<CardGrid>
  <Card title="Trap 1 — Uninitialized Local = UB" icon="error">
    C++ does NOT zero-initialize local variables:
    ```cpp
    void foo() {
        int x;
        std::cout << x;  // 💥 Undefined Behavior! May crash or print garbage
    }
    ```
    ✅ **Fix**: Always initialize: `int x{};` or `int x = 0;`. Enable `-Wuninitialized`.
  </Card>

  <Card title="Trap 2 — Pointer vs Reference Semantics" icon="error">
    References cannot be null and cannot be reseated:
    ```cpp
    int x = 10, y = 20;
    int& ref = x;
    // ref = y;   // ❌ This assigns y's VALUE to x, does NOT rebind ref!
    // ref now still aliases x, which now holds 20

    int* p = &x;
    p = &y;      // ✅ Pointer can be reassigned to point to y
    ```
  </Card>

  <Card title="Trap 3 — Integer Overflow in Mid Calculation" icon="error">
    In DSA (e.g., Binary Search), `mid = (start + end) / 2` can overflow.
    
    **✅ Safe Pattern**:
    ```cpp
    int mid = start + (end - start) / 2;  // ✅ Always safe
    // Or C++20: std::midpoint(start, end)
    ```
  </Card>

  <Card title="Trap 4 — Static Initialization Order" icon="error">
    Global statics across files have unspecified init order:
    ```cpp
    // file1.cpp
    extern int x;
    int y = x + 1;  // ⚠️ x may not be initialized yet!

    // file2.cpp
    int x = 42;
    ```
    ✅ **Fix**: Use function-local static (Meyer's singleton) — initialized on first use, thread-safe (C++11).
  </Card>

  <Card title="Trap 5 — Dangling Reference/Pointer" icon="error">
    Returning address of local variable = dangling pointer:
    ```cpp
    int* getBad() {
        int x = 10;
        return &x;  // 💥 x destroyed at end of function — dangling pointer!
    }

    // ✅ Safe alternatives:
    int getValue() { return 10; }  // Return by value
    std::unique_ptr<int> getSmart() { return std::make_unique<int>(10); }
    ```
  </Card>
</CardGrid>

## ⚡ DSA Patterns & Variable Usage

Variables play specific roles in algorithmic design. C++ gives you fine-grained control for performance.

<CardGrid>
  <Card title="Pattern: Static Global State for DFS" icon="rocket">
    Use `static` or global variables to track results across recursive calls without passing parameters.
    ```cpp
    static int maxVal = std::numeric_limits<int>::min();
    
    void dfs(TreeNode* node) {
        if (!node) return;
        maxVal = std::max(maxVal, node->val);  // Updates shared state
        dfs(node->left); 
        dfs(node->right);
    }
    // ⚠️ Reset maxVal between test cases in competitive programming!
    ```
  </Card>
  
  <Card title="Pattern: Pass-by-const-reference for Large Data" icon="shield">
    Avoid copying large structures in recursive/backtracking functions.
    ```cpp
    // ❌ Expensive: copies vector at each call
    void backtrack(std::vector<int> path) { ... }
    
    // ✅ Efficient: read-only alias, no copy
    void backtrack(const std::vector<int>& path, int depth) {
        // path.push_back(x);  // ❌ Error: const
        // Use local copy if mutation needed:
        auto newPath = path;
        newPath.push_back(depth);
        backtrack(newPath, depth+1);
    }
    ```
  </Card>

  <Card title="Pattern: Mutable for Cached Results" icon="backspace">
    Use `mutable` to allow modification inside `const` methods (e.g., memoization).
    ```cpp
    class Calculator {
        mutable std::unordered_map<int, int> cache;
    public:
        int compute(int x) const {
            if (cache.count(x)) return cache[x];  // ✅ Allowed: mutable
            int result = expensive(x);
            cache[x] = result;  // ✅ Cache update in const method
            return result;
        }
    };
    ```
  </Card>

  <Card title="Pattern: constexpr for Compile-Time Computation" icon="approve-check">
    Move DSA precomputation to compile-time with `constexpr`.
    ```cpp
    constexpr int fib(int n) {
        return (n <= 1) ? n : fib(n-1) + fib(n-2);
    }
    constexpr int fib10 = fib(10);  // ✅ Computed at compile-time!
    // Zero runtime cost — value embedded in binary
    ```
  </Card>
</CardGrid>

## 🎯 Interview Cheat Sheet

<CardGrid>
  <Card title="Where are variables stored?" icon="information">
    - **Automatic (local)** → Stack (fast, auto-destroyed on scope exit)
    - **Static** → Data segment (`.bss`/`.data`, program lifetime)
    - **Thread-local** → TLS segment (per-thread, C++11)
    - **Dynamic** → Heap (manual/RAII lifetime)
    - **Member variables** → Part of object (stack if object is local, heap if `new`)
  </Card>

  <Card title="Pass-by-value or reference?" icon="warning">
    **C++ supports both** — choose wisely:
    - Small types (`int`, pointers): **pass-by-value**
    - Large types (`std::string`, containers): **pass-by-const-reference** (read) or **reference** (write)
    - Optional/nullable: **pointer** or `std::optional<T>`
    - Want to steal: **rvalue reference** + `std::move`
  </Card>

  <Card title="Can primitive be nullptr?" icon="error">
    **No.** Only pointers and references to objects can be null (references cannot be null by design).
    ```cpp
    int x = nullptr;        // ❌ Compile error
    int* p = nullptr;       // ✅ Pointer can be null
    std::optional<int> opt; // ✅ C++17: can be empty (no value)
    ```
  </Card>

  <Card title="const vs constexpr vs consteval?" icon="approve-check">
    - `const`: Runtime immutable (value known at runtime)
    - `constexpr`: Compile-time constant if possible (C++11)
    - `consteval`: Must be compile-time — error if not (C++20)
    ```cpp
    const int a = std::rand();      // ✅ Runtime value, immutable after init
    constexpr int b = 10 + 20;      // ✅ Compile-time constant
    consteval int c() { return 42; } // ✅ Must be evaluable at compile-time
    ```
  </Card>
</CardGrid>

## 🧭 Quick-Revision Cheat Sheet

```text
✅ AUTOMATIC (LOCAL) VARIABLES:
   Declaration: int x;           // ⚠️ GARBAGE VALUE — never read before write!
   Safe init:   int x{};         // ✅ Zero-initialized (C++11 uniform init)
   Scope:       Block { } only   // No function-level scope
   Lifetime:    Destroyed at }   // Stack unwind

✅ STATIC VARIABLES:
   Declaration: static int x;    // One copy, program lifetime
   Init order:  Zero → const → dynamic (unspecified across files!)
   Access:      ClassName::x     // Preferred for class statics
   Thread-safe init: C++11 function-local static ✅

✅ DYNAMIC (HEAP) VARIABLES:
   Raw:         int* p = new int{42}; delete p;  // ⚠️ Manual cleanup
   Smart:       auto p = std::make_unique<int>(42);  // ✅ RAII, auto cleanup
   Container:   std::vector<int> v(5, 0);  // ✅ Preferred for arrays

✅ REFERENCES vs POINTERS:
   Reference:   int& r = x;      // Alias, cannot be null, cannot reseat
   Pointer:     int* p = &x;     // Address, can be nullptr, can reassign
   Rule:        Use reference when null not needed; pointer when optional

✅ PASSING PARAMETERS:
   Small type:      void f(int x)           // Pass-by-value
   Large read-only: void f(const std::string& s)  // Pass-by-const-ref
   Large mutable:   void f(std::vector<int>& v)   // Pass-by-ref
   Optional:        void f(const std::string* s)  // Pass-by-pointer
   Move semantics:  void f(std::string&& s)       // Pass-by-rvalue-ref

⚠️ COMMON TRAPS:
   • Local variables NOT zero-initialized → always use {}
   • Static init order across files is unspecified → use Meyer's singleton
   • Returning address of local → dangling pointer 💥
   • Reference cannot be null or reseated → use pointer if needed
   • int* p = new int; → garbage value! Use new int{} for zero-init

🎯 DSA BEST PRACTICES:
   • Use std::vector for dynamic collections (BFS, sliding window)
   • Pass large structs by const& to avoid copies in recursion
   • Use constexpr for compile-time precomputation (sieves, hashes)
   • Prefer std::optional<T> over raw pointers for nullable returns
   • Use std::midpoint (C++20) for overflow-safe binary search
   • Mark cache members mutable for lazy evaluation in const methods
```

> 🎯 **Interview Pro Tip**: When asked about variables in C++, always mention:  
> 1. The **four storage durations** (automatic, static, thread-local, dynamic) and their lifetimes  
> 2. **Initialization rules** (locals = garbage, statics = zero) — undefined behavior vs. defined defaults  
> 3. **Passing mechanisms** (value, reference, pointer, rvalue-ref) and when to use each  
> 4. **Const-correctness** (`const`, `constexpr`, `consteval`, `mutable`) and compile-time vs. runtime immutability  
> 5. **RAII and smart pointers** as the modern alternative to manual memory management  
> This demonstrates deep understanding of C++'s "zero-overhead" and "trust the programmer" philosophy! 🚀

## 📋 Declaration vs Definition

> Most misunderstood topic in C++ variables.

```
Declaration → tells the compiler: "this name exists, this is its type"
Definition  → actually allocates memory
```

```cpp
extern int x;       // declaration only — no memory allocated
int x;              // definition — memory allocated

extern int x;       // can declare many times ✅
int x;              // can define only ONCE (ODR) ❌ twice = linker error

void foo();         // declaration (function prototype)
void foo() { }      // definition
```

| Statement | Declaration | Definition |
|---|---|---|
| `extern int x;` | ✅ | ❌ |
| `int x;` | ✅ | ✅ |
| `int x = 5;` | ✅ | ✅ |
| `class Foo;` | ✅ | ❌ |
| `class Foo { };` | ✅ | ✅ |

## ⚙️ Storage Classes

### `auto` — Default for Locals

```cpp
auto int x = 5;   // C++03 and before — explicit auto
int x = 5;        // same — auto is default for locals

// C++11: auto = type deduction (completely different meaning)
auto x = 5;       // type deduced as int
auto x = 5.0;     // type deduced as double
auto x = 5.0f;    // type deduced as float
```

> 🔴 `auto` means two different things depending on context — pre-C++11 storage class vs C++11 type deduction.

---

### `static` — Three Different Meanings

```cpp
// Meaning 1: Static local variable
void counter() {
    static int count = 0;   // initialized ONCE, persists across calls
    count++;
    std::cout << count;
}
counter(); // 1
counter(); // 2
counter(); // 3

// Meaning 2: Static global — internal linkage
static int x = 10;   // x is INVISIBLE to other translation units
                     // each .cpp gets its own copy if they declare one

// Meaning 3: Static class member — belongs to class, not instance
class Foo {
    static int count;   // shared across ALL Foo objects
};
int Foo::count = 0;     // defined outside class
```

#### Static Local — Under the Hood

```
First call:
  check hidden flag → not initialized
  → run initializer
  → set flag = initialized
  → flag stored in .bss/.data section

Subsequent calls:
  check hidden flag → already initialized
  → skip initializer
  → use existing value

Thread safety: C++11 guarantees static local init is thread-safe
               (double-checked locking done by compiler)
```

### `extern` — Cross-File Variables

```cpp
// file: config.cpp
int timeout = 5000;      // definition — memory lives here

// file: network.cpp
extern int timeout;      // declaration — "it's defined somewhere"
// now network.cpp can use timeout
```

```
config.o  → DEFINES symbol 'timeout'
network.o → REFERENCES symbol 'timeout' (UNDEFINED)
           ↓
         Linker patches network.o's reference → config.o's address
```

> 🔴 **Global mutable `extern` = shared mutable state across files.** In multithreaded code this is a data race unless protected with `mutex` or `atomic`.

### `thread_local` — Per-Thread Storage (C++11)

```cpp
thread_local int error_code = 0;   // each thread has its OWN copy

// Thread A sets it:
error_code = 404;   // only Thread A's copy changes

// Thread B reads it:
std::cout << error_code;  // → 0 (Thread B's own copy, untouched)
```

```
Memory layout:

Thread A:  [stack] [error_code = 404] [TLS block]
Thread B:  [stack] [error_code = 0  ] [TLS block]
Thread C:  [stack] [error_code = 0  ] [TLS block]
```

**Real use:** errno, random seeds, allocator caches, per-thread logging context.

## 🔒 `const` — Runtime Constant

```cpp
const int x = 5;        // x cannot be modified after init
x = 10;                 // ❌ compile error

const int y = foo();    // ✅ initialized at runtime — value unknown at compile time
```

### `const` With Pointers — 4 Combinations

```cpp
int val = 10;

int*       p1 = &val;   // mutable ptr, mutable data
const int* p2 = &val;   // mutable ptr, CONST data  ← can't change *p2
int* const p3 = &val;   // CONST ptr, mutable data  ← can't change p3
const int* const p4 = &val; // CONST ptr, CONST data

*p2 = 20;    // ❌ data is const
p2  = &other;// ✅ pointer itself can move

*p3 = 20;    // ✅ data is mutable
p3  = &other;// ❌ pointer is const
```

> 🔑 **Read right-to-left** to decode: `const int* const p` = "p is a const pointer to const int"

## ⚡ `constexpr` — Compile-Time Constant

```cpp
constexpr int x = 5;          // ✅ value known at compile time
constexpr int y = x * 2;      // ✅ computed at compile time → 10
constexpr int z = foo();       // ✅ only if foo() is constexpr

int runtime = input();
constexpr int w = runtime;     // ❌ runtime value → not constexpr
```

### `const` vs `constexpr`

```
const:
  → value CAN be runtime
  → compiler MAY use it as compile-time if possible
  → "I won't change this"

constexpr:
  → value MUST be compile-time
  → compiler GUARANTEES it
  → "compute this at compile time"
```

```cpp
int n;
std::cin >> n;

const int a = n;          // ✅ runtime const — value unknown at compile time
constexpr int b = n;      // ❌ n is not constexpr

const int c = 5;          // compiler MIGHT treat as compile-time
constexpr int d = 5;      // compiler MUST treat as compile-time

int arr1[c];              // ✅ or ❌ — implementation defined (usually works)
int arr2[d];              // ✅ always works — d is guaranteed compile-time
```

## 🌀 `volatile` — Prevent Optimization

```cpp
volatile int sensor = 0;    // hardware register or shared memory

// WITHOUT volatile:
while (sensor == 0) { }    // compiler optimizes to: if (sensor==0) while(true){}
                            // because it thinks nothing else changes sensor

// WITH volatile:
volatile int sensor = 0;
while (sensor == 0) { }    // compiler re-reads sensor every loop iteration
```

> 🔴 `volatile` does **NOT** make code thread-safe. It only prevents the compiler from caching the value in a register. Use `std::atomic` for thread safety.

| Use Case | Tool |
|---|---|
| Hardware registers / memory-mapped I/O | `volatile` |
| Thread-safe shared variable | `std::atomic` |
| Both | `volatile std::atomic` |

```cpp
class Cache {
```

## 🎯 Type Deduction — `auto` and `decltype`

### `auto` Rules

```cpp
auto a = 5;           // int
auto b = 5u;          // unsigned int
auto c = 5.0;         // double
auto d = 5.0f;        // float
auto e = 'x';         // char
auto f = true;        // bool
auto g = nullptr;     // std::nullptr_t

const int ci = 5;
auto h = ci;          // int   ← const DROPPED
auto& i = ci;         // const int& ← const preserved via ref
auto* j = &ci;        // const int* ← const preserved via ptr
```

### `decltype` — Exact Type Query

```cpp
int x = 5;
decltype(x) y = 10;         // int — same type as x

const int& ref = x;
decltype(ref) z = x;        // const int& — exact type preserved

decltype(x + 1.0) d;        // double — type of expression

// decltype vs auto difference:
auto    a = ref;             // int   (strips const&)
decltype(ref) b = ref;       // const int& (exact type)
```

### `auto` in Different Contexts

```cpp
// Function return type deduction (C++14)
auto add(int a, int b) { return a + b; }   // returns int

// Structured bindings (C++17)
std::pair<int, std::string> p = {1, "hi"};
auto [id, name] = p;        // id=int, name=string

// Range-based for
std::vector<int> v = {1,2,3};
for (auto x : v)  { }      // x is int (copy)
for (auto& x : v) { }      // x is int& (reference)
for (const auto& x : v) { } // x is const int& (safe, no copy)
```

## 🔬 Under the Hood — Where Variables Live

```
Binary sections:

.text    → compiled code (instructions)
.rodata  → const globals, string literals
.data    → initialized non-const globals and statics
.bss     → zero-initialized globals and statics (no space in binary)
stack    → local (automatic) variables
heap     → dynamic (new/delete) variables
TLS      → thread_local variables
```

```cpp
int    a = 5;              // .data   (initialized global)
int    b;                  // .bss    (zero-init global)
const int c = 5;           // .rodata (read-only)
static int d = 5;          // .data   (file-scope static)

void foo() {
    int e = 5;             // stack   (automatic)
    static int f = 5;      // .data   (static local — NOT stack)
    int* g = new int(5);   // g on stack, *g on heap
}
```

### Stack Frame for Locals

```
foo() stack frame:
┌─────────────────────┐ ← rsp (stack pointer, high address)
│   return address    │
├─────────────────────┤
│   saved rbp         │
├─────────────────────┤
│   local int a       │ rbp - 4
├─────────────────────┤
│   local int b       │ rbp - 8
├─────────────────────┤
│   local char c      │ rbp - 12  (padded to 4 bytes)
└─────────────────────┘ ← rsp (low address)

Born:  when foo() is called (rsp adjusted)
Dies:  when foo() returns (rsp restored)
```

## 🏭 Real-World Production Scenario

**Static initialization order fiasco:**

```cpp
// file_a.cpp
int timeout = 5000;          // global definition

// file_b.cpp
extern int timeout;
int retry_limit = timeout / 1000;  // ❌ FIASCO
                                    // timeout may not be initialized yet
                                    // order of global init across files = undefined
                                    // retry_limit might be 0 or garbage
```

**Fix 1 — `constinit` (C++20):**
```cpp
constinit int timeout = 5000;  // guaranteed initialized before any code runs
```

**Fix 2 — Initialization function (classic fix):**
```cpp
int get_timeout() {
    static int timeout = 5000;  // initialized on first call — guaranteed safe
    return timeout;
}
int retry_limit = get_timeout() / 1000;  // ✅ safe
```

## 🎯 Interview Traps

**Trap 1:**
```cpp
static int x = 0;

void foo() {
    static int x = 0;    // same name — which x?
    x++;
    std::cout << x;
}
foo(); foo(); foo();      // prints?
```
> Prints `1 2 3`. The `static int x` inside `foo` is a **different variable** from the file-scope `static int x`. Local scope shadows. Each call increments the local static.

**Trap 2:**
```cpp
void foo() {
    const int x = 5;
    int* p = const_cast<int*>(&x);
    *p = 10;                    // UB or fine?
    std::cout << x;             // prints 5 or 10?
}
```
> **UB** — `x` was originally declared `const`. Even if it's on the stack (not `.rodata`), modifying a `const` object via `const_cast` is UB. The compiler may print `5` because it replaced `x` with literal `5` at compile time.

**Trap 3:**
```cpp
int x = 10;
void foo() {
    std::cout << x;     // prints?
    int x = 20;
}
```
> ❌ **Compile error** in some compilers, UB in old ones. In C++, the local `x` declaration makes the name `x` refer to the local variable for the **entire** block — including lines before its declaration. Actually in C++ this is just fine - the local `x` is declared after the use, so the `std::cout << x` refers to the global `x`. Wait, actually in C++ the scope of a local variable starts at its declaration point, not the start of the block (unlike Java). So `std::cout << x` sees the global `x = 10`, prints `10`. Then `int x = 20` declares local x. This is valid C++. Prints `10`.

> Prints `10`. In C++, a local variable's scope starts **at its declaration**, not at the start of the block. So `std::cout << x` above the declaration sees the global `x`.

**Trap 4:**
```cpp
thread_local std::vector<int> cache;

void foo() {
    cache.push_back(1);     // safe?
}
```
> `thread_local` objects with non-trivial constructors/destructors: construction happens on first use per thread, destruction at thread exit. If the thread exits while holding resources that the destructor touches (file handles, mutexes), order of destruction vs other thread-local objects is **implementation-defined** — silent resource leaks in thread pools.
