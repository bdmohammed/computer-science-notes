## What is an Identifier?

**Definition:** An identifier is any name you give to something in your program.
```c++
int age = 25;
    ───
     └── this is an identifier

void calculateSalary() { ... }
     ───────────────
            └── this is an identifier
```

| Used For                 | Example                 | Identifier     |
| ------------------------ | ----------------------- | -------------- |
| Variables                | `int age = 25;`         | `age`          |
| Functions                | `void calculateSum()`   | `calculateSum` |
| Classes                  | `class BankAccount {}`  | `BankAccount`  |
| Structs                  | `struct Node {}`        | `Node`         |
| Unions                   | `union Data {}`         | `Data`         |
| Enums                    | `enum Color { RED };`   | `Color`        |
| Enum Values              | `RED`, `GREEN`          | `RED`, `GREEN` |
| Namespaces               | `namespace myapp {}`    | `myapp`        |
| Templates                | `template<typename T>`  | `T`            |
| Template Classes         | `vector<int>`           | `vector`       |
| Template Functions       | `max<int>(a, b)`        | `max`          |
| Type Aliases (`using`)   | `using ll = long long;` | `ll`           |
| Type Aliases (`typedef`) | `typedef int Integer;`  | `Integer`      |
| Constants                | `const int MAX = 10;`   | `MAX`          |
| Macros                   | `#define MAX_SIZE 100`  | `MAX_SIZE`     |
| Labels                   | `loop:`                 | `loop`         |
| Objects                  | `BankAccount acc;`      | `acc`          |
| References               | `int& ref = age;`       | `ref`          |
| Pointers                 | `int* ptr;`             | `ptr`          |
| Member Variables         | `this->balance`         | `balance`      |
| Member Functions         | `obj.deposit()`         | `deposit`      |
| Constructors             | `BankAccount()`         | `BankAccount`  |
| Destructors              | `~BankAccount()`        | `BankAccount`  |
| Operator Overloads       | `operator+`             | `operator+`    |
| Friend Functions         | `friend void show();`   | `show`         |
| Lambda Variables         | `auto add = [](){}`     | `add`          |


### Example Breakdown

```c++
#include <iostream>

int main() {
    int x = 10;
    std::cout << "Hello World";
    return 0;
}
```

| Identifier | Purpose     |
| ---------- | ----------- |
| `iostream` | header name |
| `main`     | function    |
| `x`        | variable    |
| `std`      | namespace   |
| `cout`     | object      |


Things That Are NOT Identifiers ❌
| Thing       | Example                 |
| ----------- | ----------------------- |
| Keywords    | `if`, `class`, `return` |
| Operators   | `+`, `*`, `=`           |
| Literals    | `10`, `"hello"`         |
| Punctuation | `;`, `{}`, `()`         |


<Aside type="tip" title="Remember">
**Identifier = Just a NAME**  
But the compiler treats it as a **MEMORY REFERENCE**.
</Aside>

## The 6 Golden Rules ⭐

### Rule 1 — Allowed Characters

Only these types are allowed:

```
Letters    : a–z, A–Z
Digits     : 0–9
Underscore : _
```

<Aside type="caution">
Using anything else (`Special Keyword (#, @, %)`, `Contain spaces`, `Contain operators`, `Reserved keyword`, `boolean literal`, `Null literal`) → **Compile Time Error**
</Aside>

```c++
✅ total_number
❌ Total#         // C.E.
```

---

### Rule 2 — Starting Character

Cannot start with a digit (`0–9`).

C++ identifiers can start with:
- ✅ Can start with:
	- letter (a-z, A-Z)
	- underscore (_)
- ❌ Cannot start with:
	- digit

**Yes — modern C++ DOES support Unicode identifiers ✅
But historically it was less consistent than Java.**

```c++
✅ ABC123   // Valid    → treated as identifier
❌ 123ABC   // Invalid  → treated as a number

Identifiers beginning with:
    _ + uppercase letter
    __ (double underscore)
are always reserved for the implementation (compiler, standard library) — you should never use them.

Names starting with _ at global scope are reserved for the implementation/compiler/library.
```

---

### Rule 3 — Case Sensitivity

C++ is **case sensitive**.

```c++
abc ≠ ABC ≠ Abc

int number = 10;   // different from →
int Number = 20;
```

---

### Rule 4 — Length Limit

Technically **no limit**, but keep it readable.

```c++
numberOfStudents                            // ✅ Good
n                                           // ❌ Too vague
numberOfStudentsInEngineeringDepartment2024 // ❌ Too long
```

<Aside type="tip">
Best practice: keep identifiers **under 15 characters**.
</Aside>

---

### Rule 5 — Reserved Words

Cannot use C++ **keywords** as identifiers.

```c++
❌ int if = 10;  // invalid
```

---

### Rule 6 — Predefined Class Names

You **can** use predefined class names as identifiers — but avoid it.

```c++
✅ int String = 10;  // compiles, outputs 10
⚠️  Legal but bad practice — very confusing
```

## Special Characters Deep Dive
### 🌍 Global Scope Extra Restriction

<Aside type="danger">
At global scope, identifiers starting with _ (single underscore, any case after) are also reserved.
</Aside>

```c++
int _global = 5;      // ❌ reserved at global scope

int main() {
    int _local = 5;   // ✅ fine inside function scope
}
```

### ⚠️ Reserved — Technically Undefined Behavior to Use

<Aside type="danger">
These are not keywords but the standard reserves them. Using them = UB or implementation-defined behavior.
</Aside>

## Naming Conventions

> Not enforced by the compiler — but **mandatory in real-world SDE work**.
```
| Used For           | Common Convention            | Example                 |
| ------------------ | ---------------------------- | ----------------------- |
| Variables          | `snake_case`                 | `user_age`              |
| Functions          | `snake_case`                 | `calculate_salary()`    |
| Classes            | `PascalCase`                 | `BankAccount`           |
| Structs            | `PascalCase`                 | `Node`                  |
| Enums              | `PascalCase`                 | `Color`                 |
| Enum Values        | varies (`UPPER_CASE` common) | `RED`                   |
| Constants          | `UPPER_CASE`                 | `MAX_SIZE`              |
| Macros             | `UPPER_CASE`                 | `BUFFER_SIZE`           |
| Namespaces         | `snake_case` / lowercase     | `myapp`                 |
| Templates          | Single uppercase letter      | `T`, `U`                |
| Type Aliases       | `snake_case` or `PascalCase` | `ll`, `StringList`      |
| Member Variables   | `m_` or trailing `_`         | `m_balance`, `balance_` |
| Private Variables  | trailing `_` common          | `size_`                 |
| Global Variables   | `g_` prefix sometimes        | `g_counter`             |
| Files/Header Files | `snake_case`                 | `bank_account.cpp`      |
| Header Guards      | `UPPER_CASE`                 | `BANK_ACCOUNT_H`        |
```

# 🔬 Under the Hood — What the Compiler Does With Identifiers

---

## 🗺️ The Full Pipeline

```
your_file.cpp
      │
      ▼
┌─────────────────┐
│  Preprocessor   │  → strips comments, expands macros, handles #include
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│     Lexer       │  → breaks source into TOKENS
└────────┬────────┘    (this is where identifiers are first seen)
         │
         ▼
┌─────────────────┐
│     Parser      │  → builds AST (Abstract Syntax Tree)
└────────┬────────┘    (identifiers get roles: variable, function, type...)
         │
         ▼
┌─────────────────┐
│Semantic Analyzer│  → checks types, scopes, builds Symbol Table
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│   Code Generator│  → converts AST → IR → machine code
└────────┬────────┘    (identifiers become addresses / registers)
         │
         ▼
┌─────────────────┐
│  Name Mangler   │  → encodes identifier + type signature → symbol name
└────────┬────────┘
         │
         ▼
      .o file  (object file — machine code + symbol table)
         │
         ▼
┌─────────────────┐
│     Linker      │  → resolves symbols across .o files → final binary
└────────┬────────┘
         │
         ▼
    executable (ELF / PE / Mach-O)
```

## 🔤 Step 1 — Lexer: Identifier → Token

The lexer scans your source **character by character**.

```
Source: int age = 25;

Lexer output:
┌──────────┬─────────────────┐
│  Token   │   Type          │
├──────────┼─────────────────┤
│  int     │  KEYWORD        │
│  age     │  IDENTIFIER     │
│  =       │  OPERATOR       │
│  25      │  INTEGER_LITERAL│
│  ;       │  PUNCTUATION    │
└──────────┴─────────────────┘
```

The lexer uses this rule to identify an IDENTIFIER token:

```
if (current_char is letter or '_')
    keep reading while (letter or digit or '_')
    → emit IDENTIFIER token

then check: is this token a keyword?
    yes → emit KEYWORD token instead
    no  → it's a user-defined identifier
```

> 🔑 At the lexer stage, identifiers are just **strings**. No meaning yet.

---

## 🌳 Step 2 — Parser: Identifier Gets a Role

The parser builds an **Abstract Syntax Tree (AST)**.

```cpp
int age = 25;
```

```
AST:
        VarDecl
        /      \
    Type        Init
    "int"       /  \
             Name   Value
             "age"   25
```

```cpp
void foo(int x) { return x + 1; }
```

```
AST:
        FunctionDecl
        /     |     \
    Name    Params  Body
    "foo"     |       \
            ParmDecl  ReturnStmt
            /   \        \
          Type  Name    BinaryOp
          "int" "x"     /     \
                      DeclRef  IntLiteral
                       "x"       1
```

> 🔑 Same string `"x"` appears twice — the parser connects both uses to the **same declaration node**. This is called **name resolution**.

---

## 🗃️ Step 3 — Symbol Table: The Compiler's Dictionary

The semantic analyzer builds a **Symbol Table** — a data structure that maps every identifier to its properties.

```
Symbol Table (conceptually a scoped hash map):

┌─────────────┬──────────┬───────────┬──────────┬──────────────┐
│  Name       │  Kind    │  Type     │  Scope   │  Address/Reg │
├─────────────┼──────────┼───────────┼──────────┼──────────────┤
│  age        │  var     │  int      │  local   │  rbp-4       │
│  foo        │  func    │  int(int) │  global  │  0x401120    │
│  Student    │  class   │  —        │  global  │  —           │
│  x          │  param   │  int      │  foo     │  edi (reg)   │
└─────────────┴──────────┴───────────┴──────────┴──────────────┘
```

### Scoped Symbol Table — Nested Structure

```
Global scope
│
├── foo()  scope
│     ├── x     (param)
│     └── temp  (local var)
│
└── bar()  scope
      └── x     (different x — same name, different scope)
```

Each scope is a separate **hash map**. Lookup goes from **innermost → outward** until found or error.

```cpp
int x = 10;          // global scope → symbol table entry #1

void foo() {
    int x = 20;      // local scope → symbol table entry #2
    // compiler sees 'x' → checks local first → finds #2
    // global x is SHADOWED
}
```

## 🏷️ Step 4 — Name Mangling: The Big One

C allows two functions with the same name? No — C doesn't allow overloading.
C++ allows overloading — `foo(int)` and `foo(double)` can coexist.

But the **linker** only knows symbols as strings. So how does it distinguish them?

**Name Mangling** — the compiler **encodes type information into the symbol name**.

### Raw Example

```cpp
void foo(int x);        // mangled → _Z3fooi
void foo(double x);     // mangled → _Z3food
void foo(int, double);  // mangled → _Z3fooid
int  bar();             // mangled → _Z3barv
```

### Mangling Decode Table (Itanium ABI — used by GCC + Clang)

```
_Z          → mangled C++ symbol prefix
3           → length of name (3 chars = "foo")
foo         → the identifier itself
i           → int
d           → double
v           → void
c           → char
f           → float
l           → long
PKc         → const char* (P=pointer, K=const, c=char)
```

### Class Methods

```cpp
class Student {
    void enroll(int courseId);  // → _ZN7Student6enrollEi
};
```

```
_Z          → mangled
N           → nested name (class::method)
7Student    → class name (7 chars)
6enroll     → method name (6 chars)
E           → end of nested name
i           → int param
```

### See It Live

```bash
# compile
g++ -c main.cpp -o main.o

# view mangled symbols
nm main.o

# demangle — read human form
nm main.o | c++filt
```

## 🔗 Step 5 — Linker: Symbol Resolution

Each `.o` file has two lists:

```
main.o:
┌────────────────────────────────────┐
│ DEFINED symbols  (I provide these) │
│   _Z3fooi                          │
│   main                             │
├────────────────────────────────────┤
│ UNDEFINED symbols (I need these)   │
│   _ZNSt6vectorIiE9push_backEi      │  ← std::vector::push_back
│   printf                           │
└────────────────────────────────────┘
```

The linker's job:

```
For every UNDEFINED symbol in every .o file:
  → find a .o or .lib/.a that DEFINES it
  → patch the address in

If any symbol stays UNDEFINED → Linker Error: undefined reference to '...'
If any symbol is defined TWICE → Linker Error: multiple definition of '...'
```

---

## 📍 Step 6 — Identifier Becomes an Address

After linking, your identifier `age` no longer exists as a string anywhere in the binary.

```
Source:               int age = 25;
After compilation:    mov DWORD PTR [rbp-4], 25
In binary:            C7 45 FC 19 00 00 00
```

`age` → **gone**. Replaced by a **stack offset** (`rbp-4`) or a **memory address** or a **register**.

```
Local variable  → stack offset  (rbp - N)
Global variable → absolute address in .data or .bss section
Function        → address in .text section
Constant        → address in .rodata section
```

## 🔐 `extern "C"` — Disabling Mangling

```cpp
extern "C" void foo(int x);   // symbol stays: foo
                               // NOT: _Z3fooi
```

Why this exists:

```
C++ binary ──► calls ──► C library
C library exports symbol: "foo"
C++ would look for: "_Z3fooi"
→ linker can't find it → error

extern "C" tells the compiler:
"don't mangle this — keep the symbol name as-is"
```

> 🔑 Every C header wrapped in C++ uses this:
> ```cpp
> #ifdef __cplusplus
> extern "C" {
> #endif
>   // C declarations here
> #ifdef __cplusplus
> }
> #endif
> ```

## 🔴 ODR — One Definition Rule

Every identifier (that's a definition, not just a declaration) must be defined **exactly once** across all translation units.

```
Translation unit = one .cpp file after preprocessing
```

```cpp
// a.cpp
int counter = 0;    // definition

// b.cpp
int counter = 0;    // definition of SAME name

// Link: error — multiple definition of 'counter'
```

```cpp
// a.cpp
int counter = 0;     // definition

// b.cpp
extern int counter;  // declaration only — "it exists somewhere"
// ✅ fine — linker finds it in a.cpp
```

## 🎯 Interview Trap — Non-Obvious

**Q: If identifiers disappear in the binary, how does a debugger show variable names?**

> The binary has a **debug info section** (DWARF on Linux, PDB on Windows).
> This section maps addresses back to source line numbers and identifier names.
> It's completely separate from the executable code.

```bash
g++ -g main.cpp      # -g = include DWARF debug info
objdump --dwarf main  # see the mapping
```

> Without `-g`, identifiers are **completely gone** from the binary. The debugger would show raw addresses only.

## 🏭 Production Scenario

At a company, you get a crash report:

```
Segfault at address 0x00401A3C
```

Steps an SRE/SDE takes:

```
1. addr2line -e binary 0x00401A3C
   → src/network/socket.cpp:247

2. nm binary | grep 0x00401A3C
   → _ZN7Network6Socket7connectERKNSt7__cxx1112basic_stringIcSt11char_traitsIcESaIcEEE

3. c++filt _ZN7Network6Socket7connectERKNSt7__cxx1112basic_stringIcSt11char_traitsIcESaIcEEE
   → Network::Socket::connect(std::string const&)

4. Now you know: crash is in Network::Socket::connect at line 247
```

> 🔑 `nm`, `c++filt`, `addr2line` — three tools every C++ SDE must know.

## 📊 Summary

```
Stage           │ What happens to your identifier
────────────────┼───────────────────────────────────────────────
Lexer           │ Becomes a token (just a string)
Parser          │ Gets a role in the AST (var, func, type...)
Semantic Anal.  │ Enters the Symbol Table with scope + type
Name Mangler    │ Encoded into a unique symbol string
Code Generator  │ Replaced by stack offset / register / address
Linker          │ Symbol matched across .o files, address patched
Final Binary    │ Identifier is GONE — only addresses remain
Debugger (DWARF)│ Identifier lives again — in debug section only
```
