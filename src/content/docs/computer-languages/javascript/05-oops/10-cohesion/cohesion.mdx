## 🧲 Cohesion in JavaScript — The Module Era

> **Cohesion** measures how closely related the responsibilities of a module (or class) are.  
> In Java, we talk about Class Cohesion.  
> In **JavaScript**, we talk about **Module Cohesion**.  
> **High Cohesion**: A module does one thing well.  
> **Low Cohesion**: A module is a "God Object" or "Utils Dump."

<Aside type="tip" title="🧠 Mental Model">
**Focus vs. Chaos**:  
- **High Cohesion**: A specialized tool (e.g., `dateFormatter.js`). Easy to find, easy to test.  
- **Low Cohesion**: A junk drawer (`utils.js`). Contains dates, math, strings, and API calls. Hard to maintain.  
**Goal**: "High Cohesion, Low Coupling."
</Aside>

---

## 📋 Types of Cohesion in JS

| Type | Description | Verdict | Example |
|------|-------------|---------|---------|
| **Coincidental** | Random functions grouped together | 🔴 Worst | `utils.js` with `formatDate`, `calcTax`, `resizeImg` |
| **Logical** | Grouped by vague category | 🟠 Bad | `inputHandlers.js` (mouse, network, file) |
| **Temporal** | Grouped by lifecycle (init/cleanup) | 🟡 Moderate | `appInit.js` (DB connect, cache warm, server start) |
| **Communicational** | Operate on same data/context | 🟢 Good | `userProfile.js` (updateName, updateEmail) |
| **Functional** | All parts contribute to ONE task | 🟢 Best | `jwtService.js` (sign, verify, decode) |

## 1️⃣ Coincidental Cohesion — The "Utils" Trap

In JS, it's tempting to dump unrelated helper functions into a single file.

<Code lang="js" title="❌ Low Cohesion: The 'Utils' Dump" code={`
// utils.js
export function formatDate(date) { ... }
export function calculateTax(order) { ... }
export function resizeImage(file) { ... }
export function isValidEmail(email) { ... }

// Why it's bad:
// 1. Importing one function bundles the whole file (if not tree-shaken)
// 2. No logical relationship between date formatting and image resizing
// 3. Becomes a dumping ground for "miscellaneous" code
`} />

### ✅ The Fix: Domain-Specific Modules

<Code lang="js" title="✅ High Cohesion: Split by Domain" code={`
// dateUtils.js
export function formatDate(date) { ... }
export function parseISO(str) { ... }

// financeUtils.js
export function calculateTax(order) { ... }
export function formatCurrency(amount) { ... }

// imageUtils.js
export function resizeImage(file) { ... }

// Usage:
import { formatDate } from './dateUtils.js';
import { calculateTax } from './financeUtils.js';
`} />

## 2️⃣ Logical Cohesion — Vague Categories

Grouping things because they "feel" similar, even if they do different things.

<Code lang="js" title="❌ Logical Cohesion: Broad Handlers" code={`
// inputHandlers.js
export function handleMouseClick(e) { ... }
export function handleNetworkPacket(p) { ... } // Unrelated!
export function handleFileUpload(f) { ... }    // Unrelated!

// "Handling input" is too broad. Network logic != UI logic.
`} />

### ✅ The Fix: Split by Context

<Code lang="js" title="✅ High Cohesion: Contextual Modules" code={`
// uiEvents.js
export function handleMouseClick(e) { ... }

// networkService.js
export function handlePacket(p) { ... }

// fileService.js
export function handleUpload(f) { ... }
`} />

## 3️⃣ Functional Cohesion — The Gold Standard

All functions in a module contribute to a single, well-defined task.

<Code lang="js" title="✅ Functional Cohesion: JWT Service" code={`
// jwtService.js
import jwt from 'jsonwebtoken';

const SECRET = process.env.JWT_SECRET;

export function sign(payload) {
    return jwt.sign(payload, SECRET, { expiresIn: '1h' });
}

export function verify(token) {
    try {
        return jwt.verify(token, SECRET);
    } catch (err) {
        return null;
    }
}

export function decode(token) {
    return jwt.decode(token);
}

// Every function here relates to JWT manipulation.
// If JWT logic changes, this is the ONLY file you touch.
`} />

## 4️⃣ Class Cohesion in JS

If you use ES6 Classes, the same rules apply. A class should have a single responsibility.

<Code lang="js" title="❌ Low Cohesion: God Class" code={`
class UserManager {
    constructor(db, emailer) {
        this.db = db;
        this.emailer = emailer;
    }

    // Auth
    login(user, pass) { ... }
    
    // Profile
    updateEmail(id, email) { ... }
    
    // Billing
    chargeUser(id, amount) { ... }
    
    // Analytics
    trackLogin(id) { ... }
}
// This class changes for Auth reasons, Billing reasons, AND Analytics reasons.
`} />

### ✅ The Fix: Split Responsibilities

<Code lang="js" title="✅ High Cohesion: Focused Classes" code={`
class AuthService {
    login(user, pass) { ... }
}

class ProfileService {
    updateEmail(id, email) { ... }
}

class BillingService {
    chargeUser(id, amount) { ... }
}

// Each class has ONE reason to change.
`} />

## 🧩 DSA & Practical Patterns

<CardGrid>
  <Card title="Pattern: Functional Composition" icon="rocket">
```js
    // High cohesion functions can be composed
    const sanitize = (str) => str.trim().toLowerCase();
    const validate = (str) => str.length > 5;
    const hash = (str) => btoa(str);

    // Cohesive pipeline
    const processInput = (input) => {
        const clean = sanitize(input);
        if (!validate(clean)) throw new Error("Invalid");
        return hash(clean);
    };
```
  </Card>
  
  <Card title="Pattern: Module Encapsulation" icon="shield">
```js
    // dbModule.js
    // Internal state is hidden (High Cohesion)
    let connection = null;

    export async function connect() {
        connection = await createConnection();
    }

    export async function query(sql) {
        if (!connection) throw new Error("Not connected");
        return connection.execute(sql);
    }
    
    // Users don't know HOW it connects, just THAT it queries.
```

## 🔑 Quick Reference Summary

### Cohesion Checklist

| Question | Yes/No | Action |
|----------|--------|--------|
| Does this module do one thing? | ✅ | Keep it. |
| Does it do 3 unrelated things? | ❌ | Split it. |
| Are functions named vaguely (`handle`, `process`)? | ❌ | Rename or refactor. |
| Do methods share no state/data? | ❌ | Move them to separate modules. |
| Is it named `Utils` or `Helper`? | ⚠️ | Check for coincidental cohesion. |

### Refactoring Steps

1. ✅ **Identify God Modules**: Look for large files with unrelated imports.
2. ✅ **Extract Domains**: Move related functions to new files (e.g., `dateUtils.js`).
3. ✅ **Use ES Modules**: `export` only what’s needed. Keep internal logic private.
4. ✅ **Compose**: Import small, cohesive modules where needed.

<Aside type="caution">
**Final Checklist for High Cohesion**:
1. ✅ **One Purpose**: Each module/class has a single, clear responsibility.
2. ✅ **Related Data**: Methods operate on the same data/context.
3. ✅ **Clear Naming**: Module name reflects its specific job (e.g., `JwtService`, not `AuthHelper`).
4. ✅ **Easy to Test**: You can test the module without mocking half the app.
</Aside>

## 🔰 What Is Cohesion?

Cohesion = **how strongly related and focused the responsibilities within a single module, class, or function are**. High cohesion = everything in a unit belongs together and works toward one clear purpose.

```js
// LOW cohesion — one class does everything unrelated:
class AppUtils {
  formatDate(date)        { }   // date formatting
  sendEmail(to, body)     { }   // email sending
  hashPassword(password)  { }   // security
  parseCSV(data)          { }   // file parsing
  calculateTax(amount)    { }   // finance
  renderButton(label)     { }   // UI
}
// "AppUtils" = a junk drawer — zero shared purpose 😱

// HIGH cohesion — one class, one focused purpose:
class DateFormatter {
  format(date, pattern)   { }
  parse(str, pattern)     { }
  toRelative(date)        { }
  toISO(date)             { }
}
// Everything relates to date formatting ✅
```

## 1️⃣ Cohesion Types — From Worst to Best

### Type 1: Coincidental Cohesion — Worst

```js
// Elements grouped by chance — no relationship:
class MiscHelpers {
  // What do these have in common? NOTHING:
  formatDate(date)           { return date.toISOString(); }
  hashPassword(pw)           { return crypto.createHash("sha256").update(pw).digest("hex"); }
  parseCSV(text)             { return text.split("\n").map(r => r.split(",")); }
  renderSpinner()            { return "<div class='spinner'></div>"; }
  calculateCompoundInterest(p, r, n, t) { return p * (1 + r/n) ** (n*t); }
  connectDatabase(url)       { return new Pool({ connectionString: url }); }
}

// Problems:
// → No shared purpose → any change touches unrelated things
// → Impossible to name accurately ("Helpers", "Utils", "Misc" = red flags)
// → Grows without bound — everyone adds to it
// → Tests cover unrelated cases in one file
// → Cannot reuse parts without importing everything

// Fix: extract each group into its own cohesive unit
```

### Type 2: Logical Cohesion — Grouped by Type Not Purpose

```js
// All "input handling" — but completely different domains:
class InputHandlers {
  handleKeyboard(event)    { return this.#processKeyEvent(event); }
  handleMouse(event)       { return this.#processMouseEvent(event); }
  handleTouch(event)       { return this.#processTouchEvent(event); }
  handleFormSubmit(event)  { return this.#processFormData(event); }
  handleFileUpload(files)  { return this.#processFiles(files); }
  // "input handling" — logical category but wrong grouping
  // Keyboard and file upload share no meaningful state or logic
}

// Better — group by domain/feature, not by type:
class FormHandler {
  #validators; #sanitizers;
  constructor({ validators, sanitizers }) {
    this.#validators = validators;
    this.#sanitizers = sanitizers;
  }
  submit(event) { /* form-specific logic */ }
  upload(files) { /* file handling deeply tied to form */ }
  validate(data) { /* form validation */ }
}
// Everything serves ONE form-handling purpose ✅
```

### Type 3: Temporal Cohesion — Grouped by When, Not Why

```js
// Startup routine — things that happen at the same time:
class AppInitializer {
  async initialize() {
    await this.#connectDatabase();    // DB concern
    await this.#loadConfig();         // config concern
    await this.#startServer();        // HTTP concern
    await this.#scheduleJobs();       // scheduler concern
    await this.#warmupCache();        // cache concern
    await this.#registerPlugins();    // plugin concern
  }
}
// Grouped because they run at startup — not because they're related
// Change DB startup → touch the same class as server startup 😱

// Better — orchestrate cohesive units:
class Application {
  #db; #config; #server; #scheduler; #cache; #plugins;

  constructor({ db, config, server, scheduler, cache, plugins }) {
    this.#db         = db;
    this.#config     = config;
    this.#server     = server;
    this.#scheduler  = scheduler;
    this.#cache      = cache;
    this.#plugins    = plugins;
  }

  async start() {
    await this.#config.load();        // Config cohesive unit
    await this.#db.connect();         // DB cohesive unit
    await this.#cache.warmup();       // Cache cohesive unit
    await this.#plugins.initialize(); // Plugin cohesive unit
    await this.#scheduler.start();    // Scheduler cohesive unit
    await this.#server.listen();      // Server cohesive unit
  }
}
// Orchestrator delegates to cohesive units ✅
```

### Type 4: Procedural Cohesion — Grouped by Execution Sequence

```js
// Steps that happen in sequence but serve different concerns:
class OrderProcessor {
  process(order) {
    this.#validateOrder(order);       // validation concern
    this.#checkInventory(order);      // inventory concern
    this.#chargePayment(order);       // payment concern
    this.#updateInventory(order);     // inventory concern (again)
    this.#createShipment(order);      // shipping concern
    this.#sendNotification(order);    // notification concern
    this.#updateAnalytics(order);     // analytics concern
  }
}
// Looks like a pipeline but mixes 6 different concerns
// Each step belongs to a different domain

// Better — pipeline with cohesive steps:
class OrderPipeline {
  #steps;
  constructor(steps) { this.#steps = steps; }

  async run(order) {
    for (const step of this.#steps) {
      await step.execute(order); // each step is its own cohesive unit
    }
  }
}

// Each step is internally cohesive:
class ValidateOrderStep {
  execute(order) { /* ONLY validation logic */ }
}
class ChargePaymentStep {
  #paymentGateway;
  execute(order) { /* ONLY payment logic */ }
}
```

### Type 5: Communicational Cohesion — Operate on Same Data

```js
// Better — all methods work on the same order data:
class OrderCalculator {
  #taxRates; #discountRules;

  constructor({ taxRates, discountRules }) {
    this.#taxRates      = taxRates;
    this.#discountRules = discountRules;
  }

  subtotal(order)       { return order.items.reduce((s, i) => s + i.price * i.qty, 0); }
  discount(order)       { return this.#discountRules.apply(order, this.subtotal(order)); }
  tax(order)            { return (this.subtotal(order) - this.discount(order)) * this.#taxRates.get(order.region); }
  shipping(order)       { return order.items.reduce((s, i) => s + i.weight, 0) * 0.5; }
  total(order)          { return this.subtotal(order) - this.discount(order) + this.tax(order) + this.shipping(order); }
  breakdown(order)      {
    return {
      subtotal:  this.subtotal(order),
      discount:  this.discount(order),
      tax:       this.tax(order),
      shipping:  this.shipping(order),
      total:     this.total(order),
    };
  }
}
// All methods operate on the same 'order' data structure ✅
// Cohesive — they share a single data concern
```

### Type 6: Sequential Cohesion — Output of One is Input of Next

```js
// Each method's output feeds the next — pipeline over same data:
class TextProcessor {
  #source;

  constructor(source) { this.#source = source; }

  // Each method transforms same data through a sequence:
  normalize()  { this.#source = this.#source.trim().toLowerCase(); return this; }
  sanitize()   { this.#source = this.#source.replace(/[<>'"&]/g, ""); return this; }
  tokenize()   { this.#tokens = this.#source.split(/\s+/).filter(Boolean); return this; }
  filter(stopWords) {
    this.#tokens = this.#tokens.filter(t => !stopWords.has(t));
    return this;
  }
  stem()       { this.#tokens = this.#tokens.map(t => this.#stemWord(t)); return this; }
  result()     { return this.#tokens; }

  #stemWord(word) {
    // simple stemming
    return word.replace(/ing$|ed$|s$/, "");
  }
}

// Sequential — each step feeds the next, all serve text processing:
const tokens = new TextProcessor("  Running and jumped over FENCES  ")
  .normalize()
  .sanitize()
  .tokenize()
  .filter(new Set(["and", "over"]))
  .stem()
  .result();
// ["run", "jump", "fenc"]
```

### Type 7: Functional Cohesion — Best

```js
// All elements contribute to ONE well-defined function:
class PasswordHasher {
  static #SALT_ROUNDS = 12;
  static #MIN_ENTROPY = 50; // bits

  // ALL of these serve ONE purpose: secure password hashing
  static #calculateEntropy(password) {
    const charsetSize = /[A-Z]/.test(password) ? 26 : 0
      + /[a-z]/.test(password) ? 26 : 0
      + /[0-9]/.test(password) ? 10 : 0
      + /[^A-Za-z0-9]/.test(password) ? 32 : 0;
    return password.length * Math.log2(charsetSize || 1);
  }

  static #validate(password) {
    if (typeof password !== "string") throw new TypeError("Password must be string");
    if (password.length < 8) throw new RangeError("Password too short");
    if (this.#calculateEntropy(password) < this.#MIN_ENTROPY) {
      throw new Error("Password too weak");
    }
  }

  static async hash(password) {
    this.#validate(password);
    return bcrypt.hash(password, this.#SALT_ROUNDS);
  }

  static async verify(password, hash) {
    return bcrypt.compare(password, hash);
  }

  static isStrong(password) {
    return this.#calculateEntropy(password) >= this.#MIN_ENTROPY;
  }
}

// Every method, field, and helper serves ONE purpose:
// secure password operations. Nothing else. ✅

## 5️⃣ Cohesion vs Coupling — The Relationship

```
┌──────────────────────────────────────────────────────────┐
│         COHESION AND COUPLING — INVERSE PRESSURE         │
│                                                          │
│  Goal: HIGH cohesion + LOW coupling                      │
│                                                          │
│  HIGH cohesion                                           │
│  → related things are TOGETHER in one unit               │
│  → unrelated things are SEPARATED into own units         │
│  → each unit has clear, single purpose                   │

│  LOW coupling                                            │
│  → units depend on each other MINIMALLY                  │
│  → communication via abstractions/interfaces             │
│  → change one unit without touching others               │

│  Splitting a god class → higher cohesion per unit        │

│                                                          │
│  Common trap:                                            │
│  Splitting too much → micro-classes with ONE method      │

## 7️⃣ Measuring Cohesion — LCOM

```js
// Lack of Cohesion of Methods (LCOM) — informal JS version:
// High LCOM = low cohesion
// Low LCOM  = high cohesion

class CohesionAnalyzer {
  // Analyze which fields each method accesses:
  analyze(className, methods) {
    const fieldSets = methods.map(m => new Set(m.accessedFields));
    let sharedPairs = 0;
    let totalPairs  = 0;

    for (let i = 0; i < fieldSets.length; i++) {
      for (let j = i + 1; j < fieldSets.length; j++) {
        totalPairs++;
        // If methods share at least one field → related:
        const shared = [...fieldSets[i]].some(f => fieldSets[j].has(f));
        if (shared) sharedPairs++;
      }
    }

    const lcom = totalPairs > 0 ? 1 - (sharedPairs / totalPairs) : 0;
    return {
      className,
      lcom,              // 0 = perfect cohesion, 1 = no cohesion
      verdict: lcom < 0.3 ? "✅ Cohesive" : lcom < 0.7 ? "⚠️ Moderate" : "❌ Low cohesion",
      sharedPairs,
      totalPairs
    };
  }
}

// Example analysis:
const analyzer = new CohesionAnalyzer();

// Cohesive class — methods share fields:
analyzer.analyze("DateFormatter", [
  { name: "format",     accessedFields: ["locale", "pattern"] },
  { name: "parse",      accessedFields: ["locale", "pattern"] },
  { name: "toRelative", accessedFields: ["locale"] },
  { name: "toISO",      accessedFields: ["pattern"] },
]);
// sharedPairs = 5/6 → LCOM ≈ 0.17 → ✅ Cohesive

// God class — methods don't share fields:
analyzer.analyze("AppUtils", [
  { name: "formatDate",       accessedFields: ["dateLocale"] },
  { name: "sendEmail",        accessedFields: ["smtpConfig"] },
  { name: "hashPassword",     accessedFields: ["bcryptRounds"] },
  { name: "parseCSV",         accessedFields: ["csvDelimiter"] },
  { name: "calculateTax",     accessedFields: ["taxRates"] },
]);

class Order {

  #items;
  #status;
  #payments    = [];
  #statusLog   = [];
  #createdAt;
  #updatedAt;

  static #VALID_TRANSITIONS = {
    pending:    ["confirmed", "cancelled"],
    confirmed:  ["processing", "cancelled"],
    processing: ["shipped", "cancelled"],
    shipped:    ["delivered", "returned"],
    delivered:  [],
    cancelled:  [],
    returned:   ["refunded"],
    refunded:   [],
  };

  constructor({ id, userId, items }) {
    if (!items?.length) throw new Error("Order must have items");
    this.#id        = id ?? crypto.randomUUID();
    this.#userId    = userId;
    this.#items     = items.map(i => ({ ...i }));
    this.#status    = "pending";
    this.#createdAt = new Date();
    this.#updatedAt = new Date();
    this.#logStatus("pending", "Order created");
  }

  // ── Queries (no mutation) ─────────────────────────────
  get id()        { return this.#id; }
  get userId()    { return this.#userId; }
  get status()    { return this.#status; }

  get createdAt() { return this.#createdAt; }

      .filter(p => p.status === "succeeded")

    return paid || this.subtotal;

    return this.#payments.some(p => p.status === "succeeded");

    return ["pending", "confirmed"].includes(this.#status);
  }

  get history() { return [...this.#statusLog]; }

  // ── Commands (mutation, return this) ─────────────────
  #transition(newStatus, reason) {
    const allowed = Order.#VALID_TRANSITIONS[this.#status];
    if (!allowed.includes(newStatus)) {
      throw new Error(`Cannot transition from ${this.#status} to ${newStatus}`);
    }
    this.#status    = newStatus;
    this.#updatedAt = new Date();
    this.#logStatus(newStatus, reason);
    return this;

    this.#payments.push({ ...payment, recordedAt: new Date() });
    this.#updatedAt = new Date();
    return this;

    if (!this.#EMAIL_RE.test(email)) throw new ValidationError("email", "Invalid email format");
    if (email.length > 254) throw new ValidationError("email", "Email too long");

  static #validatePassword(password) {
    if (typeof password !== "string") throw new TypeError("Password must be a string");
    if (password.length < 8)    throw new ValidationError("password", "Too short — min 8 chars");
    if (password.length > 128)  throw new ValidationError("password", "Too long — max 128 chars");
    if (!/[A-Z]/.test(password)) throw new ValidationError("password", "Needs uppercase letter");
    if (!/[0-9]/.test(password)) throw new ValidationError("password", "Needs a digit");
  }

  static #validateName(name, field = "name") {
    if (typeof name !== "string")  throw new TypeError(`${field} must be a string`);
    if (!this.#NAME_RE.test(name)) throw new ValidationError(field, `Invalid ${field}`);
  }

  on(event, handler) {
    this.#assertHandler(handler);
    if (!this.#handlers.has(event)) this.#handlers.set(event, new Set());
    this.#handlers.get(event).add(handler);
    return () => this.off(event, handler); // returns unsubscribe
  }

  once(event, handler) {
    this.#assertHandler(handler);
    const wrapper = async (data) => {
      this.off(event, wrapper);
      return handler(data);
    };
    wrapper._original = handler;
    return this.on(event, wrapper);
  }

  off(event, handler) {
    const handlers = this.#handlers.get(event);
    if (!handlers) return false;
    const direct  = handlers.delete(handler);
    // Also check once-wrappers:
    const wrapped = [...handlers].find(h => h._original === handler);
    if (wrapped) handlers.delete(wrapped);
    return direct || !!wrapped;
  }

  // ── Middleware ─────────────────────────────────────────
  use(middleware) {
    this.#assertHandler(middleware);
    this.#middleware.push(middleware);
    return this;
  }

  // ── Emission ───────────────────────────────────────────
  async emit(event, data) {
    const payload = await this.#runMiddleware(event, data);
    this.#log(event, payload);

    const results = await Promise.allSettled([
      ...(this.#handlers.get(event) ?? []),
      ...(this.#handlers.get("*") ?? []),
    ].map(h => h(payload)));

    const failed = results.filter(r => r.status === "rejected");
    if (failed.length > 0) {
      failed.forEach(f => this.emit("error", { event, error: f.reason }));
    }

    return results;
  }

  // ── Queries ────────────────────────────────────────────
  listenerCount(event) { return this.#handlers.get(event)?.size ?? 0; }
  hasListeners(event)  { return (this.#handlers.get(event)?.size ?? 0) > 0; }
  get events()         { return [...this.#handlers.keys()]; }
  get log()            { return [...this.#eventLog]; }

  // ── Private helpers ────────────────────────────────────
  #assertHandler(fn) {
    if (typeof fn !== "function") throw new TypeError("Handler must be a function");
  }

  async #runMiddleware(event, data) {
    let payload = data;
    for (const mw of this.#middleware) {
      payload = await mw(event, payload) ?? payload;
    }
    return payload;
  }

  #log(event, data) {
    this.#eventLog.push({ event, data, at: Date.now() });
    if (this.#eventLog.length > this.#maxLog) this.#eventLog.shift();
  }
}
// Every method, field, and helper serves event pub/sub ✅
```

## 💀 Interview Traps

### Trap 1: "Utils" and "Helpers" are always low cohesion signals

```js
// These names are red flags for coincidental cohesion:
// utils.js, helpers.js, common.js, shared.js, misc.js

// If you find yourself adding to utils.js — ask:
// "What concept unifies ALL items in this file?"

// If the answer is "they're all utility functions" → split by domain:
// utils/date.js       → DateUtils (date formatting, parsing)
// utils/string.js     → StringUtils (truncate, slugify, capitalize)
// utils/array.js      → ArrayUtils (chunk, flatten, unique)
// utils/validation.js → Validators (email, phone, url checks)

// EXCEPT: some utilities ARE cohesive around a concept:
// math-utils.js — all functions operate on numbers → cohesive ✅
// color-utils.js — all functions convert/manipulate colors → cohesive ✅
// The domain "math" or "color" IS the unifying concept ✅

// It's not the word "utils" that's wrong —
// it's the LACK OF UNIFYING CONCEPT that signals low cohesion
```

### Trap 2: Splitting too much destroys cohesion at the wrong level

```js
// OVER-SPLIT — each class has ONE method:
class UserEmailValidator { validate(email) { } }
class UserPasswordValidator { validate(pw) { } }
class UserNameValidator { validate(name) { } }
class UserAgeValidator { validate(age) { } }

// Now caller must know about 4 classes just to validate a user:
new UserEmailValidator().validate(email);
new UserPasswordValidator().validate(password);
new UserNameValidator().validate(name);
new UserAgeValidator().validate(age);
// Low cohesion at the CALLER level now — must coordinate 4 validators 😱
// Also: high coupling — caller depends on all 4

// RIGHT — cohesive at the right granularity:
class UserValidator {
  validateEmail(email)    { /* email rules */ }
  validatePassword(pw)    { /* password rules */ }
  validateName(name)      { /* name rules */ }
  validateAge(age)        { /* age rules */ }

  validateRegistration({ email, password, name, age }) {
    this.validateEmail(email);
    this.validatePassword(password);
    this.validateName(name);
    this.validateAge(age);
  }
}
// Cohesive: one class owns all user validation ✅
// Right granularity: caller needs ONE dependency ✅
```

### Trap 3: Mixing abstraction levels destroys function cohesion

```js
// LOW cohesion — mixes policy (what) and mechanism (how):
async function registerUser(email, password) {
  // Policy level (what):
  if (await userExists(email)) throw new ConflictError("Email taken");

  // Mechanism level (how) — SQL directly in business logic 😱:
  const salt = await bcrypt.genSalt(12);
  const hash = await bcrypt.hash(password, salt);
  const { rows } = await pool.query(
    "INSERT INTO users (email, hash) VALUES ($1, $2) RETURNING *",
    [email, hash]
  );

  // Policy level again:
  await sendWelcomeEmail(rows[0].email);
  return rows[0];
}

// HIGH cohesion — consistent policy level:
async function registerUser(email, password) {
  await assertEmailAvailable(email);           // policy ✅
  const user = await createUser(email, password); // policy ✅
  await sendWelcomeEmail(user.email);          // policy ✅
  return user;
}

// Details live in their own cohesive functions:
async function createUser(email, password) {
  const hash = await hashPassword(password);   // mechanism
  return userRepo.save({ email, passwordHash: hash }); // mechanism
}
```

### Trap 4: Data classes without behavior = anemic domain model

```js
// ANEMIC — class only holds data, behavior lives elsewhere:
class Order {
  constructor(data) { Object.assign(this, data); }
  // No methods — just a data bag 😱
}

// All behavior in a separate service:
class OrderService {
  static calculateTotal(order)     { return order.items.reduce(...); }
  static canBeCancelled(order)     { return order.status === "pending"; }
  static applyDiscount(order, pct) { order.discountPct = pct; } // mutates order directly
  static validateItems(order)      { /* reaches into order's structure */ }
}

// Problems:
// 1. Order class has zero cohesion — no behavior belongs to it
// 2. OrderService has artificial cohesion — all about Order, but separate
// 3. Business rules live OUTSIDE the entity they govern
// 4. Change Order's structure → must find all OrderService methods

// HIGH COHESION — behavior lives WITH data:
class Order {
  #items; #status; #discountPct = 0;

  constructor(items) { this.#items = items; this.#status = "pending"; }

  // Behavior lives WITH the data it operates on:
  get total()      { return this.subtotal * (1 - this.#discountPct); }
  get subtotal()   { return this.#items.reduce((s,i) => s + i.price * i.qty, 0); }
  get canCancel()  { return this.#status === "pending"; }

  applyDiscount(pct) {
    if (pct < 0 || pct > 1) throw new RangeError("Discount 0–1");
    this.#discountPct = pct;
    return this;
  }

  cancel() {
    if (!this.canCancel) throw new Error("Cannot cancel");
    this.#status = "cancelled";
    return this;
  }
}
```

### Trap 5: Constructor doing too much — temporal cohesion in initialization

```js
// LOW cohesion constructor — does unrelated initialization:
class WebServer {
  constructor(port) {
    this.app = express();           // HTTP setup
    this.db  = new Pool(DB_URL);   // Database setup — different concern!
    this.cache = new Redis(REDIS); // Cache setup — different concern!
    this.logger = pino();          // Logging setup — different concern!

    // Middleware setup — HTTP concern, ok:
    this.app.use(express.json());
    this.app.use(cors());

    // Configuring DB — not HTTP server's concern 😱:
    this.db.on("error", err => this.logger.error(err));
    this.db.query("SET search_path=public");

    this.app.listen(port);
  }
}

// HIGH cohesion — WebServer only cares about HTTP:
class WebServer {
  #app; #port;

  constructor(port, middlewares = []) {
    this.#app  = express();
    this.#port = port;
    middlewares.forEach(m => this.#app.use(m)); // HTTP concern ✅
  }

  addRoute(method, path, handler) {
    this.#app[method](path, handler);
    return this;
  }

  async start() {
    return new Promise(resolve =>
      this.#app.listen(this.#port, resolve)
    );
  }
}

// Database has its own cohesive class:
class DatabaseService {
  constructor(config) { this.#pool = new Pool(config); }
  async connect() { /* validate connection */ }
  query(sql, p) { return this.#pool.query(sql, p); }
}
```

## 📊 DSA / Internals Connection

> Cohesion maps directly to the **information hiding** principle in CS theory (Parnas, 1972) — a module should encapsulate one design decision. High cohesion = one decision encapsulated. Low cohesion = multiple unrelated decisions in one unit, hiding nothing.
>
> In V8, cohesion has a direct performance connection via **hidden classes (shapes)**. A cohesive class always creates objects with the same properties in the same order → all instances share ONE hidden class → property access via shape-indexed lookup → O(1), cache-friendly. A low-cohesion god class creates objects with different properties depending on which methods you call → multiple hidden classes → inline cache becomes **polymorphic** (2–4 shapes) or **megamorphic** (5+ shapes) → slower property access on every access in hot code paths.
>
> The **LCOM (Lack of Cohesion of Methods)** metric is a graph theory problem: create a bipartite graph where methods and instance variables are nodes, edges connect methods to variables they access. LCOM = number of disconnected subgraphs in this bipartite graph. Zero disconnected components = perfectly cohesive. Multiple disconnected components = the class should be split.
